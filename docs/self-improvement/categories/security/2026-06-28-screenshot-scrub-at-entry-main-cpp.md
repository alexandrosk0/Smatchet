- 2026-06-28 · orchestrator (PR-D #1566 spawn-auth) · [security] · P3 — defence-in-depth: if a pre-plugin subprocess is ever added to `Source/Standalone/main.cpp`, scrub `SMATCHET_MCP_SPAWN_TOKEN` from its inherited environment at entry
  Details: PR-D's M1 fix builds an explicit merged `lpEnvironment` block for the spawned child (Windows) / `setenv` on the forked child (POSIX) so the per-spawn MCP token is injected *only* into the intended child, replacing the prior transient parent-env mutation that briefly exposed the token to any concurrently-spawned process. The token therefore does NOT live in the parent process environment today. BUT: that guarantee is structural, not enforced — it holds only because `main.cpp` spawns nothing else before the MCP plugin owns the token. If a future change adds an earlier subprocess (telemetry pinger, crash-handler relaunch, updater probe, etc.) that inherits the full parent env, and the token were ever placed in the parent env again, it would leak to that subprocess. Low likelihood (no such subprocess exists; token is loopback-only + ephemeral per-spawn), hence P3.
  Concrete next action: NO action now. WHEN a pre-plugin subprocess is added to `main.cpp`: either (a) keep using an explicit merged env block per child (never put the token in the parent env) — the pattern PR-D already establishes — or (b) `unsetenv("SMATCHET_MCP_SPAWN_TOKEN")` / drop it from the parent env immediately before any non-MCP `CreateProcess`/`fork+exec`.
