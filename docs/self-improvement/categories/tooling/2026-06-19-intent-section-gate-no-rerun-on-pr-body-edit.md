- 2026-06-19 · orchestrator · [tooling] · P3 — `intent-section-gate-no-rerun-on-pr-body-edit`: the block-allowlisted `Intent section` doc-validation gate reads `github.event.pull_request.body`, but its `pull_request` trigger declares no `types:` (GitHub defaults to opened/synchronize/reopened — NOT `edited`), so filling a `## Intent` section via `gh pr edit` after open does NOT re-run the gate; the stale red persists until a push (synchronize) re-reads the body.
  Details: on #1417 I added the required `## Intent` section with `gh pr edit --body`, but the PR stayed BLOCKED — `Intent section` (on `merge-gates.sh` `MERGE_GATES_BLOCK_ALLOWLIST_RE`, ADR-0022) was still red. Root cause: `.github/workflows/doc-validation.yml`'s `pull_request:` trigger lists no `types:`, so GitHub's default event set (opened, synchronize, reopened) excludes `edited` — the body-reading gate never re-evaluates on a metadata-only body change. I cleared it with an empty `git commit --allow-empty` (a synchronize event), which re-read the now-filled body and went green. Distinct from `intent-gate-bypassed-via-non-poller-merge` (process/, same date), which is the MERGE path skipping a red Intent; this is the CHECK never re-running after the fix that should clear it, so an author burns a wasted push-cycle every time they fill `## Intent` post-open.
  Concrete next action: re-trigger on body edits without re-running the whole heavy doc-validation suite per edit — preferred (a) split the `Intent section` job into its own minimal workflow whose `pull_request` trigger is `types: [opened, edited, synchronize, reopened]` (cheap — the job only reads the PR body); or (b) add `types: [opened, synchronize, reopened, edited]` to `doc-validation.yml`'s `pull_request` trigger and accept the full-suite re-run on each body edit. Until then, document in `ship-loops.md`: after adding/fixing `## Intent` on an open PR, push (an empty commit if needed) to clear the stale red. Est ~30 min for (a).
