## Context

The plan-lock system (git-ref CAS locks under `refs/locks/*`, design `docs/plans/shipped/git-ref-plan-locks.md`) is **healthy but dormant**: a 9/9 primitive self-test passes, all three render/staleness/cleanup workflows are green, but the last 20 PRs (#1378–#1401) were solo/sequential single-subsystem work that never filed a claim, and the render mirror `docs/plans/active/_plan-locks.generated.md` has shown "No active plan-locks" unchanged since 2026-05-31 (`d7bc9e7f`). Filing a lock is currently **advisory** — nothing forces an agent to claim a write set before editing files, so two parallel agents editing the same files silently race; the only protection is each agent voluntarily running the pre-flight overlap check documented in `_plan-locks-archive.md`.

This plan makes lock-filing **enforced, but only when it matters**: a write set must be claimed before edits **iff another session is concurrently live** (force-on-contention). Solo/sequential work — the common case — pays zero tax. Enforcement is defense-in-depth across three layers so no single harness or bypass defeats it: (A) a Claude Code `PreToolUse` hook at edit time, (B) a harness-agnostic `pre-push` git hook, (C) a server-side CI merge-gate that is unbypassable except via an explicit out-of-band label.

After this lands, X is true: **when ≥2 sessions are live and an agent edits a file outside any lock it holds, the edit (A) / push (B) / merge (C) is blocked with a copy-paste `lock-claim.sh` remediation line, while solo work is never gated.** Originating thread: session investigation of "are the _plan-locks working?" → "how can we force all agents to file a plan lock before changing any files?" (design forks locked: Scope = force-on-contention; Layers = all three A+B+C).

## Approach

Layer A's trigger is a **repo-global** live-agent count, not a per-tree one. A single `sr_count_live_siblings` call (`agents/scripts/core/session-registry-lib.sh:146`) only scans the local tree's `.claude/.active-sessions`, so two sibling worktrees never see each other — useless for the canonical `nsc slug-A` / `nsc slug-B` parallel setup. Instead the hook enumerates `git worktree list --porcelain` and calls `sr_count_live_siblings(regdir, own_sid, now)` **once per worktree registry** (the integration tree is itself a worktree in that list), summing into a **repo-global sibling count**. `sr_count_live_siblings` excludes this session's own `session_id` in whichever registry holds it and no-ops the exclusion elsewhere, so the per-tree calls compose cleanly. The trigger is **≥2 agents live ≡ ≥1 sibling**, not write-set overlap — overlap is circular (you can't compute it until everyone has already filed a lock, which is the behaviour being forced). When the sibling count is **0** (solo) the hook `exit 0`s (no tax on solo work). When **≥1 sibling** it requires the edit's target path be covered by a `refs/locks/*` claim whose `branch` matches this worktree's current HEAD branch (i.e. *this* session's own seed lock — `owner`/`AGENT_ID` is **not** the discriminator; see the identity note below), else emits `permissionDecision: "deny"` with a copy-paste `lock-claim.sh` line. The lock-table read is `locks-show.sh`-backed (`git fetch +refs/locks/*` + `cat-file`) and cached ~30 s; any network/parse/worktree-enum failure **fails open** (advisory, never wedge a session).

The three layers are deliberately asymmetric in their fail-mode. A and B are **advisory / fail-open** local hooks (catch the mistake early, cheaply, but never hard-wedge a flaky-network session) — A at edit time inside Claude Code, B at `git push` time for any harness (the catch-all for non-Claude-Code agents, wired via `core.hooksPath`). C is the **fail-closed hard net**: a GitHub Actions check (named `Plan-lock gate`) that recomputes contention server-side (overlap between this PR's changed files and any **other-branch `refs/locks/*` write set** — the declared-write-set basis **only**, NOT raw other-open-PR changed-file sets; non-circular, since it does not require THIS PR to have filed a lock) and reds — blocking merge. Its blocking power comes from the **meant-to-block allow-list** (`MERGE_GATES_BLOCK_ALLOWLIST_RE`, `merge-gates.sh:132`), NOT a new branch-protection required check — the #923 mechanism: a non-required check whose name is on the allow-list blocks merge with zero out-of-repo branch-protection mutation. Unbypassable except the `plan-lock-out-of-band` label that downgrades the `Plan-lock gate` RED → WARN via the poller's jq-filter CI-downgrade path (`ci_warn_downgraded`), identical to `tests-out-of-band` → `Test-delta gate` / `perf-out-of-band` → `Perf PR-fast` (NOT the bespoke gate-scoped `cr-out-of-band` path). This is the same advisory-pair-plus-hard-net shape the tree-guards already use (`guard-shared-tree.sh` advisory + `guard-head-drift.sh` hard net).

**Identity: all three layers key on `branch`, never `owner` / `AGENT_ID`.** `AGENT_ID` is **unprovisioned in every production session** — `lock-claim.sh:84` / `lock-claim-update.sh:99` default `${AGENT_ID:-orchestrator}`, and only the test suite (`test-lock-primitives.sh`) ever sets it. So every real lock is `owner=orchestrator`, and a guard reading `AGENT_ID` also gets `orchestrator`: an **owner-keyed check is a no-op** — two parallel sessions both read `owner==orchestrator`, each sees the other's lock as "mine," and the collision the layer exists to catch slips straight through. The reliable, always-derivable discriminator is **`branch`**: Layer A allows an edit iff the path is covered by a lock whose `branch` == this worktree's HEAD branch (my own seed); Layer B refuses a push overlapping a lock from a different branch; Layer C blocks a PR whose `github.head_ref` ≠ an overlapping lock's `branch`. `owner` stays in `claim.json` as advisory metadata (audit + `locks-show.sh` display), **not a gate**. Re-introducing owner-keying anywhere silently restores the pass-through bug — the Layer A bats carries an owner-collision canary (two `owner=orchestrator` locks on different branches must still deny). **Same-tree-same-branch contention** (two sessions sharing one integration tree on the same branch) is **out of plan-lock scope** — the tree guards (`guard-shared-tree.sh` / `guard-head-drift.sh`) own that hazard; plan-locks target cross-*branch* parallel work.

**Lock seeding (adoption).** A lock must already exist when a *second* agent's first edit hits the guard — so seeding is **eager and decoupled from enforcement**: the ship-loop files a claim from the plan-doc's **§Files-to-modify** list at task start whenever a plan exists, reusing the declared write set verbatim (no separate discovery step). Eager seeding closes the race where agent A starts solo, files nothing, then agent B goes live and A is now contended with no lock filed — by always seeding from the plan, A's claim is present as the early-warning substrate the moment B arrives. *Seeding* is eager (file whenever a plan exists); *enforcement* (the deny) stays force-on-contention (≥2 live) — the two are independent. Plan-less tasks (small fixes, no plan-doc) have no auto-seed: they file on the first deny via the `lock-claim.sh` one-liner the guard hands them, and force-on-contention makes plan-less-AND-contended rare. `lock-claim-update.sh` expands the seeded set on mid-work discovery.

**Coverage match (how an edited path matches a `write_set`).** `write_set` is a raw repo-relative path list (`_lock-json.py:48-55` — no normalization, no globbing applied at claim time). An edited path is **covered** iff, after normalizing both sides to repo-relative forward-slash, it string-equals a `write_set` entry **or** sits under an entry that ends in `/` (directory prefix). **No glob engine** — plain equality + dir-prefix is the one rule that is byte-identical in bash (Layers A/B) and Python (Layer C); `fnmatch` / shell-glob semantics diverge subtly between the two and would let a layer pass locally while C blocks. The seed extracts clean entries from the plan's **§Files-to-modify** (stripping the `(new)` / ` — description` annotations); plan authors write a bare path or a dir-prefix entry (the strict-zone case, e.g. `Source/Core/src/Sync/`, is one dir entry). Mid-work growth re-files the **full** grown set via `lock-claim-update.sh <slug> <write-set-file>` — the git-ref backend *replaces* `write_set` from the file (`lock-claim-update.sh:124-129`), it does **not** append, so the deny one-liner hands a full-set path, never a single filename.

The non-obvious trade-off that shaped the design: **filing a claim must never itself be blocked.** `lock-claim.sh` builds its orphan commit via `git hash-object` / `git mktree` / `git commit-tree` and pushes a ref — it writes **zero** working-tree files — so the edit-time guard can never create a chicken-and-egg deadlock where you can't claim because claiming requires an edit. Mid-work write-set discovery (an agent realises it must touch a file it didn't list) is handled by `lock-claim-update.sh` (holder-only scope expansion); the guard's deny message hands the agent the exact one-liner.

## Risks / non-goals

**Risks:**
- **Per-edit network cost (Layer A).** Each edit under contention would otherwise `git ls-remote refs/locks/*`. Mitigation: `lock-table-cache.sh` caches the table in a temp file with ~30 s TTL; cache miss refreshes, network error **fails open** (advisory bias-to-allow, identical to `guard-shared-tree.sh`'s missing-lib fall-open `:70`).
- **Mid-work file discovery friction.** An agent that discovers it must touch an unlisted file is blocked on the first edit. Mitigation/intent: this friction is the point (it forces write-set honesty); the deny message hands the exact `lock-claim-update.sh <slug> <write-set-file>` one-liner (holder-only, one round-trip) — the file must hold the **full grown set**, because the git-ref backend *replaces* `write_set` from it (`lock-claim-update.sh:124-129`), not just the newly-discovered path. Accepted; an opt-in `SMATCHET_PLAN_LOCK_AUTOEXPAND=1` fast-path that auto-expands the holder's own lock is documented but **off by default** (auditability over convenience).
- **Override-env footgun (the exact bug this design must not repeat).** An inline `SMATCHET_REQUIRE_PLAN_LOCK=0 <edit>` prefix does **not** reach a PreToolUse hook — the hook reads its own env before the tool runs. Mitigation: the deny message copies `guard-shared-tree.sh:150`'s wording verbatim — "export … in the session env BEFORE launch." Accepted (inherent to the hook model).
- **False-block on solo work.** Mitigation: force-on-contention — repo-global sibling count 0 (no *other* live agent) → `exit 0`. Zero tax on the common case. (Threshold is ≥1 sibling, not ≥2 — the "excluding self" off-by-one trap.) **Verification dependency (confirm at impl):** a worktree session must self-register a `.claude/.active-sessions/<id>` entry (writer = `session-heartbeat.sh` / `session-tree-banner.sh`); if a worktree session does NOT register in its own tree, the global sum under-reports and Layer A silently no-ops. Layers B/C (origin `refs/locks/*`) still catch it — but flag this in the impl so Layer A isn't trusted as the sole net.
- **Fail-open layers could let a contended edit through.** Accepted by design: A/B are advisory (catch-early, never wedge); **Layer C is the fail-closed hard net** (server-side required check, unbypassable except the explicit `plan-lock-out-of-band` label). Defense-in-depth, same shape as `guard-shared-tree.sh` (advisory) + `guard-head-drift.sh` (hard net).
- **Stale lock wedging contention detection.** A claim from an abandoned session could falsely block. Mitigation: Layer C treats a lock older than `lock-staleness.yml`'s `THRESHOLD_DAYS=14` as non-blocking; the daily sweep frees it regardless.
- **Unattributable lock (empty / detached `branch`).** `lock-claim.sh:85` defaults `branch` to `detached` (or empty via `LOCK_BRANCH=""`) when HEAD has no symbolic ref. Layer C cannot attribute such a lock to a branch, so it treats an empty / `detached` `branch` as **non-blocking** (bias-to-allow — the hard net must not wedge on an un-attributable claim; the stale sweep ages it out). Surfaces the agent flow as the place to guarantee `LOCK_BRANCH` is set when seeding.
- **Chicken-and-egg deadlock — NOT a risk (explicit non-risk).** `lock-claim.sh` touches no working-tree file, so claiming is never itself gated by the edit guard. Cited so a reviewer doesn't re-raise it.

**Non-goals:**
- Not *gating/blocking* solo/sequential work — enforcement (the deny) is force-on-contention only; a solo edit is never blocked. (Eager seeding still files a lock from the plan on a solo plan-task, but filing is a free, non-blocking ref push; the "no tax" guarantee is about *blocking*, not about whether a ref is pushed.)
- Not changing the lock wire format, ref layout, or backend dispatch (`SMATCHET_LOCK_BACKEND=p4-counter` still works; see Out of scope).
- Not building a lock dashboard / UI / live-contention visualiser.
- Not rewriting the frozen `_plan-locks-archive.md` advisory protocol history (it stays frozen at the 2026-05-17 cutover).
- Not covering **same-tree-same-branch** contention (two sessions on one integration tree, same branch) — the tree guards (`guard-shared-tree.sh` / `guard-head-drift.sh`) own that hazard; plan-locks key on `branch`, so a shared branch is indistinguishable to them by design. Cross-*branch* parallel work is the target.
- Not provisioning a per-session `AGENT_ID` — `owner` stays advisory-only metadata; all gating is `branch`-keyed (the unprovisioned-`AGENT_ID` finding, see § Approach identity note). Per-session granularity is unnecessary because the only case it would add (two sessions, same branch) is tree-guard scope above.
