# Plan — Dev onboarding, first-run tracker setup, QUICKSTART

> **Slug**: `dev-onboarding-first-run-quickstart` (matches this file's basename without `.md`).
>
> **Status**: `active` — three independently shippable slices. Slice 3 (QUICKSTART) must land at-or-after slice 1 so it cites the real entry point; slice 2 is independent of both.

## Context

Three onboarding gaps surfaced from a fresh Windows clone/build session plus a UX walkthrough of first launch:

1. **Build friction.** [`docs/plans/msvc-build-onboarding-hardening.md`](../shipped/msvc-build-onboarding-hardening.md) § Approach promised that `build_standalone.ps1` would "bootstrap the Visual Studio compiler environment automatically for `*-msvc` presets", and its § Implementation log line 85 asserts *"`build_standalone.ps1` (plan file 1) already had the MSVC bootstrap from slice 1."* **That is false in the tree**: [`scripts/dev/local/build_standalone.ps1`](../../../scripts/dev/local/build_standalone.ps1) contains zero `vcvars` import — its only `vswhere` use is `Get-VsWherePath` (:77-95) locating MSBuild for the VS-generator branch. Callers must still wrap with [`scripts/dev/with-msvc.ps1`](../../../scripts/dev/with-msvc.ps1) when `cl.exe` is absent from PATH. A shipped plan claiming a delivery it did not make is itself a gate escape — § Out of scope names the postmortem follow-up.
2. **First-run product gap.** Fresh installs already open Preferences and default to read-only ([`ConfigManager.cpp:1478-1483`](../../../Source/Core/src/Config/ConfigManager.cpp:1478) sets `ReadOnlyMode = true` + `ShowPreferencesWindow = true` when no config file existed), so the user does land on the Preferences window — but the **Tracker tab does nothing to guide them**. It has no completion state, no explanation of why the app is read-only, and — unlike the Assistant and Whisper tabs ([`AiPrefsTestConnection.h`](../../../Source/Core/include/AiPrefsTestConnection.h), [`SmatchetPreferencesUi_Whisper.cpp`](../../../Source/Core/src/Ui/SmatchetPreferencesUi_Whisper.cpp)) — **no Test-connection control at all**. The only tracker reachability probe today is the **background poller** in [`AppController_Connectivity.cpp:158-177`](../../../Source/Core/src/AppController_Connectivity.cpp:158), which probes the **already-live focused-context backend** and therefore cannot validate credentials the user has not yet committed. Net effect: a new user types a token, hits Save & Sync, and learns it was wrong only via a downstream sync failure.
3. **Doc friction.** [`BUILD.md`](../../../BUILD.md) is complete but long. New contributors want a ≤35-line "clone → build → run → connect tracker" path at repo root.

**Intended outcome**: after all three slices land, a Windows user runs `.\build.ps1` from an ordinary PowerShell (no VS Developer Prompt), reads `QUICKSTART.md` for the five-step path, and on first launch lands on a Tracker tab that explains the read-only state, verifies credentials against the live backend **before** committing them, and clears read-only only once they are proven.

## Approach

Three PR-sized slices, one concern each, no cross-slice code coupling (slice 3 only cross-links slice 1's entry point).

**Slice 1 — root `build.ps1` + the missing MSVC bootstrap.** Extract the vcvars-discovery/import block from `with-msvc.ps1` into a dot-sourced module `scripts/common/SmatchetMsvcEnv.ps1` exposing `Test-SmatchetMsvcAvailable` + `Import-SmatchetMsvcEnvironment`; have `with-msvc.ps1` (behaviour-preserving refactor) and `build_standalone.ps1` (the actual gap-close) both call it. Add a root `build.ps1` that resolves the repo root from `$PSScriptRoot`, auto-selects a preset, prints the chosen preset **and the reason**, then delegates to `scripts/dev/local/build_and_run.ps1`. `build.ps1` carries **no CMake logic and no build logic** — the existing wrappers stay the implementation. That constraint is not stylistic: it is the whole mitigation for the kill-PowerShell collision (§ Risks), so a reviewer should reject any build logic that lands in `build.ps1`.

**Slice 2 — make the Preferences Tracker tab a real setup surface.** No new banner and no new window: first run already opens Preferences on this tab, so the work goes into the surface already in front of the user. Three pieces. (a) A **candidate-credential probe** — the one genuinely new mechanism. `ITrackerBackendFactory::Create(trackerType, cfg)` ([`ITrackerBackendFactory.h:30`](../../../Source/Core/include/ITrackerBackendFactory.h:30)) already builds a backend from an arbitrary `TrackerConfig`, so a Test-connection button can build a throwaway backend from the *uncommitted buffer* values, call `Connectivity().ProbeReachability(cfg)` on a worker, and post the verdict back through `app.mainThreadDispatcher`, with a cancel-atom guard copied from `AiPrefsTestConnection::TriggerProbe`. (b) A **`TrackerSetupCompleted` flag** driving a first-run explainer on the tab ("Smatchet is read-only until a tracker is connected") and gating the read-only clear on a verified probe. (c) The buffer→config copy currently inlined at the top of `onPreferencesSaveAndSync` gets **extracted with a signature that fills a caller-supplied `TrackerConfig`**, not one that writes into `d.cfg` — the probe needs a candidate config built from the buffers *without* mutating the live config, and Save & Sync simply passes `d.cfg` as the out-param. The probe helper lives in its own TU so bucket-E can drive it without traversing the tab — the same reason `AiPrefsTestConnection` was lifted out of its own tab.

**Slice 3 — `QUICKSTART.md`.** Pure docs; leads with `.\build.ps1`, demotes raw preset blocks in `README.md` to an "Advanced" subsection.

## UX Pillar callouts

- **Pillar 1 (perf, 144 Hz / 6.94 ms steady-state)**: slices 1 + 3 have no runtime impact. Slice 2 adds **no always-on draw work** — every new widget lives inside the Preferences window, which is not drawn when closed, and the explainer sits behind a `NeedsSetup` bool test. The probe runs off-thread. Steady-state cost with Preferences closed is zero.
- **Pillar 2 (UI-thread never blocks > 100 ms without visible cue)**: the credential probe is network I/O and **must never** run inline. It goes on a detached worker with a `mainThreadDispatcher` post-back; the button flips to a disabled "Testing…" state for the duration — the same visible-cue shape the Assistant tab already ships. The `/* PILLAR2_WORKER_ONLY */ // est-latency: <N>ms` annotation is required on the probe body.
- **Pillar 3 (never crash)**: three hazards. (a) Probe supersession — the cancel atom must be re-created per trigger and checked inside the posted lambda, or a late verdict writes into `UiDrawSession` state after Preferences closed. (b) Backend lifetime — the throwaway backend is captured by value in the worker lambda and never installed on a context (ADR-0012). (c) The veteran migration runs inside `ConfigManager::Load`'s already-`try`-wrapped region and must not throw on a partially-populated config; `ShouldGrandfatherExistingUser` takes a `const&` and performs no allocation beyond string compares.
- **Pillar 4 (accessibility — keyboard nav / font scaling / WCAG AA)**: all new controls are standard `ImGui::Button` / `InputText` / `TextWrapped` inside an existing tab, so tab-order and font scaling come free. WCAG AA contrast on the verdict colours is **not** audited here — the tab reuses the Assistant tab's `resultType` colour convention, so it inherits whatever that already is. Flagged, not fixed.

## Risks / non-goals

### Risks

- **Collision with [`docs/plans/kill-powershell-minimize-toolchain.md`](kill-powershell-minimize-toolchain.md)** — that active plan's Phase 1 converts `build_and_run.ps1` and `build_standalone.ps1` to bash, and Phase 2 ports `scripts/common/SmatchetCMakeCommon.ps1` to `.sh`. This plan adds a **new** root `build.ps1` and a **new** `scripts/common/SmatchetMsvcEnv.ps1` on top of exactly those files. Direct collision, not a parity gap. **Mitigation (decided: keep kill-PS alive, ship the shim)**: `build.ps1` is a ≤60-line dispatcher with zero build logic, so kill-PS re-points its single delegation line at `build-and-run.sh` and keeps the entry-point name; and `SmatchetMsvcEnv.ps1` is added to kill-PS's Phase-2 port list **in the slice-1 PR** (a one-line edit to that plan — do not defer it; an unrecorded collision is exactly how the msvc-onboarding claim went stale). Slice 1 must not grow build logic into `build.ps1`; that is what would make the collision expensive.
- **`app-controller-fan-in` gate fires** — `TrackerCredentialProbe` needs `#include "AppController.h"` (for both the factory accessor and `mainThreadDispatcher`), and that gate is a **hard-FAIL ratchet-down-only** cap at the current baseline (115), *not* WARN-first. Accepted as the cost of keeping fixture injection testable (item 15): add `SMATCHET_DEVIATION(rule=app-controller-fan-in; reason=candidate-credential probe needs the backend factory + main-thread dispatcher; owner=<author>; revisit=<date>)` above the include. Budget one gate-argument round in review.
- **Stale-credential grandfathering** — `ShouldGrandfatherExistingUser` checks that a credential is *present*, not that it *works*. A user with a revoked PAT is silently skipped past the one surface built to fix them. **Accepted for v1**: the Test-connection button is available to them on demand, and gating the migration on the background poller's last verdict would make config load depend on network state, which is worse. Revisit if it generates reports.
- **Offline first run** — clearing `ReadOnlyMode` only behind a green probe strands a user with no network in permanent read-only. Mitigation: an explicit secondary action on the explainer — "Save without verifying (stays read-only)" — which persists the credentials and sets `TrackerSetupCompleted = true` but leaves `ReadOnlyMode` untouched, so the background poller can flip it later. The safety default is never silently discarded.
- **Verified-state staleness** — a green probe followed by a keystroke in the token field must not still count as verified. Mitigation: `trackerPrefsTestVerifiedFingerprint` (item 18); the read-only clear compares it against the current buffers and refuses on mismatch. This is a bucket-E assertion, not a code-review promise.
- **MSVC env import mutates process env** — accepted; scoped to the script process, identical to existing `with-msvc.ps1` behaviour.
- **Silent loss of the LLVM PATH de-prioritisation during extraction** — the one `with-msvc.ps1` behaviour with no existing guard; breaks `ninja-clang-*` in a way that reads as a compiler bug. Mitigated by test case (e) in item 5.
- **Preset auto-detect picks the wrong toolchain** — mitigated by printing the chosen preset *and the reason*; explicit `-Preset` always wins; test-build-wrapper asserts the table.
- **Discoverability** — with no banner, a user who closes Preferences before finishing setup gets no further nudge until they reopen it. Accepted for v1: they are already in read-only and that state is visible in the main UI. A first-run banner or coachmark is the named follow-up (§ Out of scope) if this proves insufficient.

- No new first-run window, banner, or modal. The tab that already opens is the surface.
- No Whisper / MCP / AI-assistant steps. Whisper keeps its own banner.
- No Perforce setup — tracker backends only.
- No Linux/macOS build wrapper. Windows-first; `QUICKSTART.md` says so explicitly.
