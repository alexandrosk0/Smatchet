## Approach (expanded)

**Keep the internal layout of the new repo byte-identical to the current in-tree layout** (`agents/…`, `docs/agent-rules/…`, `docs/harness/…`, `AGENTS.md` at the new repo's root; from `docs/self-improvement/` only the framework doc `AGENT_SELF_IMPROVEMENT.md` moves — the entries, ledgers and `categories/` stay host-side per grill decision 4 / ADR-0025). Every intra-surface relative link and script path then survives the move unchanged; only **cross-boundary** references (surface ↔ product) need rewriting. Cross-boundary means exactly four shapes: (a) a layer script reading host content (`docs/plans/`, `docs/self-improvement/categories/`, `backlog/`, `Source/`, `project.config.json`); (b) a host script or workflow invoking `agents/scripts/…`; (c) a harness adapter materialising `.claude/`-style links whose *source* is layer content and whose *dest* is host-side; (d) markdown links that cross the boundary in either direction. `docs/PORTABILITY.md` § External path contracts is the **starting hint** for (a)+(b), not ground truth — its own line citations have already rotted (it cites `test-backlog-counts.sh` lines 32-33/40-49; the live file has `INDEX`/`DIR` at **36-37** and the `declare -A FILES` map at **41-51**, a since-added bypass/exit-code comment block shifted everything +4; its `setup-harness.sh` row still describes a `link_dir ".claude/agents" "agents"` call that no longer exists at all). Phase A therefore **re-derives** the inventory from the tree and treats the table as a cross-check, not a source.

**De-risk with an indirection phase before the move.** Phase A introduces a **dual-root** pair — `PROJECT_ROOT` (host tree: plans, backlog, entries, `Source/`, `project.config.json`) and `AGENT_LAYER_ROOT` (layer tree: `agents/`, `docs/agent-rules/`, `docs/harness/`) — both exported by `project-config.sh` (bare names plus `PC_PROJECT_ROOT` / `PC_AGENT_LAYER_ROOT` twins so `bash scripts/dev/project-config.sh` prints them for debugging, matching that file's existing `PC_<UPPER_SNAKE>` contract), both defaulting to the repo root pre-flip, and rewrites every consumer (workflows, `scripts/dev/*`, hooks, `setup-harness.sh`, docs where load-bearing) to address each tree through the right root **while the files have not moved**. The actual flip (Phase C) then changes one value (`AGENT_LAYER_ROOT=agent-layer`) plus the `git rm` + `git submodule add`, instead of a big-bang path rewrite entangled with the move itself. Layer scripts that read *host* content (plan index, backlog counts, entry sweeps, the merge-snapshot ledger, the plan-lock table) resolve via `PROJECT_ROOT`; scripts that read *layer* content (agent-contract checks, harness provisioning, the script-freshness self-fingerprint) resolve via `AGENT_LAYER_ROOT` — the distinction is what lets the layer repo run standalone (`PROJECT_ROOT=$AGENT_LAYER_ROOT`, its own `project.config.json`). A third class exists and is the one the binary framing hides: **dual-root scripts** that read both trees in one file (`merge-gates.sh`, `git-janitor.sh`, the plan-lock set). Those need both vars sourced, not a single substitution — Phase A row 5a classifies every consumer into single-root vs dual-root before any edit lands.

**Phase ordering is load-bearing, not cosmetic.** A → B → C → D is the only order in which each step is independently revertible:

- **A before B** — the indirection is provably a no-op while both roots point at the same tree, so a regression in Phase A is attributable to the rewire alone and reverts as one PR. Doing the rewire *with* the move would make every red check ambiguous between "path var wrong" and "file missing".
- **B before C** — the layer repo must exist, be green on its own CI, and be reachable at the `.gitmodules` URL before Smatchet deletes anything. Phase C's `git rm` is only safe once the deleted content has a proven upstream home.
- **C before D** — the two-repo ship-loop docs and `auto-bump.yml` describe a topology that does not exist until the flip lands; writing them earlier makes them untestable prose.
- **A is itself three PRs** (see the Phase A preamble below) because the rewire's file count (31 checkout-bearing workflow files — a **superset** containing the 14 that also invoke `agents/` scripts, out of 33 workflow files total — plus ~60 layer scripts) exceeds the per-PR file ceiling that keeps CodeRabbit review usable, and the natural seams are clean.

**"CI proves the indirection green" means, concretely:** every Phase A PR is green on the **nine PR-binding lanes** — `agentic-selftests` (all 94 bats suites, both sides of the future 61/33 split), `build-and-test`, `codeql`, `doc-validation`, `dup-scan`, `mobile-security`, `perf-pr-fast`, `plan-lock-gate`, `shell-lint` (all nine trigger on `pull_request`; five also on `merge_group`) — plus a **manual `workflow_dispatch` smoke** on the four lanes that never fire on a PR and would otherwise ship unproven: `cr-oob-review-backfill`, `issue-janitor`, `locks-render`, `lock-staleness`. `dependabot-auto-merge` is `workflow_run`-only with **no** dispatch trigger — it cannot be proven on the PR; its edit must therefore be a pure literal substitution, called out in the PR body for reviewer attention, and confirmed on the first live dependabot PR after merge. A Phase A PR that is green on the nine but skipped the four dispatch smokes has **not** proven the indirection.

**Two-repo ship-loop is the real ongoing cost** and is designed in, not discovered later: an agent-surface edit becomes (1) a PR in `the-unwilling-agentic-bunch` gated by that repo's own CI (agentic-selftests over the 61 moved bats suites, shell-lint, doc-validation subset, merge-gates.sh reused on itself), then (2) a one-line submodule-pointer-bump PR in Smatchet — **opened automatically by a per-merge workflow in the layer repo** (grill decision 5), with `git-janitor` as backstop proposer and the new `agent-layer-integration.yml` host lane as the bump PR's binding check (grill decision 3). `docs/agent-rules/ship-loops.md` gets a new § Two-repo ship-loop codifying this. The trade-off accepted: per-edit friction up, in exchange for independent versioning/release of the layer and true reuse.

1. `scripts/dev/project-config.sh` — export the dual-root pair: `AGENT_LAYER_ROOT` (default `$REPO_ROOT`) + `PROJECT_ROOT` (default `$REPO_ROOT`) + `PC_*` twins; `project.config.json` resolution order `$SMATCHET_PROJECT_CONFIG` env → superproject root (`git rev-parse --show-superproject-working-tree`) → layer repo root, so the same script works host-side, from inside the future submodule, and standalone in the layer repo's own CI (`PROJECT_ROOT=$AGENT_LAYER_ROOT` there). **[PR A1]**
   - **1a — reconcile with the pre-existing `PC_CONFIG_FILE` override.** Line 18 already does `PC_CONFIG_FILE="${PC_CONFIG_FILE:-$_pc_root/project.config.json}"`; that hook predates this plan and is what bats fixtures inject. It stays **rung 0, highest precedence** (a caller naming an exact file is strictly more specific than a root); `$SMATCHET_PROJECT_CONFIG` is rung 1 and accepts either a file or a directory. Concrete sketch replacing lines 15-18 — note line 42's `PC_SCHEMA_FILE="${PC_SCHEMA_FILE:-$_pc_root/…}"` derives from the same `$_pc_root` and must be re-pointed at the **resolved** config's directory in the same edit, or the schema lookup keeps using the old root:

     ```sh
     _pc_self="${BASH_SOURCE[0]:-$0}"
     _pc_layer_root="$(cd "$(dirname "$_pc_self")/../.." && pwd)"   # was $_pc_root
     _pc_super="$(git -C "$_pc_layer_root" rev-parse --show-superproject-working-tree 2>/dev/null | tr -d '\r')"

     _pc_resolve_config() {
       [ -n "${PC_CONFIG_FILE:-}" ] && { printf '%s\n' "$PC_CONFIG_FILE"; return; }          # rung 0
       if [ -n "${SMATCHET_PROJECT_CONFIG:-}" ]; then                                        # rung 1
         case "${SMATCHET_PROJECT_CONFIG//\\//}" in                    # must be ABSOLUTE
           /*|[A-Za-z]:/*) ;;
           *) echo "project-config: SMATCHET_PROJECT_CONFIG must be an absolute path (got '$SMATCHET_PROJECT_CONFIG')" >&2; return 1 ;;
         esac
         if [ -d "$SMATCHET_PROJECT_CONFIG" ]
           then printf '%s/project.config.json\n' "$SMATCHET_PROJECT_CONFIG"
           else printf '%s\n' "$SMATCHET_PROJECT_CONFIG"; fi
         return
       fi
       if [ -n "$_pc_super" ] && [ -f "$_pc_super/project.config.json" ]; then               # rung 2
         printf '%s/project.config.json\n' "$_pc_super"; return
       fi
       printf '%s/project.config.json\n' "$_pc_layer_root"                                   # rung 3
     }
     PC_CONFIG_FILE="$(_pc_resolve_config)"
     PC_SCHEMA_FILE="${PC_SCHEMA_FILE:-$(dirname "$PC_CONFIG_FILE")/project.config.schema.json}"
     ```

     Note `PC_SCHEMA_FILE` (line 42 today) hardcodes `$_pc_root/…` — it **must** follow the resolved config, not the script's own root, or the no-deps required-key gate at lines 52-61 validates the layer's config against the host's schema (or silently skips via the `FileNotFoundError` pass).
   - **1b — the root exports.** `PROJECT_ROOT` derives from the resolved config's directory, which yields the superproject root inside a submodule and the layer root standalone. `AGENT_LAYER_ROOT` **cannot** simply be `$_pc_layer_root`: the script is dual-homed (row 1d), so post-flip it also exists at `$PROJECT_ROOT/scripts/dev/` host-side, where `$_pc_layer_root` is the *host* root — and every `$AGENT_LAYER_ROOT/agents/…` path would then silently point at the directory the flip just deleted. It is resolved by **content probe** instead, and the result is absolutised against `PROJECT_ROOT` (never `$PWD`) before export. Order matters: `PROJECT_ROOT` is computed first because both the probe and the absolutisation anchor on it:

     ```sh
     PROJECT_ROOT="${PROJECT_ROOT:-$(dirname "$PC_CONFIG_FILE")}"
     if [ -z "${AGENT_LAYER_ROOT:-}" ]; then
       if [ -d "$_pc_layer_root/agents/scripts/core" ]; then
         AGENT_LAYER_ROOT="$_pc_layer_root"             # running from inside the layer
       elif [ -d "$PROJECT_ROOT/agent-layer/agents/scripts/core" ]; then
         AGENT_LAYER_ROOT="$PROJECT_ROOT/agent-layer"   # host: layer is the mounted submodule
       else
         AGENT_LAYER_ROOT="$_pc_layer_root"             # pre-flip / submodule not initialised
       fi
     fi
     case "${AGENT_LAYER_ROOT//\\//}" in                          # match a \ -> / normalised copy
       /*|[A-Za-z]:/*) ;;                                        # already absolute (POSIX or drive-rooted)
       [A-Za-z]:*) echo "project-config: drive-relative AGENT_LAYER_ROOT '$AGENT_LAYER_ROOT' is ambiguous" >&2; return 1 ;;
       *) AGENT_LAYER_ROOT="$PROJECT_ROOT/$AGENT_LAYER_ROOT" ;;  # relative: anchor on PROJECT_ROOT, never $PWD
     esac
     PC_AGENT_LAYER_ROOT="$AGENT_LAYER_ROOT"; PC_PROJECT_ROOT="$PROJECT_ROOT"
     export AGENT_LAYER_ROOT PROJECT_ROOT PC_AGENT_LAYER_ROOT PC_PROJECT_ROOT
     ```

     Both still honour a caller-set value, so standalone layer CI can force `PROJECT_ROOT=$AGENT_LAYER_ROOT` and the row-12 flip can force `AGENT_LAYER_ROOT=agent-layer` without touching the resolution logic — and because the `case` normalisation runs *after* the probe, that bare relative `agent-layer` is exported as `$PROJECT_ROOT/agent-layer`, so a consumer that `cd`s before dereferencing it still resolves. The `case` matches on a backslash-normalised copy (`${AGENT_LAYER_ROOT//\\//}`) rather than on a bracket expression containing a backslash, which `sh` glob patterns read ambiguously; MSYS `/c/…` matches the first arm and Windows `C:/…` (or `C:\…`, post-normalisation) the second. The absolute arm is `[A-Za-z]:/*`, **not** `[A-Za-z]:*`: a Windows *drive-relative* path such as `C:agent-layer` means "the current directory on drive C", is not absolute, and is not `$PROJECT_ROOT`-anchorable either — classifying it as absolute would reintroduce exactly the cwd dependence this normalisation exists to remove, so it gets its own arm that hard-errors. The same three-arm shape applies to the rung-1 `SMATCHET_PROJECT_CONFIG` check above, which rejects **any** relative value outright so `PROJECT_ROOT` can never become caller-cwd dependent; rung 0 (`PC_CONFIG_FILE`) deliberately keeps accepting a relative value for back-compat with the bats fixtures that already inject it, canonicalising it against `$PWD` at the point of use. **Fixture hazard, must be enumerated before this lands**: deriving `PROJECT_ROOT` from `dirname "$PC_CONFIG_FILE"` means any caller injecting `PC_CONFIG_FILE` — rung 0, which is exactly what the bats fixtures do — silently re-points `PROJECT_ROOT` at that fixture's temp dir instead of the repo. Enumerate every injector first (`grep -rln 'PC_CONFIG_FILE' tests/bats/`) and, per suite, either set `PROJECT_ROOT` explicitly in the fixture or assert the temp-dir value is what the suite actually wants. A suite that silently gains a temp-dir `PROJECT_ROOT` is the failure mode this sub-row exists to catch.
   - **1c — bare-name collision, checked.** `PROJECT_ROOT` is already used as a *local* variable in three unrelated Unreal-plugin scripts (`scripts/dev/local/package-unreal-plugin-msvc.sh`, `scripts/dev/local/build-and-deploy-unreal-plugin.sh`, `scripts/publish/install-unreal-plugin.sh`, where it means "the Unreal project to deploy into", fed by `SMATCHET_UNREAL_PROJECT_ROOT`). Verified safe: none of the three sources `project-config.sh` and each assigns the variable before first use, so the export cannot leak in. The `PC_PROJECT_ROOT` twin exists precisely so scripts that dislike the bare name have a namespaced alias. Add a one-line comment at the export site naming this collision so a future reader does not "fix" it.
   - **1d — dual-homing is deliberate, not an oversight.** This file ships in **both** repos after Phase B (the layer needs it to bootstrap standalone; the host needs it before the submodule is initialised). The single-source rule for the fork and its drift check are Phase B/C's obligation — row 1 only guarantees the logic is *location-independent* (no path in the sketch above assumes which repo it is running from), which is what makes a byte-identical copy safe in the first place.
   - **Acceptance**: row 1b must also append the four new vars to the `_pc_exports` string — the direct-execution branch emits **only** `printf '%s
' "$_pc_exports"`, so a bare `export` statement in the file produces no stdout and any acceptance grepping the direct run is untestable until `_pc_exports` carries them.
