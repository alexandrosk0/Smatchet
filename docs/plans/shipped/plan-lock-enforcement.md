## Context

The plan-lock system (git-ref CAS locks under `refs/locks/*`, design `docs/plans/shipped/git-ref-plan-locks.md`) is **healthy but dormant**: a 9/9 primitive self-test passes, all three render/staleness/cleanup workflows are green, but the last 20 PRs (#1378–#1401) were solo/sequential single-subsystem work that never filed a claim, and the render mirror `docs/plans/active/_plan-locks.generated.md` has shown "No active plan-locks" unchanged since 2026-05-31 (`d7bc9e7f`). Filing a lock is currently **advisory** — nothing forces an agent to claim a write set before editing files, so two parallel agents editing the same files silently race; the only protection is each agent voluntarily running the pre-flight overlap check documented in `_plan-locks-archive.md`.

This plan makes lock-filing **enforced, but only when it matters**: a write set must be claimed before edits **iff another session is concurrently live** (force-on-contention). Solo/sequential work — the common case — is never *blocked*, and pays at most one cross-edit-cached liveness probe (the sibling-count is cached ~15 s, § Approach), not a per-edit `tasklist`. Enforcement is defense-in-depth across three layers so no single harness or bypass defeats it: (A) a Claude Code `PreToolUse` hook at edit time, (B) a harness-agnostic `pre-push` git hook, (C) a server-side CI merge-gate that is unbypassable except via an explicit out-of-band label.

After this lands, X is true: **when ≥2 sessions are live and an agent edits a file outside any lock it holds, the edit (A) / push (B) / merge (C) is blocked with a copy-paste `lock-claim.sh` remediation line, while solo work is never gated.** Originating thread: session investigation of "are the _plan-locks working?" → "how can we force all agents to file a plan lock before changing any files?" (design forks locked: Scope = force-on-contention; Layers = all three A+B+C).

## Approach

Layer A's trigger is a **repo-global** live-agent count, not a per-tree one. The hook enumerates `git worktree list --porcelain` and, for **every** worktree registry (the integration tree is itself a worktree in that list), runs `sr_entry_is_live(entry, now)` over each entry, accumulating the **live basenames** (= `session_id`s) into a **union set** — then drops own and counts **distinct**, giving a **repo-global sibling count**. It does **not** sum `sr_count_live_siblings` returns: that helper yields a per-regdir *count* (`session-registry-lib.sh:154`, `printf '%s' "$live"`), which **cannot dedup** a `session_id` present in two regdirs (it would count it twice → false contention → false deny). `sr_entry_is_live` is the per-entry primitive `sr_count_live_siblings` itself calls internally, so a union-of-distinct over it costs the same number of liveness checks while staying dedupable. The reason this scan-over-**every**-regdir is required is **not** "siblings in separate worktrees can't see each other" — it is that the registry writer's regdir is **non-deterministic w.r.t. tree**: `session-tree-banner.sh:24` uses `PROJ="${CLAUDE_PROJECT_DIR:-$(pwd)}"` and `REGDIR="$PROJ/.claude/.active-sessions"` (`:51`), and `CLAUDE_PROJECT_DIR` is **unset** in the hook env — so `PROJ` falls back to `$(pwd)`, landing the entry wherever the SessionStart hook's cwd resolved. **Verified substrate (2026-06-19 fleet snapshot):** 15 live/legacy entries all pool in the integration tree's `C:/Dev/Smatchet/.claude/.active-sessions` (all stamped `branch=feat/tsan-subset-sync-layer`, the integration HEAD — *including this session's own entry, though it runs in the `bugbot-merge-gate` worktree*), while ~90 worktree-local regdirs sit empty — **one** outlier (`C:/Dev/trees/keybindings-menu-shortcuts`, 2 entries) proves worktree-local registration *does* occasionally happen. So entries land **mostly central, sometimes worktree-local**; summing over every regdir is the only count robust to where they actually fall. Own-self exclusion is one global drop of own `session_id` from the union set (cleaner than `sr_count_live_siblings`'s per-regdir exclude-and-no-op-elsewhere), correct regardless of which registry holds own entry. **Dedup across regdirs by `session_id` is intrinsic to the union**: a resumed session that re-runs SessionStart under a changed cwd can leave two entries under one sid in two regdirs — the set unions them to **one** distinct basename, so an accidental double-entry can't manufacture a false-contention deny (a plain sum-of-counts would; that is exactly why Layer A scans entries via `sr_entry_is_live` rather than summing `sr_count_live_siblings`). The trigger is **≥2 agents live ≡ ≥1 sibling**, not write-set overlap — overlap is circular (you can't compute it until everyone has already filed a lock, which is the behaviour being forced). When the sibling count is **0** (solo) the hook `exit 0`s (no tax on solo work). When **≥1 sibling** it requires the edit's target path be covered by a `refs/locks/*` claim whose `branch` matches this worktree's current HEAD branch (i.e. *this* session's own seed lock — `owner`/`AGENT_ID` is **not** the discriminator; see the identity note below), else emits `permissionDecision: "deny"` with a copy-paste `lock-claim.sh` line. The lock-table read is `locks-show.sh`-backed (`git fetch +refs/locks/*` + `cat-file`) and cached ~30 s; any network/parse/worktree-enum failure **fails open** (advisory, never wedge a session). The **sibling-count is itself cross-edit-cached** (~15 s TTL, separate temp-file key from the lock table) — because each PreToolUse runs in a fresh bash process, the per-process `tasklist` memo (`session-registry-lib.sh:61-90`) does not survive across edits, so without this cache every edit would re-pay a `git worktree list --porcelain` + (if any authoritative-pid entry exists) a `tasklist`, *even when solo* — the verified 2026-06-19 pile-up of 15 central entries means counting siblings is never free. The count cache is keyed on the **registry** substrate (`.active-sessions`), so a `refs/locks/*` change does **not** bust it (wrong substrate — the count is who's-alive, not what's-claimed); invalidation is **TTL-only**. Staleness under-reports a *newly-live* sibling for ≤ TTL → a few un-gated edits slip, accepted: Layer A is advisory and B (every push) / C (every PR push) are the authoritative net. The guard derives its own `session_id` (for the self-exclusion) from the PreToolUse stdin `.session_id` field, **never** `sr_session_pid` — that spawns a ~300–500 ms powershell CIM ancestor-walk (`session-registry-lib.sh:98-115`) the guard's hot path must not pay.

The three layers are deliberately asymmetric in their fail-mode. A and B are **advisory / fail-open** local hooks (catch the mistake early, cheaply, but never hard-wedge a flaky-network session) — A at edit time inside Claude Code, B at `git push` time for any harness (the catch-all for non-Claude-Code agents, wired via `core.hooksPath`). C is the **fail-closed hard net**: a GitHub Actions check (named `Plan-lock gate`) that recomputes contention server-side (overlap between this PR's changed files and any **other-branch `refs/locks/*` write set** — the declared-write-set basis **only**, NOT raw other-open-PR changed-file sets; non-circular, since it does not require THIS PR to have filed a lock) and reds — blocking merge. Its blocking power comes from the **meant-to-block allow-list** (`MERGE_GATES_BLOCK_ALLOWLIST_RE`, `merge-gates.sh:132`), NOT a new branch-protection required check — the #923 mechanism: a non-required check whose name is on the allow-list blocks merge with zero out-of-repo branch-protection mutation. Unbypassable except the `plan-lock-out-of-band` label that downgrades the `Plan-lock gate` RED → WARN via the poller's jq-filter CI-downgrade path (`ci_warn_downgraded`), identical to `tests-out-of-band` → `Test-delta gate` / `perf-out-of-band` → `Perf PR-fast` (NOT the bespoke gate-scoped `cr-out-of-band` path). This is the same advisory-pair-plus-hard-net shape the tree-guards already use (`guard-shared-tree.sh` advisory + `guard-head-drift.sh` hard net).

**Identity: all three layers key on `branch`, never `owner` / `AGENT_ID`.** `AGENT_ID` is **unprovisioned in every production session** — `lock-claim.sh:84` / `lock-claim-update.sh:99` default `${AGENT_ID:-orchestrator}`, and only the test suite (`test-lock-primitives.sh`) ever sets it. So every real lock is `owner=orchestrator`, and a guard reading `AGENT_ID` also gets `orchestrator`: an **owner-keyed check is a no-op** — two parallel sessions both read `owner==orchestrator`, each sees the other's lock as "mine," and the collision the layer exists to catch slips straight through. The reliable, always-derivable discriminator is **`branch`**: Layer A allows an edit iff the path is covered by a lock whose `branch` == this worktree's HEAD branch (my own seed); Layer B refuses a push overlapping a lock from a different branch; Layer C blocks a PR whose `github.head_ref` ≠ an overlapping lock's `branch`. `owner` stays in `claim.json` as advisory metadata (audit + `locks-show.sh` display), **not a gate**. Re-introducing owner-keying anywhere silently restores the pass-through bug — the Layer A bats carries an owner-collision canary (two `owner=orchestrator` locks on different branches must still deny). **Same-tree-same-branch contention** (two sessions sharing one integration tree on the same branch) is **out of plan-lock scope** — the tree guards (`guard-shared-tree.sh` / `guard-head-drift.sh`) own that hazard; plan-locks target cross-*branch* parallel work.

**Lock seeding (adoption).** A lock must already exist when a *second* agent's first edit hits the guard — so seeding is **eager and decoupled from enforcement**: the ship-loop files a claim from the plan-doc's **§Files-to-modify** list at task start whenever a plan exists, reusing the declared write set verbatim (no separate discovery step). Eager seeding closes the race where agent A starts solo, files nothing, then agent B goes live and A is now contended with no lock filed — by always seeding from the plan, A's claim is present as the early-warning substrate the moment B arrives. *Seeding* is eager (file whenever a plan exists); *enforcement* (the deny) stays force-on-contention (≥2 live) — the two are independent. Plan-less tasks (small fixes, no plan-doc) have no auto-seed: they file on the first deny via the `lock-claim.sh` one-liner the guard hands them, and force-on-contention makes plan-less-AND-contended rare. `lock-claim-update.sh` expands the seeded set on mid-work discovery. **Seeding is idempotent, with branch-aware exit-1**: a resumed / re-entered session re-runs the seed and `lock-claim.sh` exits 1 (lock already held); the seed reads the held lock's `branch` to classify — **own HEAD branch → benign** (re-seed, goal already met), **different branch → WARN** (cross-branch slug collision Layer C will block; surface the breadcrumb, don't swallow it). Never an error path either way (non-blocking); the git-ref CAS is the atomic race-resolver, so there is no check-then-claim guard above it (TOCTOU). Mechanics (mktemp write-set FILE, `LOCK_PLAN`, default-`LOCK_BRANCH`-from-in-worktree-HEAD, branch-aware exit-1) live in item 8.

**Coverage match (how an edited path matches a `write_set`).** `write_set` is a raw repo-relative path list (`_lock-json.py:48-55` — no normalization, no globbing applied at claim time). An edited path is **covered** iff, after normalizing both sides to repo-relative forward-slash, it string-equals a `write_set` entry **or** sits under an entry that ends in `/` (directory prefix). **No glob engine** — plain equality + dir-prefix is **one bash implementation shared by all three layers** (the `lock-table-cache.sh` coverage primitive, item 3, reused verbatim by A/B *and* the Layer C decision `.sh`), so it is byte-identical **by construction — same code, same language**, not by a fragile cross-language conformance test. `_lock-json.py` is the **shared JSON parser** all three shell out to (`format-json` → the `write_set` list); it does **not** itself do coverage-match. Keeping all three in bash removes the `fnmatch` / shell-glob divergence a bash-vs-Python split would carry (a layer passing locally while C blocks). The cross-platform normalize (`\`→`/`) is the *same* bash — a no-op on the ubuntu CI runner (Layer C), active on Windows git-bash (A/B) — correct on both. The seed extracts clean entries from the plan's **§Files-to-modify** by a defined rule (§Files-to-modify item 8): the **first** backtick-delimited token on each numbered (`N.`) line, with the trailing `:line-range`, ` (new)`, and ` — description` stripped — the orchestrator applies it **inline** when seeding (it is already reading the plan; no markdown-parsing script). The "first token" rule is what skips the **cross-reference paths** that appear later in an item's prose (item 1 cites `guard-shared-tree.sh:77-86` as a "mirror this helper" ref, not a write target): the plan-doc convention is that each numbered item **leads** with the file it modifies, so the lead token is the write target and the rest are refs. Bold `**…**` sub-headers are non-numbered → skipped. Extraction imperfection is safe by construction: an over-include is a harmless reservation, a miss self-heals via deny→file (§ Lock seeding). Plan authors write a bare path or a dir-prefix entry (the strict-zone case, e.g. `Source/Core/src/Sync/`, is one dir entry). Mid-work growth re-files the **full** grown set via `lock-claim-update.sh <slug> <write-set-file>` — the git-ref backend *replaces* `write_set` from the file (`lock-claim-update.sh:124-129`), it does **not** append, so the deny one-liner hands a full-set path, never a single filename.

The non-obvious trade-off that shaped the design: **filing a claim must never itself be blocked.** `lock-claim.sh` builds its orphan commit via `git hash-object` / `git mktree` / `git commit-tree` and pushes a ref — it writes **zero** working-tree files — so the edit-time guard can never create a chicken-and-egg deadlock where you can't claim because claiming requires an edit. Mid-work write-set discovery (an agent realises it must touch a file it didn't list) is handled by `lock-claim-update.sh` (holder-only scope expansion); the guard's deny message hands the agent the exact one-liner.

**Layer B — harness-agnostic pre-push hard-stop (advisory, fail-open):**
4. `scripts/git-hooks/pre-push` — add a third independent stop `(C) UNLOCKED-CONTENDED-PUSH`. **Insert it after the `(A)` direct-push block (`:84`) and BEFORE the `branch=` / `(B)` block (`:86`)** — **not** after `(B)`: `(B)` `exit 0`s for the normal feature-branch-with-open-PR case (`:97-98`), so a `(C)` placed after it is dead code for exactly the contended-feature-branch push it must guard. **Layer C — server-side CI merge-gate (fail-closed hard net):**
5. `.github/workflows/plan-lock-gate.yml` (new) — emits **`Plan-lock gate`** as a **job-name CheckRun** (workflow job `name: Plan-lock gate`, exit-code-driven: the sourceable decision `*.sh` returns non-zero on contention → the job conclusion is FAILURE → a `CheckRun{name:"Plan-lock gate"}` node). **It MUST be a CheckRun, not a StatusContext.** The poller blocks on *both* node types (the rollup normalizes `if .__typename=="CheckRun" then .name else .context`, `merge-gates.sh:392`,`:425`), but the CI-downgrade `$downgraded` filter **hard-codes `.__typename == "CheckRun"`** (`:429-430`) — so a `Plan-lock gate` posted as a StatusContext (a `statuses: write` API call, the `cr-finding-gate.yml` mechanism) would still *block* yet its `plan-lock-out-of-band` override would **silently never match** → a dead, un-downgradable gate. A native Actions job conclusion *is* a CheckRun by construction, so driving the job red via the script's exit code yields the correct node type for free — no `statuses: write` permission, no API post. Trigger `on: pull_request: [develop]` (opened/synchronize/reopened → the changed-file set + lock table re-evaluate on every push). **Changed-file compute uses the repo's canonical delta-gate idiom — three-dot `git diff --name-only origin/${{ github.base_ref }}...HEAD` with `fetch-depth: 0` + an explicit `git fetch --no-tags origin "${{ github.base_ref }}"` (template = `perf-pr-fast.yml:79-83` / `coverage.yml:96`, NOT cr-finding-gate.yml, which is CR-comment-driven and computes no changed files).** Three-dot `origin/develop...HEAD` diffs from the merge-base, so it is **byte-equivalent to Layer B's `$(git merge-base origin/develop HEAD)..HEAD`** — adopting it gives the A/B/C coverage symmetry the 3-layer design rests on *for free* (a path B blocks, C blocks; no skew). **`fetch-depth: 0` is mandatory and load-bearing**: a shallow checkout breaks merge-base → an **empty** changed set → the fail-closed hard net silently blocks nothing (a *dead net*, the Q12 failure class — the 2026-06-14 pillar2 `--depth=1` incident broke base-ref fetch across 5 workflows, the cautionary precedent). **If `origin/develop` will not resolve, the job reds itself** (`::error` + `exit 1`, the high-integrity precedent at `build-and-test.yml:308-309`) rather than `|| true`-ing to an empty set — a hard net that can't compute its input must fail **loud**, not silently green; `plan-lock-out-of-band` is the escape valve if a transient infra blip wedges a legit PR. cr-finding-gate.yml is cited **only** as the StatusContext-posting mechanism to **avoid** (Q12), not as a structure to borrow. **TOCTOU residual**: a lock filed by a sibling *after* this gate's last run on PR-X won't red PR-X until PR-X's next push-trigger; the window is *covered, not open* — the sibling's own PR-Y gate sees PR-X's already-filed lock and reds PR-Y (whichever filed first wins the symmetric race), and Layer B re-checks at every push. A scheduled re-run is therefore unnecessary; documented as accepted residual, not mitigated with extra machinery. NOT a branch-protection required check — its blocking power is registered in item 6 via the allow-list. Computes this PR's changed files; enumerates `refs/locks/*` claims (the authoritative global write sets on origin); reds (non-zero) when this PR's changed files overlap a claim's `write_set` owned by a different `branch` (**derived as `github.head_ref` ≠ the lock's `branch` field** — the only identity available in Actions, since CI has no agent `AGENT_ID`; a lock whose `branch` == this PR's head is **self** and never blocks, and a lock with an empty / missing `branch` is **unattributable → non-blocking**, freed by the stale sweep). **Comparison basis is the declared `refs/locks` write_set ONLY — not raw other-open-PR changed-file overlap** (that re-introduces the file-overlap-as-trigger coupling Q1 removed and false-trips every adjacent / stacked PR; lock-less agents are driven to file via Layers A/B, not caught by a noisy second C trigger). Non-circular: does not require THIS PR to have filed a lock. Honours stale locks as non-blocking (older than `lock-staleness.yml`'s `THRESHOLD_DAYS=14`). The checkout step must fetch the lock refs explicitly (`git fetch origin '+refs/locks/*:refs/locks/*'` — `actions/checkout` does not pull custom refs by default). Decision logic lives in a sourceable **bash** `*.sh` (testable headless, see § Verification), not inline YAML and **not Python** — it sources the same `lock-table-cache.sh` coverage primitive as Layers A/B (byte-identical-by-construction, § Approach coverage-match) and shells out to `_lock-json.py` for the JSON parse, exactly as A/B do; the only Python in any layer is that shared parser. Bash is on the ubuntu runner and is the repo's gate-script convention (`merge-gates.sh` et al. are bash sourced in CI). **Includes an idempotent `Ensure plan-lock-out-of-band label exists` step** (existence-check via `gh label list … | grep -qx`, then `gh label create plan-lock-out-of-band`, `secrets.GITHUB_TOKEN`) — verbatim shape of `lock-staleness.yml:59-71`'s `plan-lock-stale` step (`gh label create` errors on duplicate, hence the guard). ## Risks / non-goals

**Risks:**
- **Per-edit cost (Layer A) — network AND local-probe.** *Network*: each edit under contention would otherwise `git ls-remote refs/locks/*` — mitigated by the ~30 s lock-table cache. *Local probe*: the sibling-count is **not** free either — each PreToolUse is a fresh bash process, so the per-process `tasklist` memo (`session-registry-lib.sh:61-90`) does not carry across edits, and counting siblings re-pays a `git worktree list --porcelain` + (whenever any authoritative-pid entry exists — the verified 2026-06-19 snapshot has 15) one `tasklist`, **even when solo**. So "solo pays zero tax" is true only for *blocking*, not compute. Mitigation: the ~15 s count-cache (item 3) collapses a multi-edit slice to one probe per TTL window; a stale count **fails open** toward under-reporting contention (Layer A quiets, B/C are the net), identical bias-to-allow to `guard-shared-tree.sh`'s missing-lib fall-open (`:70`). The expensive `sr_session_pid` powershell ancestor-walk (`:98-115`) is **never** on the guard's path — `own_sid` comes from the PreToolUse `.session_id`. **Second-hook-always-runs**: plan-lock is the 2nd PreToolUse hook on the edit matcher (alongside `guard-head-drift.sh`); both **always run** (deny wins, array order cosmetic) — so plan-lock pays its probe even on an edit head-drift would deny, and the solo `exit 0` (siblings==0) is the *only* thing bounding the common case, never a head-drift short-circuit. A 3000 ms timeout (verbatim head-drift) that a slow contended lock-read blows returns **no deny → tool proceeds = fail-open** (a feature: same bias-to-allow as every other Layer A failure; B/C are the net).
- **Mid-work file discovery friction.** An agent that discovers it must touch an unlisted file is blocked on the first edit. Mitigation/intent: this friction is the point (it forces write-set honesty); the deny message hands the exact `lock-claim-update.sh <slug> <write-set-file>` one-liner (holder-only, one round-trip) — the file must hold the **full grown set**, because the git-ref backend *replaces* `write_set` from it (`lock-claim-update.sh:124-129`), not just the newly-discovered path. Accepted; an opt-in `SMATCHET_PLAN_LOCK_AUTOEXPAND=1` fast-path that auto-expands the holder's own lock is documented but **off by default** (auditability over convenience).
- **Override-env footgun (the exact bug this design must not repeat).** An inline `SMATCHET_REQUIRE_PLAN_LOCK=0 <edit>` prefix does **not** reach a PreToolUse hook — the hook reads its own env before the tool runs. Mitigation: the deny message copies `guard-shared-tree.sh:150`'s wording verbatim — "export … in the session env BEFORE launch." Accepted (inherent to the hook model).
- **False-block on solo work.** Mitigation: force-on-contention — repo-global sibling count 0 (no *other* live agent) → `exit 0`. Zero tax on the common case. (Threshold is ≥1 sibling, not ≥2 — the "excluding self" off-by-one trap.) **OBSERVED substrate dependency (not hypothetical — verified 2026-06-19):** worktree sessions do **not** reliably self-register in their own tree's `.claude/.active-sessions`; the entry lands wherever the SessionStart hook's `$(pwd)` resolved because `CLAUDE_PROJECT_DIR` is unset (`session-tree-banner.sh:24`,`:51`). Empirically all live entries pool in the integration tree's regdir (one worktree-local outlier). This is exactly why Layer A **scans every regdir** (`git worktree list` enumeration, unioning distinct live `session_id`s via `sr_entry_is_live`, see § Approach) instead of reading one — the union-of-distinct is robust to the non-deterministic landing site, so it does **not** under-report (and dedups a double-registered sid rather than double-counting it). The residual failure is only if a live session registered in **no** discoverable regdir at all (none observed); Layers B/C (origin `refs/locks/*`) remain the backstop, so Layer A is never the sole net. (Root-cause fix — a canonical pwd-independent regdir — is deferred, see Out of scope.)
- **Fail-open layers could let a contended edit through.** Accepted by design: A/B are advisory (catch-early, never wedge); **Layer C is the fail-closed hard net** (server-side required check, unbypassable except the explicit `plan-lock-out-of-band` label). Defense-in-depth, same shape as `guard-shared-tree.sh` (advisory) + `guard-head-drift.sh` (hard net).
- **Stale lock wedging contention detection.** A claim from an abandoned session could falsely block. Mitigation: Layer C treats a lock older than `lock-staleness.yml`'s `THRESHOLD_DAYS=14` as non-blocking. **Note the daily staleness sweep does NOT auto-delete** — it only opens/updates a GitHub Issue (`lock-staleness.yml` header) — so the 14-day non-blocking cutoff in the gate logic, not the sweep, is what prevents an aged orphan from wedging; actual ref removal is `lock-cleanup.yml` (PR close) + the orphan-release wiring below.
- **Orphan lock → Layer-B/C false-block (the release-loop this plan must close).** Eager seeding (item 8) files a `refs/locks/<slug>` at task start, but the *only* automatic ref-removal is `lock-cleanup.yml`, which fires on PR close **and** only if the PR body carries a `lock-slug: <slug>` line it can parse (`lock-cleanup.yml` "Parse lock-slug from PR body"; no line → no-op, ref persists). Today no PR files that line (system dormant), so absent new wiring every seeded PR would **orphan its lock on merge** and Layers B/C would false-block every later PR overlapping that `write_set` until manual delete (staleness never deletes — Issue-only). Mitigation (item 8 + item 11): (1) the ship-loop's open-PR step writes `lock-slug: <slug>` into the PR body whenever a lock was seeded, so a merged PR releases promptly on the same squash-merge; (2) `lock-cleanup.yml` is extended to also release on **closed-unmerged** PRs, so an abandoned branch's reservation is freed too — neither merge nor abandon orphans a seeded lock. Residual: a lock seeded for a task abandoned **before any PR opens** still relies on the 14-day non-blocking cutoff + manual delete (rare; accepted).
- **Layer C dead-net via shallow checkout.** If `plan-lock-gate.yml` checks out shallow (no `fetch-depth: 0`) or the base fetch fails, `git diff origin/develop...HEAD` returns an **empty** changed set → the fail-closed hard net silently blocks nothing (the Q12 failure class; the 2026-06-14 pillar2 `--depth=1` incident is the precedent). Mitigation: `fetch-depth: 0` + explicit `git fetch --no-tags origin "$base_ref"` are mandatory, and base-resolution failure **reds the job** (`::error` + `exit 1`, `build-and-test.yml:308` precedent) rather than `|| true`-ing — a `base-unresolvable-fails-closed` bats case locks it.
- **Cross-branch slug collision (seed).** Two worktrees off one plan-doc share a slug but differ in branch; the second seed's `lock-claim.sh` exits 1 (single-occupancy CAS — only one branch holds `refs/locks/<slug>`). Risk: an unconditional "exit 1 = benign" swallow hides the collision, then Layer C blocks the second branch's PR downstream (it edits files in the first branch's `write_set`) with no local breadcrumb. Mitigation: the seed is **branch-aware** (item 8) — it reads the held lock's `branch` and **WARNs** when it ≠ my HEAD ("slug held by `<other>`; Layer C will block — pick a distinct slug or coordinate"), while still swallowing my-own-branch re-seed as benign. Non-blocking (breadcrumb, not stop); `$held` is only a SHA so the one seed-time `branch` read is necessary to classify.
- **Unattributable lock (empty / detached `branch`).** `lock-claim.sh:85` defaults `branch` to `detached` (or empty via `LOCK_BRANCH=""`) when HEAD has no symbolic ref. Layer C cannot attribute such a lock to a branch, so it treats an empty / `detached` `branch` as **non-blocking** (bias-to-allow — the hard net must not wedge on an un-attributable claim; the stale sweep ages it out). Surfaces the agent flow as the place to guarantee `LOCK_BRANCH` is set when seeding.
- **Chicken-and-egg deadlock — NOT a risk (explicit non-risk).** `lock-claim.sh` touches no working-tree file, so claiming is never itself gated by the edit guard. Cited so a reviewer doesn't re-raise it.
- **Lock-less concurrent work defeats all three layers — the backstop is not categorical (adversarial review F1, 2026-06-20).** B and C block only on overlap against an **existing** `refs/locks/*` claim (Layer C is declared-write_set-basis, non-circular). A lock exists only via eager-seed (plan-having) or a Layer-A deny→file — and the deny needs Layer A to *detect* contention, which is fail-open on five paths (stale count cache, sibling in no discoverable regdir, network/lib error, timeout, self-exclusion miss). So two **plan-less** (or same-slug CAS-loser) concurrent agents on overlapping files, with Layer A under-detecting for ≥1, file **no lock on either side** and race silently through A+B+C. The "B/C are the authoritative net" framing elsewhere overstates coverage: B/C net only *filed-or-overlapping-filed* locks, so this is a genuine **all-layer** gap for the unstructured case — not merely "a few un-gated edits B/C catch." Accepted residual (force-on-contention makes plan-less-AND-contended rare); the honest framing is a "plan-less concurrent work is out of guaranteed scope" non-goal. Decision owed before ship (§ Adversarial review F1).

**Non-goals:**
- Not *gating/blocking* solo/sequential work — enforcement (the deny) is force-on-contention only; a solo edit is never blocked. (Eager seeding still files a lock from the plan on a solo plan-task, but filing is a free, non-blocking ref push; the "no tax" guarantee is about *blocking*, not about whether a ref is pushed.) **The "no tax" guarantee is specifically about blocking — there is a small, capped *compute* cost (the cross-edit-cached sibling-count probe, ~15 s TTL; see the per-edit-cost Risk), not literally zero.**
- Not changing the lock wire format, ref layout, or backend dispatch (`SMATCHET_LOCK_BACKEND=p4-counter` still works; see Out of scope).
- Not building a lock dashboard / UI / live-contention visualiser.
- Not rewriting the frozen `_plan-locks-archive.md` advisory protocol history (it stays frozen at the 2026-05-17 cutover).
- Not covering **same-tree-same-branch** contention (two sessions on one integration tree, same branch) — the tree guards (`guard-shared-tree.sh` / `guard-head-drift.sh`) own that hazard; plan-locks key on `branch`, so a shared branch is indistinguishable to them by design. Cross-*branch* parallel work is the target.
- Not provisioning a per-session `AGENT_ID` — `owner` stays advisory-only metadata; all gating is `branch`-keyed (the unprovisioned-`AGENT_ID` finding, see § Approach identity note). Per-session granularity is unnecessary because the only case it would add (two sessions, same branch) is tree-guard scope above.
- **Plan-less concurrent work is out of guaranteed scope (F1 resolution, 2026-06-20).** When two plan-less (or same-slug CAS-loser) sessions edit overlapping files and Layer A under-detects contention (its fail-open paths), no lock is filed on either side, so B and C — which only block against an *existing* claim — have nothing to compare and all three layers pass.
