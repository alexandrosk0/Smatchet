## Context

`Source/Core/include/AppController.h` is **1410 lines** (verified `git show origin/develop` 2026-06-19; the debt entry's "~1110 / ~150-method" figure is stale) with ~228 method-ish declarations spanning ~9 concerns, owning 10+ `unique_ptr` subsystems and ~10 mutexes across nine partial-class TUs (`AppController.cpp` 2699L, `AppController_CatalogAndFieldEdit.cpp` 2063L, `AppController_LuaBindings.cpp` 1507L, `AppController_LuaBindings_Draw.cpp` 1282L, `AppController_Attachments.cpp` 400L, `AppController_Connectivity.cpp` 368L, `AppController_LuaBindingsCore.cpp` 329L, `AppController_IssueCreateOffline.cpp` 284L, `AppController_LuaStubs.cpp` 72L) plus the src-only `AppControllerImpl.h` (212L). It is the highest-coupling node in `Source/Core` — the merge-conflict + reasoning bottleneck (debt.md 2026-05-28 P2, re-verified 2026-06-19).

Decomposition is already underway and **principled**: `OfflineQueueService` (`Source/Core/include/Sync/OfflineQueueService.h`), `TicketSyncService` (`Source/Core/include/Sync/TicketSyncService.h`), and `LuaAutomationHost` (`Source/Core/include/LuaAutomationHost.h`) were lifted out behind narrow ISP `*Deps` interfaces (`IOfflineQueueDeps.h`, `ITicketSyncDeps.h`) with one concrete adapter (`GridContextDepsAdapter`) and header-only fakes (`tests/support/FakeOfflineQueueDeps.h`, `FakeTicketSyncDeps.h`). **This plan continues that exact pattern, mirroring it for each new extraction.** Intended outcome: after this plan lands, `AppController.h` is a thin facade delegating to owned single-responsibility services, each independently unit-tested behind a `*Deps` interface, with no behaviour change.

Originating debt: `docs/self-improvement/categories/debt.md` 2026-05-28 P2 (`AppController` god-object) + the 2026-05-28 P3 follow-up (queue/dead-letter struct relocation, partly shipped) + the `ilocalcache-seam` sub-task (transitive SQLite-purity route).

## Approach

**Mirror the proven 3-service template, one concern per phase, each a standalone shippable PR.** The template (verified against all three existing extractions) is: (1) a narrow `I<Name>Deps` interface at `Source/Core/include/` exposing only the AppController-side state the service reaches into; (2) a `<Name>Service` class in `Source/Core/include/Sync/` (or a concern-appropriate sub-dir) owning its own state + mutex, constructed eagerly in `Initialize` as a `unique_ptr` member, taking `I<Name>Deps&` at construction; (3) `GridContextDepsAdapter` (or a new sibling adapter) implements the new interface by forwarding to AppController/`GridLiveContext`; (4) AppController's public methods become thin delegators preserving the exact signature; (5) a header-only `tests/support/Fake<Name>Deps.h` + a `tests/Core/<Name>Service.test.cpp` doctest unit linked into both `SmatchetTsanTests` (light, no-ImGui) and `SmatchetTests`.

**Behaviour-preservation is the hard contract.** Each phase is a pure refactor — when state moves into a service, **its mutex and every invariant move with it as a unit** (never split a lock from the data it guards). The trade-off that shaped phase ordering: the lowest-risk, most self-contained clusters go first (host callbacks, then editmeta cache) to bank the pattern and shrink the header before touching the cross-coupled connectivity FSM and the struct relocations that unlock SQLite-purity.

**Two key corrections to the debt entry's starting hypotheses, verified in code** (both reshape the plan vs the debt entry's text):
- The **field-catalog state is already de-singletoned** — `AvailableFields` / `AvailableComponents` / `AvailableUsers` / catalog error+warning / `currentCatalogProjectKey_` / `projectComponentOptions_` and `availableFieldsMutex_` all live in `GridContextFieldCatalog` inside `GridLiveContext` (per AppController.h:1118-1127; accessed via the `fieldCatalog()` focused-context delegator), **not on AppController**. So debt hypothesis (b) "field-edit/editmeta-cache cluster" splits: the field-catalog half is already extracted; only the **editmeta cache** (`editMetaMutex_` + `issueEditMeta_` + `issueTypeEditMeta_` + `issueEditMetaWarmupInFlight_`, AppController.h:1213-1216) plus the **field-edit network pipeline** (`SubmitFieldEdit*` family) remain on AppController.
- The queue/dead-letter result structs the debt entry's sub-task wanted relocated are **already in `Sync/OfflineQueueTypes.h`** (AppController.h:91-94 includes it; AppController re-exports via `using`-aliases at :739-790). The residual SQLite-purity conduit is therefore narrower than the debt entry states — see Phase 5.

## Threading / mutex-safety analysis

The class owns ~10 mutexes; the invariant per phase is **the mutex moves with the state it guards, never split**.

- **Phase 0 (HostCallbacks)**: no mutex. The 7 `std::function` members are written once at host setup (UI thread, pre-worker) and read on the UI thread — same "publish-once" discipline as today (mirrors `uiThreadId_`, AppController.h:1388-1395). No locking added or removed.
- **Phase 1 (EditMetaCacheService)**: owns `editMetaMutex_` (AppController.h:1213) guarding `issueEditMeta_` / `issueTypeEditMeta_` / `issueEditMetaWarmupInFlight_`. **All four move together into the service.** Verified the mutex guards exactly these three containers and nothing else (`AppController_CatalogAndFieldEdit.cpp:626,861,905`). The warm worker's **per-project-component write targets `GridContextFieldCatalog::projectComponentOptions_` under `availableFieldsMutex_`** (a *different* mutex, in `GridLiveContext`) — that write stays adapter-forwarded under the catalog's own lock with the **kick-time context-pointer capture (#975)** preserved exactly (`AppController_CatalogAndFieldEdit.cpp:656-660,783-825`). Two mutexes, two owners, no split. UI-thread reads of `CanEditFieldForIssue` take `editMetaMutex_`; service preserves.
- **Phase 2 (FieldEditPipelineService)**: holds no long-lived mutex of its own — `SubmitFieldEdit*` is call-frame-scoped (the `SubmitFieldEditCtx` holds references bounded to the call frame, AppController.h:1261-1273). It *consumes* Phase 1's `editMetaMutex_` (via the EditMetaCacheService deps) and the offline-queue's lock (via `QueueFieldEditOffline` delegation). No new lock; cross-service calls go through interface methods, not shared raw state.
- **Phase 3 (ConnectivityMonitorService)** — the delicate one. The probe state (`trackerConnectivityProbeInFlight_`, `trackerConnectivityProbeFuture_`, `nextTrackerConnectivityProbeAt_`, `lastTrackerConnectivityState_`, the recovery latch) is **UI-thread-only by contract** (driven from the per-frame `TickTrackerConnectivityMonitor`) — no mutex today, none added; the `std::future` is the only cross-thread handle and it stays owned by the single UI-thread FSM. The two `std::atomic<bool>` latches (`fieldCatalogRefetchAfterLiveTicketSyncPending_`, `deferredLiveTrackerBackendSuccessNotify_`, AppController.h:1317-1318) move as atomics (read by UI consumers any frame). `LastTrackerTicketSyncWarning` (plain `std::string`, AppController.h:1128) is written both here AND by TicketSyncService via the adapter (`ITicketSyncDeps::SetLastTrackerTicketSyncWarning`) — **both writers verified UI-thread** (writer 1: `ApplyTrackerConnectivityProbeResult` `AppController_Connectivity.cpp:114` ← `TickTrackerConnectivityMonitor` ← `SmatchetUI.cpp:613`; writer 2: `TicketSyncService.cpp:51,59,68,373,386` ← `TickStreamingApply` ← `AppController.cpp:724 TickAllContexts` — both per-frame UI tick), so moving the string into ConnectivityMonitorService keeps a single logical owner, and the adapter's `SetLastTrackerTicketSyncWarning` override re-points to the service. **CORRECTION (triple-check #1): the catalog-warning reads/writes stay UNLOCKED via adapter forwarding, preserving the current UI-thread-only single-kick-time-`cat`-latch discipline (`AppController_Connectivity.cpp:197,285`) — do NOT add `availableFieldsMutex_` acquisition on the connectivity path (it would create a new lock-ordering edge vs the warm worker which already holds that lock at `:727`).** **CORRECTION (triple-check #2/#3): there is no "construct before `ticketSync_`" invariant** — `ticketSync_` is per-context (N instances at `AppController.cpp:468`+`:1742`), connectivity is global. Correct invariant: the global `ConnectivityMonitorService` is constructed eagerly in `Initialize` before the first frame tick; all N per-pane adapters' `SetLastTracker*` overrides forward into that one constructed service (the override is a runtime call, not a construction-time write, so the only requirement is "service exists before any tick").
