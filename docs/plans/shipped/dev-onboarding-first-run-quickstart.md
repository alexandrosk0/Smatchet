## Context

Three onboarding gaps surfaced from a fresh Windows clone/build session plus a UX walkthrough of first launch:

1. **Build friction.** [`docs/plans/msvc-build-onboarding-hardening.md`](../shipped/msvc-build-onboarding-hardening.md) § Approach promised that `build_standalone.ps1` would "bootstrap the Visual Studio compiler environment automatically for `*-msvc` presets", and its § Deviations from plan (:85) closed that row by asserting *"`build_standalone.ps1` (plan file 1) already had the MSVC bootstrap from slice 1."* **That is false in the tree**: [`scripts/dev/local/build_standalone.ps1`](../../../scripts/dev/local/build_standalone.ps1) contains zero `vcvars` import — its only `vswhere` use is `Get-VsWherePath` (:71-83) locating MSBuild for the VS-generator branch, and `git log -S vcvars` on that path is empty across all history. What the file *did* have was `Use-Msys2Ucrt64Environment` — an **MSYS2** env setup, now dead code (defined :105-170, no caller in the committed tree). So the concrete fresh-clone break is a **configure-time `CMAKE_CXX_COMPILER`/`cl.exe` not found** for `ninja-*-msvc` outside a VS Developer Prompt — *not* a wrong-preset problem (`ninja-debug-msvc` is already the default). The real vcvars import exists and is production-grade in [`scripts/dev/with-msvc.ps1`](../../../scripts/dev/with-msvc.ps1); nothing needs writing, only wiring. That gate escape is now RCA'd — [`postmortems.md`](../../self-improvement/postmortems.md) 2026-08-03 · PR #495.
2. **First-run product gap** — *materially narrowed while this plan was in review; re-scoped 2026-08-03 against `develop`.* Fresh installs already open Preferences and default to read-only ([`ConfigManager_Load.cpp:718-723`](../../../Source/Core/src/Config/ConfigManager_Load.cpp:718) sets `ReadOnlyMode = true` + `ShowPreferencesWindow = true` when no config file existed), so the user does land on the Preferences window. **PR #1833 ("UX pass 2", `d8446877`) then shipped the candidate-credential probe this plan had scoped as its one genuinely-new mechanism**: `AppController::ProbeTrackerCredentials` ([`AppController.cpp:140-156`](../../../Source/Core/src/AppController.cpp:140)) builds a throwaway backend from an arbitrary `TrackerConfig` and returns the verdict, and `DrawTrackerTestConnection` ([`SmatchetPreferencesUi.cpp:572`](../../../Source/Core/src/Ui/SmatchetPreferencesUi.cpp:572), called at :673) renders a Test-connection button on the Tracker tab that probes the **current buffer** credentials off-thread. So the "no Test-connection control at all" premise is **no longer true** — do not re-plan it.

   What remains is the **setup-state half**: the tab still has no completion flag, no explanation of *why* the app is read-only, and no link between a green probe and clearing `ReadOnlyMode`. A user can now verify a token before committing it, but nothing tells them they must, and Save & Sync clears read-only whether or not the probe was ever run or came back green. The background poller ([`ConnectivityMonitorService.cpp:174`](../../../Source/Core/src/ConnectivityMonitorService.cpp:174)) still probes only the **already-live** backend and remains irrelevant to first-run credential entry.
3. **Doc friction.** [`BUILD.md`](../../../BUILD.md) is complete but long. New contributors want a ≤35-line "clone → build → run → connect tracker" path at repo root.

**Intended outcome**: after all three slices land, a Windows user runs `.\build.ps1` from an ordinary PowerShell (no VS Developer Prompt), reads `QUICKSTART.md` for the five-step path, and on first launch lands on a Tracker tab that explains the read-only state, verifies credentials against the live backend **before** committing them, and clears read-only only once they are proven.

## Approach

Three PR-sized slices, one concern each, no cross-slice code coupling (slice 3 only cross-links slice 1's entry point).

**Slice 1 — root `build.ps1`, wiring the MSVC env that already exists.** *Scope settled from tree evidence, not from the shipped plan's claim* (§ Context 1): the vcvars import is **already written and production-grade** in [`with-msvc.ps1`](../../../scripts/dev/with-msvc.ps1) — vswhere enumeration with a VC.Tools component filter, `build.msvc_toolset_pin`, the x64/ARM64 batch matrix, the `cmd /c "…bat && set"` dump-and-apply, the LLVM PATH de-prioritisation, a non-zero exit on not-found (`2` at plan time; PR-1's CR follow-up moved it to a dedicated `78` — see § Deviations). Nothing needs writing; the gap is that **no entry point calls it**. So slice 1 is *wiring only*: a root `build.ps1` that resolves the repo root from `$PSScriptRoot`, auto-selects a preset, prints the chosen preset **and the reason**, and delegates to `scripts/dev/local/build_and_run.ps1` — directly when `cl.exe` is already on PATH, otherwise **through** `with-msvc.ps1` (whose `& $exe @rest` tail runs a `.ps1` in-process inside the imported env, so no second import mechanism is needed).

**Explicitly rejected: extracting a `scripts/common/SmatchetMsvcEnv.ps1` module and refactoring `with-msvc.ps1` to consume it.** With `build_standalone.ps1` having *no* import to de-duplicate, extraction removes zero duplication and buys only risk — silently dropping the LLVM PATH ordering or the not-`-latest` install-selection loop is exactly the #495 failure class this plan just RCA'd (§ Out of scope). Revisit only if a second independent importer ever appears. `build.ps1` likewise carries **no CMake logic and no build logic** — the existing wrappers stay the implementation. That constraint is not stylistic: it is the whole mitigation for the kill-PowerShell collision (§ Risks), so a reviewer should reject any build logic that lands in `build.ps1`.

**Slice 2 — make the Preferences Tracker tab a real setup surface.** No new banner and no new window: first run already opens Preferences on this tab, so the work goes into the surface already in front of the user. **This slice was ~60% delivered by PR #1833 before it started** (§ Context 2); what follows is the re-scoped remainder, and the *already-done* column is stated explicitly so a reviewer can reject any re-implementation.

*Already shipped by #1833 — do not rebuild:* (a) the **candidate-credential probe** — `AppController::ProbeTrackerCredentials` ([`AppController.cpp:140`](../../../Source/Core/src/AppController.cpp:140)) builds a throwaway backend via `ITrackerBackendFactory::Create` ([`ITrackerBackendFactory.h:30`](../../../Source/Core/include/ITrackerBackendFactory.h:30)) and returns `ProbeReachability`'s verdict; (b) the **buffer→config extraction**, delivered with exactly the out-param signature this plan specified — `CopyTrackerBuffersToConfig(const UiDrawSession& d, TrackerConfig& cfg)` ([`SmatchetPreferencesUi.cpp:540`](../../../Source/Core/src/Ui/SmatchetPreferencesUi.cpp:540)), called by the probe at :578 with a candidate config and by `onPreferencesSaveAndSync` at :794 with `d.cfg`, keeping `NormalizeViewsBackendKey` (:545) and `TrimTrackerCredentialFields` (:559) inside the helper so neither caller can bypass the issue-#979 trim; (c) the **Test-connection UI** + its `trackerPrefsTest{InFlight,Result,ResultKind,Gen}` session fields ([`SmatchetUiSession.h:305-310`](../../../Source/Core/include/Ui/SmatchetUiSession.h:305)) + the four `prefs.tracker.test.*` en/fr strings ([`SmatchetLocalization.cpp:1101-1106`](../../../Source/Core/src/SmatchetLocalization.cpp:1101)).

One design note worth inheriting rather than "fixing": #1833 used a **monotonic generation counter** (`++d.trackerPrefsTestGen`, checked inside the posted lambda) where this plan had specified a `shared_ptr<atomic<bool>>` cancel atom copied from `AiPrefsTestConnection`. The counter is the better primitive here — it supersedes stale probes *and* handles window-close with one integer compare, no allocation, no atom to reset. Do **not** retrofit the cancel-atom shape for symmetry with the Assistant tab.

*The remainder this slice actually delivers* is the **setup-state half**: a `TrackerSetupCompleted` flag on `TrackerConfig` (serialized, with a veteran migration so existing users never see the explainer), a pure `TrackerSetupPure` decision helper, a first-run explainer on the tab ("Smatchet is read-only until a tracker is connected"), and — the load-bearing piece — **gating the read-only clear on a probe that came back green for the credentials currently in the buffers**. That last one needs a `trackerPrefsTestVerifiedFingerprint` field that #1833 did not add: the existing probe state records *a* verdict, not *which credentials* it verified, so without a fingerprint a user could probe successfully, then edit the token, then Save & Sync and clear read-only on an unverified value.

**Slice 3 — `QUICKSTART.md`.** Pure docs; leads with `.\build.ps1`, demotes raw preset blocks in `README.md` to an "Advanced" subsection.

It does **not** re-implement the detection — with-msvc's own stderr line is the diagnosis.

## UX Pillar callouts

- **Pillar 1 (perf, 144 Hz / 6.94 ms steady-state)**: slices 1 + 3 have no runtime impact. Slice 2 adds **no always-on draw work** — every new widget lives inside the Preferences window, which is not drawn when closed, and the explainer sits behind a `NeedsSetup` bool test. The probe runs off-thread. Steady-state cost with Preferences closed is zero.
- **Pillar 2 (UI-thread never blocks > 100 ms without visible cue)**: the credential probe is network I/O and **must never** run inline. As shipped it already satisfies this — `LaunchBackgroundTask` + `PostToMainThread` off the UI thread ([`SmatchetPreferencesUi.cpp:584-586`](../../../Source/Core/src/Ui/SmatchetPreferencesUi.cpp:584)) with a `BeginDisabled` + `prefs.tracker.test.testing` cue for the duration (:573, :622-626). **Outstanding**: the `/* PILLAR2_WORKER_ONLY */ // est-latency: <N>ms` annotation is **absent** from both `ProbeTrackerCredentials` and the dispatch site (`grep -n PILLAR2_WORKER_ONLY` on both files → no match), so the shipped code satisfies the invariant behaviourally but not the scanner contract. Adding it is a slice-2 deliverable; est-latency 3000 ms (the HTTP timeout the backends already use).
- **Pillar 3 (never crash)**: three hazards. (a) Probe supersession — **handled as shipped** by the generation counter (`++d.trackerPrefsTestGen` on trigger :582 and on Preferences close :155, compared inside the posted lambda :587), so a late verdict from an abandoned probe returns without touching `g_ui`. The new fingerprint field must be cleared at that same close site or it survives into the next session's window. (b) Backend lifetime — the throwaway backend is a `const std::unique_ptr<ITrackerBackend>` local to `ProbeTrackerCredentials` and is never installed on a context (ADR-0012); note the *config* is captured by value into the worker lambda (`probeCfg`), which is what keeps concurrent UI edits from corrupting the worker's view. (c) The veteran migration runs inside the loader's already-`try`-wrapped region and must not throw on a partially-populated config; `ShouldGrandfatherExistingUser` takes a `const&` and performs no allocation beyond string compares.
- **Pillar 4 (accessibility — keyboard nav / font scaling / WCAG AA)**: all new controls are standard `ImGui::Button` / `InputText` / `TextWrapped` inside an existing tab, so tab-order and font scaling come free. WCAG AA contrast on the verdict colours is **not** audited here — the tab reuses the Assistant tab's `resultType` colour convention, so it inherits whatever that already is. Flagged, not fixed.

## Risks / non-goals

### Risks

- **Collision with [`docs/plans/kill-powershell-minimize-toolchain.md`](kill-powershell-minimize-toolchain.md)** — that active plan's Phase 1 converts `build_and_run.ps1` and `build_standalone.ps1` to bash, and Phase 2 ports `scripts/common/SmatchetCMakeCommon.ps1` to `.sh`. This plan adds a **new** root `build.ps1` on top of exactly those files. Direct collision, not a parity gap. **Mitigation (decided: keep kill-PS alive, ship the shim)**: `build.ps1` is a ≤60-line dispatcher with zero build logic, so kill-PS re-points its single delegation line at `build-and-run.sh` and keeps the entry-point name; and `build.ps1` is added to kill-PS's Phase-2 port list **in the slice-1 PR** (a one-line edit to that plan — do not defer it; an unrecorded collision is exactly how the msvc-onboarding claim went stale). The rescope (no `SmatchetMsvcEnv.ps1` module, no `with-msvc.ps1` refactor) shrinks this collision to one new file. Slice 1 must not grow build logic into `build.ps1`; that is what would make the collision expensive.
- **~~`app-controller-fan-in` gate fires~~ — RETIRED (2026-08-03).** This risk existed only because the probe was planned as a standalone TU needing `#include "AppController.h"`. #1833 put the probe **on `AppController` itself** and the dispatch inside `SmatchetPreferencesUi.cpp`, which already includes the header — so the cap (baseline 115, hard-FAIL ratchet-down-only) is untouched and **no `SMATCHET_DEVIATION` is owed**. The remaining new TU, `TrackerSetupPure`, is pure and must **not** include `AppController.h`; if an implementation finds itself reaching for it there, that is the signal the setup predicate has absorbed orchestration it should not own.
- **Stale-credential grandfathering** — `ShouldGrandfatherExistingUser` checks that a credential is *present*, not that it *works*. A user with a revoked PAT is silently skipped past the one surface built to fix them. **Accepted for v1**: the Test-connection button is available to them on demand, and gating the migration on the background poller's last verdict would make config load depend on network state, which is worse. Revisit if it generates reports.
- **Offline first run** — clearing `ReadOnlyMode` only behind a green probe strands a user with no network in permanent read-only. Mitigation: an explicit secondary action on the explainer — "Save without verifying (stays read-only)" — which persists the credentials and sets `TrackerSetupCompleted = true` but leaves `ReadOnlyMode` untouched, so the background poller can flip it later. The safety default is never silently discarded.
- **Verified-state staleness** — a green probe followed by a keystroke in the token field must not still count as verified. Mitigation: `trackerPrefsTestVerifiedFingerprint` (item 16); the read-only clear compares it against the current buffers and refuses on mismatch. This is a bucket-E assertion, not a code-review promise.
- **MSVC env import mutates process env** — accepted; scoped to the script process, identical to existing `with-msvc.ps1` behaviour.
- **Dead-code removal is a real diff, not a comment fix** — deleting `Use-Msys2Ucrt64Environment` (item 2a) is safe only because the tree has no caller. Verified by a repo-wide grep (2026-08-03): the sole definition is `scripts/dev/local/build_standalone.ps1:105`, and every surviving *call* site lives in a stale sibling checkout — `.claude/streams/watch-button/scripts/{dev/build_standalone.ps1:182,publish/release_github.ps1:537}` and `.codex/worktrees/*` — all pre-#495 snapshots outside this repo's checkout, which must not be read as evidence of a live caller. (`scripts/publish/release_github.ps1:540` mentions the name only in a removal comment.) If a caller is found at implementation time, drop item 2a and keep the function — the pre-flight throw (item 2b) is the load-bearing half.
- **Duplicated happy path across `README.md` and `QUICKSTART.md`** (decision: keep both, QUICKSTART links out). Two root docs now describe the same clone → build → run path, so they can drift. **Accepted** — a single root doc would either bury the quickstart inside `README.md` or strip the README of a build section entirely, both worse for a first-time visitor. Mitigation: `QUICKSTART.md` is the only place the steps are *spelled out*; `README.md`'s Build section leads with `.\build.ps1` plus a link and keeps only the Advanced preset table. **Consequence a future editor must respect: any change to the happy path touches both files** — flag it in review, do not "fix" the duplication by deleting one file.
- **Preset auto-detect picks the wrong toolchain** — mitigated by printing the chosen preset *and the reason*; explicit `-Preset` always wins; test-build-wrapper asserts the table.
- **Discoverability** — with no banner, a user who closes Preferences before finishing setup gets no further nudge until they reopen it. Accepted for v1: they are already in read-only and that state is visible in the main UI. A first-run banner or coachmark is the named follow-up (§ Out of scope) if this proves insufficient.

- **`build.ps1` routes BOTH dispatch branches through native `powershell.exe -File`**, not just the no-`cl.exe` one. § Files to modify item 1 specifies invoking `build_and_run.ps1` **directly** on the `cl.exe`-present branch; the direct `& $buildAndRun @forward` form was implemented, and slice-1 test 4 caught it binding **positionally** (`Preset=-Preset Target=ninja-iter-msvc`) — a PowerShell **array** splat binds by position, only a hashtable binds by name. The plan's intent ("directly" = do not import the MSVC env redundantly) is preserved — the cl-present branch still never touches `with-msvc.ps1`, asserted by test 6.

- **`with-msvc.ps1`'s "no usable toolchain" status moved from `2` to `78`** — the plan (§ Slice 1, § Files to modify item 3, § Reused-as-is) describes the wrapper's pre-existing `exit 2` as the no-VS contract `build.ps1` keys its install hints on. A CodeRabbit round on PR-1 showed that contract is unsound *as written*: the wrapper's tail is `& $exe @rest; exit $LASTEXITCODE`, so every non-wrapper exit code is the **wrapped** command's, and cmake/ninja/ctest all return 2 routinely — a build that merely failed would print "no usable MSVC toolchain". `78` is out of that range, so the collision goes from live to theoretical. **Residual, accepted and filed**: an in-band status can never be fully unambiguous — no wrapped command returns 78 today (the only wrapped command is `build_and_run.ps1` → cmake/ninja/ctest), but a wrapped command that *did* would still be misreported. The out-of-band fix (a separate status channel — marker file, stderr sentinel) is a larger change to both `build.ps1`'s `$LASTEXITCODE`-only read and the sandbox harness that stubs the wrapper by exit code alone; backlogged as [`categories/tooling/2026-08-04-with-msvc-out-of-band-status.md`](../../self-improvement/categories/tooling/2026-08-04-with-msvc-out-of-band-status.md).

- **The persisted-flag item became a reuse of the already-shipped `BackendHasBeenReachable`** — dropping § Files to modify items **7, 8, 9** (the new `TrackerSetupCompleted` config key, its serialize/deserialize rows, and the first-launch migration) **and the § Verification bucket-A `ShouldGrandfatherExistingUser` matrix**. The re-audit found [`ConfigManager`](../../../Source/Core/src/Config/ConfigManager.cpp) already persists `BackendHasBeenReachable`, set on the first successful backend round-trip — semantically the same "this user has a working tracker" bit the plan wanted to add, and already migration-safe for existing users (an existing config with a reachable backend already has it true), which is exactly what `ShouldGrandfatherExistingUser` existed to compute. The shipped code adds the clear **behind** the verified-fingerprint gate, which lands on the plan's § Non-goals invariant ("clears only after a successful save behind a verified probe") from the other direction. **Amended post-review (`273d43e4`)**: the first cut cleared `ReadOnlyMode` *alone*, which Cursor Bugbot flagged on PR #1935 — read-only is not the flag the rest of the first-run surface reads. `NeedsSetup()`, the locked main menu and the grid welcome state all key on `BackendHasBeenReachable`, so the user saw the save succeed while the app still rendered first-run until the connectivity monitor latched the same verdict a tick later.
