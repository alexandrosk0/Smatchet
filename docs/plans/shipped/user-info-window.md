## Context

Implements the clean-room **User Info Window** spec: a full-window inspector for a single person — identity, recent VCS submissions (Perforce and/or git), recent tracker activity, and the team groups they belong to. Opened by selecting a user elsewhere in the app; acts as a launch point into p4v, the tracker (browser), and the app's active query.

The spec is tracker-agnostic. Smatchet's active backend is pluggable (`ITrackerBackend` → Jira / Plane / GitHub). Today **only `JiraClient` implements `ITrackerCollaboration`** (group-name + user search); `PlaneClient::Collaboration()` and `GitHubClient::Collaboration()` return `nullptr` ([PlaneClient.cpp:149](../../../Source/Core/src/Tracker/PlaneClient.cpp:149), [GitHubClient.cpp:72](../../../Source/Core/src/Tracker/GitHubClient.cpp:72)). There is **no activity-feed struct/endpoint**, **no group-members fetch**, **no global group catalog**, **no p4-changes-by-user** query, and **no git/GitHub-commits-by-user** query. This plan adds: a narrow backend **activity role** implemented by all three trackers, the P4 + GitHub-commits VCS queries behind a common `VcsSubmission` shape, the config keys, and the window itself.

**After this lands**: selecting a user opens a full window showing their recent VCS submissions (p4 changes and/or GitHub commits — unified feed or separate sections, user-switchable), a day-windowed tracker activity feed, and expandable team-group membership, with click-to-p4v / open-in-browser / add-to-query / copy interactions throughout — full-fidelity on **Jira, Plane, and GitHub** backends, and laid out **mobile-first** so it works on a phone framebuffer (shipped Android host, `docs/plans/mobile-app-jql-mvp.md`) as well as in desktop docking.

**Sequencing dependency — tracker/UI slices land after [`multi-grid-tabs.md`](multi-grid-tabs.md).** Multi-grid de-singletons the app: `AppController::Backend` (one `atomic_load`ed `ITrackerBackend`) becomes `map<paneId, GridLiveContext>` (each pane its own `unique_ptr<ITrackerBackend>`), and the single active query (`cfg.JqlQuery`) becomes per-pane `viewId` with global actions targeting `focusedPaneId`. This window's two cross-cutting touch-points — **which backend answers user/activity/group lookups** and **where add-to-query writes** — both resolve through a **pane**: the window captures the **source pane** (the pane the user was selected in) at `Open()` and uses *that* pane's `GridLiveContext` backend for all tracker lookups and *that* pane's view for add-to-query. Slices 3–5 therefore depend on multi-grid **S1** (de-singleton + per-pane backend + focused-pane model) and **S3/S4** (focus model + global-action routing); the multi-grid-independent parts (P4 + GitHub-commits VCS queries, shared-helper extraction, config keys — Slices 1–2) carry no such dependency and can land earlier. Exact accessor names (`AppController::BackendForPane(paneId)` / `GridLiveContext::Backend()` / `UiDrawSession::focusedPaneId`) are the *assumed* multi-grid post-landing shape — confirm against the merged API before Slice 3.

**Relation to [`dual-ui-mode-desktop-mobile.md`](../shipped/dual-ui-mode-desktop-mobile.md)** (Phase 0 shipped — plan in `docs/plans/shipped/`): **no hard dependency.** The window is designed mobile-first (single column, collapsible sections, touch targets, width-adaptive row stacking) so it renders correctly in today's desktop docking AND slots into the Mobile-mode shell unchanged when dual-ui-mode lands. It does not reference `UiMode` or the mobile chrome.

Scope decisions (confirmed with user 2026-06-06; **revised 2026-06-10** per R1–R3):

- **Tracker support = Jira + Plane + GitHub full-fidelity, resolved per source-pane backend.** *(Supersedes the 2026-06-06 "Plane/GitHub degrade empty, zero backend code" decision.)* Activity + group lookups move to a **new narrow nullable role `ITrackerActivity`** (`ITrackerBackend::Activity()`, `nullptr` if unsupported — same pattern as `Collaboration()`; **[ADR-0021](../../adr/0021-itracker-activity-sixth-role.md)**), so Plane/GitHub implement activity + groups **without** being forced to fake the full `ITrackerCollaboration` surface (comments/watchers/votes/worklogs stay Jira-only and out of scope). Group-membership methods **move** to the new role (re-grill Q2): `FetchUserGroupNames` is **deleted from `ITrackerCollaboration`** and its single backend call-site ([AppController_CatalogAndFieldEdit.cpp:1711](../../../Source/Core/src/AppController_CatalogAndFieldEdit.cpp:1711)) repoints to `Activity()` — one home per capability, no duplication. The window null-checks `Activity()` on the source pane's backend and renders empty tracker sections only when it's genuinely null (e.g. fixture backends).
- **Activity feed is always project/repo-scoped — never instance-wide** (re-grill Q3). All three backends scope the feed to the **source pane's project/repo**: Jira's discovery JQL gains a `project = <source-pane-project>` clause; Plane uses its naturally project-scoped issue-history endpoints; GitHub uses **repo issue events** (repo-scoped — NOT the account-wide user-events API with its 90-day retention + noise). Uniform feed semantics ("this user's activity in this project"), bounded HTTP cost.
- **Groups map honestly per backend** (re-grill Q4): Jira = real groups (existing `FetchUserGroupNames`); GitHub = **org teams** (`read:org`-gated — missing scope degrades empty + status hint); **Plane = none** (Plane's API has no group/team concept — the groups section hides entirely on Plane panes; no pseudo-group fakery). `ProductionGroupKeyword` highlighting applies wherever real names exist.
- **VCS submissions = Perforce and/or GitHub commits, behind one `VcsSubmission` shape.** p4 changes come from local `p4 changes -u <user>` (as before); git commits come from the **GitHub REST API** (`GET /repos/{owner}/{repo}/commits?author=<email-or-login>`, repos from a new config key, auth reusing the tracker config's `GitHubPat`/`GitHubBaseUrl` — re-grill Q6: `TrackerConfig` persists **all** backends' creds simultaneously regardless of active `TrackerType` ([ConfigManager.h:60](../../../Source/Core/include/Config/ConfigManager.h:60)), so the git section works even when the source pane runs Jira/Plane; empty PAT → git section hides + status warning). Which sources appear is config-driven (p4 configured → p4 rows; `GitCommitRepos` non-empty → git rows). **Layout is switchable: unified feed (rows tagged p4/git, merged by timestamp, mobile default) or separate sections** — a `VcsFeedLayout` config key + an in-window toggle.
- **Activity feed = one row per user-authored change event, per backend's native model.** Jira: changelog items via JQL `assignee WAS "{user}" OR reporter WAS "{user}"` over `updated >= -Ddays` → per-issue `expand=changelog` → author + window filter. Plane: issue-activity endpoints filtered by actor + window. GitHub: **repo issue events** by actor + window (re-grill Q3). All three map into the same backend-agnostic `TrackerActivityEntry`. Progress counter = items-scanned / total.
- **Issue-key detection = new `FindFirstIssueKeyInText` helper in `ProjectResolver`, delegating per-token to the existing `ExtractIssueKeyPrefix`.** Reuse keeps key-validation single-source; only a word-boundary tokenizer is new.
- **`onAddToQuery` = replace the source pane's view query with the key-equality query in that backend's query language** (re-grill Q5/Q5b — the **key clause**, per Tracker `CONTEXT.md`): Jira `key = "{key}"` filters **server-side** (builder exists, [JiraIssueSearch.cpp:201](../../../Source/Core/src/Tracker/JiraIssueSearch.cpp:201)); Plane `key:PROJ-123` and GitHub `key = "owner/repo#N"` get a NEW **client-side post-fetch filter** — the only clauses those two languages evaluate locally (Plane's mini-language has **no general evaluator** today; the fetch returns the whole project — the post-filter narrows the result set, fetch via the existing backend-agnostic `FetchIssuesForKeys` [ITrackerIssueReader.h:54](../../../Source/Core/include/ITrackerIssueReader.h:54) where applicable). No general query-language work — key clause only. Post-multi-grid there is no single active query — add-to-query targets the **source pane's** view through multi-grid's per-pane view-mutation path. If the source pane has closed, fall back to `focusedPaneId` (or no-op + status line if none). **Deliberate deviation from spec 7.4**: the activity Issue cell passes the parsed **key** (not the issue URL) to add-to-query; the URL is kept only for the context-menu "Open in Browser".
- **Mobile-first layout.** Single-column flow of collapsible sections (identity → VCS → activity → groups), touch-sized hit targets (≥ ~40px scaled), no fixed-width multi-column tables — rows stack to two-line cards below `kNarrowLayoutWidthPx` (600px logical, new shared header `Source/Core/include/Ui/SmatchetLayoutBreakpoints.h` — re-grill Q8; pre-seeds dual-ui-mode's breakpoint) and widen into columns above it. Desktop docking gets the same window, just wider. No `UiMode` dependency.
- **Shared P4 CL-preview tooltip + p4v launcher = extracted to public helpers** (`DrawClTooltipAsync` / `LaunchP4VcLike` are today coupled to `AnnotateAnalysisUi`'s private `_Internal.h` + a single global hover slot). Extraction moves the hover state out of the Annotate singleton (key it by CL) so two windows don't collide.
- **All activity + group + VCS state is in-memory.** No SQLite table, no schema bump, no migration. Only persisted addition = the JSON config keys. Terms canonicalised in [Tracker `CONTEXT.md`](../../../Source/Core/src/Tracker/CONTEXT.md): `TrackerActivityEntry`, **"group roster"** (`GroupMemberCache`) — NOT "group catalog" (collides with **Field catalog**). New term: `VcsSubmission` (source-tagged p4/git submission row).
- Delivered as **5 slices / 4 PRs** (see § Approach).

## Approach

**Five slices, batched into 4 PRs** (per § PR-batching — one PR per logical feature, split along seams; slices 1+2 are both "VCS foundation" and batch together):

**Slice 1 — P4 foundation + shared-helper extraction + config keys (no UI window).** *(PR 1, multi-grid-independent)*
(a) Add `P4ChangesForUser(cfg, p4user, maxN) -> vector<P4ChangeSummary>` to the P4 layer (new `p4 changes -u <user> -m N -s submitted` invocation, reusing `P4RunCommand`); pure-logic output parse is bucket-A testable. (b) **Extract** the shared CL-preview tooltip + p4v launcher out of `AnnotateAnalysisUi_Internal.h` into public helpers (`P4ClPreview.{h,cpp}` + `P4vLaunch.{h,cpp}`), moving the hover slot off the Annotate singleton (key by CL); repoint `AnnotateAnalysisUi` to the extracted helpers (DRY-positive, no behaviour change). (c) Add config keys via the existing table-driven `FieldDesc`/backend-block pattern (clamp like `cl_cache_max`): `ProductionGroupKeyword` (string), `UserActivityDayWindow` (int, default 30), `MaxUserChanges` (int), `GitCommitRepos` (string, comma-separated `owner/repo` list, default empty), `VcsFeedLayout` (string enum `unified|separate`, default `unified`). (d) Define the common `VcsSubmission` struct (source tag `P4|Git`, id, ISO timestamp, author, first-line message, optional URL) + the p4 adapter (`P4ChangeSummary → VcsSubmission`) + the timestamp merge-sort for the unified feed (pure logic, bucket-A).

**Slice 2 — GitHub commits-by-user VCS source.** *(PR 1, multi-grid-independent)*
`GitHubCommitsForUser(cfg, authorEmailOrLogin, maxN) -> vector<VcsSubmission>` — iterate `GitCommitRepos`, `GET /repos/{owner}/{repo}/commits?author=…&per_page=…` via `TrackerHttpClient` (subsystem invariant), auth = the tracker config's `GitHubPat`/`GitHubBaseUrl` (persisted regardless of active `TrackerType` — works under Jira/Plane panes; re-grill Q6); map commit JSON → `VcsSubmission` (source `Git`, html_url for browser-open). Author match uses the tracker user's **email** (the commits API matches author email or login — email avoids a separate identity-mapping table; risk-flagged below). Empty `GitHubPat` → the git section **hides** + a status-line warning (unauthenticated 60 req/hr is not viable). Lives beside the GitHub tracker client but is **VCS-section plumbing, not the tracker backend** — it works regardless of which tracker the source pane runs.

**Slice 3 — backend activity role + Jira implementation (strict zone).** *(PR 2)*
New narrow nullable role: `ITrackerActivity` (`Source/Core/include/ITrackerActivity.h`) with `FetchUserActivity(accountId, dayFrom, dayTo, progress&, out&, err&)` returning the backend-agnostic `TrackerActivityEntry` (timestamp, issueKey, issueUrl, summary, actionLabel, details); `FetchGroupMembers(groupName, out&, err&)`; `FetchUserGroupNames(accountId, out&, err&)` (**moved** from `ITrackerCollaboration` per re-grill Q2 — deleted there, its single backend call-site [AppController_CatalogAndFieldEdit.cpp:1711](../../../Source/Core/src/AppController_CatalogAndFieldEdit.cpp:1711) repoints to `Activity()`, and the Jira implementation [JiraUserAndMeta.cpp:372](../../../Source/Core/src/Tracker/JiraUserAndMeta.cpp:372) relocates under the new role — one home per capability); `ClearUserActivity()`; plus `TrackerActivityProgress` (current/total) for the loading bar. `ITrackerBackend::Activity()` returns `nullptr` by default. **Jira implements** (one changelog-item-per-row, author-filtered, JQL `assignee WAS / reporter WAS` discovery **ANDed with `project = <source-pane-project>`** — re-grill Q3 project scoping; Jira-shaped JQL stays behind `JiraClient`, e.g. `JiraActivityFeed.{h,cpp}`). The in-memory **group roster** (`GroupMemberCache`) is held **per `GridLiveContext`**, loaded lazily. AppController delegators take a **pane/backend selector** (`paneId`), resolve the source pane's `GridLiveContext.Backend()`, and null-check its `Activity()`. All HTTP routes through `TrackerHttpClient`. Delegate to `tracker-backend` (+ `architect` for the role-introduction + per-pane delegator reshape).

**Slice 4 — Plane + GitHub activity implementations (strict zone).** *(PR 3)*
`PlaneClient` implements `Activity()`: activity from Plane's issue-activity/history endpoints filtered by actor + day window (naturally project-scoped — re-grill Q3); **groups = none** (re-grill Q4 — Plane's API has no group/team concept; `FetchUserGroupNames` returns empty, the groups section hides on Plane panes, no member-list pseudo-groups). `GitHubClient` implements `Activity()`: activity from **repo issue events** (`GET /repos/{owner}/{repo}/issues/events` — repo-scoped per re-grill Q3, NOT the account-wide user-events API with its 90-day retention) filtered by actor + window; groups = **org teams** (`GET /orgs/{org}/teams` + membership) when the configured repo belongs to an org and the token has read:org — otherwise the groups section degrades empty with a status hint (not an error). Both map into `TrackerActivityEntry`; no Jira types leak. **`Collaboration()` stays `nullptr` for both** — comments/watchers/votes/worklogs remain out of scope. **Plus the key-clause post-filters** (re-grill Q5b): Plane gains a `key:PROJ-123` clause parse + client-side post-fetch filter (the only Plane clause evaluated locally — the mini-language has no general evaluator); `GitHubQueryFromJql` gains `key = "owner/repo#N"` handling + the same client-side post-filter. Delegate to `tracker-backend`.

**Slice 5 — the UI window, mobile-first.** *(PR 4)*
New `SmatchetUserInfoUi` (header + VCS section + activity section + groups section + shared issue-key context-menu popup), following the `AnnotateAnalysisUi` / `SmatchetPerfUi` full-window pattern: `DrawWindow(AppController&, UiDrawSession&, bool* pOpen)` + `Open(sourcePaneId, displayName, email, accountId)` — the **source pane id** is captured so all tracker lookups + add-to-query target that pane's backend/view. **Layout is mobile-first**: one vertical column of collapsible sections; per-row touch targets ≥ ~40px (scaled); below `kNarrowLayoutWidthPx` (600px, shared `SmatchetLayoutBreakpoints.h`) VCS/activity rows render as stacked two-line cards, above it as table columns; the VCS section honours `VcsFeedLayout` (unified tagged feed vs separate Perforce/Git sections) with an in-window toggle that writes the config key. Registered in `SmatchetUI::drawSecondaryWindows()`. Reuse the **extracted** `P4ClPreview` tooltip + `P4vLaunch` (p4 rows); git rows get open-in-browser via the commit `html_url`. `onStatus` / `onAddToQuery` thread through `UiDrawSession`; `onAddToQuery` replaces the **source pane's** view query via multi-grid's per-pane view-mutation path (fall back to `focusedPaneId` if the source pane closed). Issue/details/description key rendering uses `FindFirstIssueKeyInText`. All backend/P4/GitHub fetches run on a **worker thread**, posting back via `MainThreadDispatcher` (the `SmatchetAuditUi` pattern) — never sync on the ImGui thread (Pillar 2). Window resolves + null-checks the source pane's `Activity()` → empty tracker sections only for genuinely role-less backends / closed pane. One-shot group-fetch flag; Escape/Close → `ClearUserActivity` on that backend; per-render group resolution. Delegate to `grid-engine` / general UI.

Trade-offs: (1) the activity feed is the riskiest surface — now ×3 backends with three different native models (changelog / issue-history / events). It is isolated in Slices 3–4 so the UI (Slice 5) builds against the role interface and ships full-fidelity per backend as each lands; day-windowing + actor-filter bound row/fetch volume everywhere. (2) The narrow `ITrackerActivity` role costs one more interface but avoids forcing Plane/GitHub through the fat `ITrackerCollaboration` contract — the alternative (implement Collaboration with stubbed failures) would lie to every existing Collaboration call-site.

## UX Pillar callouts

- **Pillar 1 (perf, 144 Hz / 6.94 ms steady-state)**: Window draws bounded scroll regions — cost bounded by visible rows. Activity visible-window filtering (spec 7.2: string compare on `YYYY-MM-DD`) runs per-frame over a snapshot list; keep the list bounded and the filter O(n) cheap. Unified-feed merge-sort happens once per fetch completion (worker thread), never per-frame. No per-frame allocation in the draw path. Width-adaptive layout switch is a branch on `ImGui::GetContentRegionAvail().x`, not a relayout pass.
- **Pillar 2 (UI-thread never blocks > 100 ms without visible cue)**: All I/O (p4 changes fetch, GitHub commits fetch, activity fetch on any backend, group-members fetch, p4 describe for tooltips) is **worker-thread / async** — never synchronous in the ImGui draw path. Activity load shows a progress bar (spec 7.6) driven by the current/total counter; VCS fetch logs "Loading…" and the load button disables while in flight. CL tooltip uses the existing async `DrawClTooltipAsync`. Any new sync-I/O reachable from `ImGui::*` is a CRITICAL — must carry `/* PILLAR2_WORKER_ONLY */`.
- **Pillar 3 (never crash)**: RAII throughout; bounds-check all parsing (p4 changes output, GitHub commit/event JSON, Jira changelog JSON, Plane activity JSON, 6+-digit CL scan, estimate-seconds parse → leave unchanged on failure per spec 7.5.1). Graceful degrade for role-less backends / missing token scopes (empty sections + status hint, never throw). Empty `catch(...)` banned.
- **Pillar 4 (accessibility — keyboard nav / font scaling / WCAG AA)**: Escape closes (spec 3.3) — keyboard-reachable. **Mobile-first directly serves this pillar**: touch targets ≥ ~40px scaled, single-column flow survives font scaling without horizontal overflow, collapsible headers are full-width hit zones. Color roles map to Smatchet's config palette (contrast inherited from theme). Full keyboard nav of tables is aspirational/backlogged (consistent with existing windows); no new auto-fail.

## Risks / non-goals

- **Hard dependency on `multi-grid-tabs` landing first (Slices 3–5).** They build on multi-grid's de-singletoned `AppController` (`map<paneId, GridLiveContext>`, per-pane backend) + focused/source-pane model — APIs that don't exist until multi-grid S1+S3/S4 merge. Mitigation: assumed accessor names flagged inline as "confirm against merged API"; **Slices 1–2 (P4 + GitHub-commits VCS, shared-helper extraction, config keys) carry no multi-grid dependency** and ship as PR 1 independently/earlier. If multi-grid slips, Slices 3–5 wait; PR 1 still ships.
- **Source-pane lifecycle while window is open.** The window captures `sourcePaneId` at `Open()`; that pane can be closed/hidden before the user acts. Risk: dangling backend reference / writing add-to-query into a dead pane. Mitigation: resolve the backend through `GridLiveContext` each use (not a cached pointer) — gone pane → degrade (tracker sections empty / add-to-query falls back to `focusedPaneId` or no-ops with a status line). Never deref a retired backend (multi-grid graveyard, ADR-0012).
- **Three self-designed activity contracts** (Jira JQL `WAS` + changelog scan; Plane issue-history; GitHub **repo issue events**). Risk: per-backend volume/rate-limits (Jira: N issues × 1 changelog fetch; Plane: per-project scans; GitHub: repo-issue-events pagination — repo-scoped, so no 90-day account-event retention cap, but a busy repo means many pages before the day-window cutoff). Mitigation: day-windowed queries (spec 7.1), actor + window filters bound rows, progress counter everywhere; Jira isolated in Slice 3 / Plane+GitHub in Slice 4 so the UI never blocks on any one backend's tuning. **Plane/GitHub API-shape verification is the first task of Slice 4** — if an endpoint can't deliver per-user activity within budget, that backend's feed degrades (documented + status hint), not the plan.
- **GitHub groups require org + token scope** (`read:org`). Personal/non-org repos have no teams → groups section degrades empty with a status hint. Accepted.
- **Identity mapping across systems.** p4 username = email local-part (spec 6.1) — users whose p4 id ≠ email local-part get no/incorrect changes; GitHub commit-author match = tracker email — users whose commit email ≠ tracker email (noreply addresses!) get no/missing commits. Accepted for v1 (spec edge-case §11) — both surfaced via the "Loading … for {derived-id}…" log line so the derived identity is visible. A per-user identity-override map is flagged out-of-scope.
- **GitHub API rate limits** — unauthenticated 60 req/hr makes the commits source + GitHub activity effectively token-required. Mitigation: status-line warning when `GitCommitRepos`/GitHub activity is exercised without a token; per-open fetch (no polling).
- **`ITrackerActivity` role introduction touches every backend** (new pure virtual on `ITrackerBackend`). Risk: missed override in a fixture backend breaks the build. Mitigation: it's a compile error, not a runtime surprise — dual-target build gate catches it; fixtures return `nullptr`.
- **Shared-helper extraction touches working code** (`AnnotateAnalysisUi`). Risk: regressing the Annotate window's CL tooltip / p4v launch. Mitigation: pure extraction, no behaviour change; the Annotate window's existing bucket-E/scenario coverage must stay green after repointing (verify in Slice 1).
- **Date-window filter relies on `YYYY-MM-DD` string ordering** (spec 7.2, §11). Risk: a backend timestamp not leading with that format breaks the cutoff — now ×3 backends + 2 VCS sources. Mitigation: normalise all timestamps to ISO-8601 at the adapter boundary (`TrackerActivityEntry` / `VcsSubmission` construction); keep the "shorter than 10 chars → keep unconditionally" rule; assert per-source in bucket-A.
- **Deliberate spec deviation (add-to-query value)** — the activity Issue cell passes the parsed key, not the issue URL (spec 7.4), so add-to-query produces a valid key-equality query. Recorded here so it isn't mistaken for an accidental drop; the URL is still used for context-menu browser-open.
- **Mobile-first without the mobile shell.** The window ships before dual-ui-mode; the narrow-width layout is exercised on desktop only by resizing. Mitigation: bucket-E + screenshot coverage at a phone-width framebuffer (~400px logical) is part of Slice 5 verification, so the mobile layout is gated even before the shell exists.
- **Non-goals**: not adding a user-picker/search entry point (window is opened by an existing selection elsewhere); not enabling Plane/GitHub **Collaboration** (comments/watchers/votes/worklogs — `Collaboration()` stays `nullptr` for both; only the new narrow `Activity()` role lands); not local-`git log` support (GitHub API only — a local-clone source is a flagged follow-up); not redesigning the Annotate tooltip or p4v launcher beyond the extraction; not `UiMode`/mobile-shell integration (dual-ui-mode's job); not adding keyboard-grid-nav beyond Escape-to-close (Pillar 4 backlog).
