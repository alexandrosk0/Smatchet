## Context

The user wants Smatchet's tracker capability on phones. Three prior feasibility answers (this session) established: (1) the standalone-light pillars survive on mobile; (2) it can live **in this repo** sharing one `CORE_SOURCES`; (3) the work is overwhelmingly a **host-shell job on a renderer/input-agnostic Core** — not a Core rewrite. This plan turns that into an executable, phased build.

**MVP definition (Phase 0, "just standard")**: launch on Android → enter Jira credentials + a JQL string → see the matching issues as a **scrollable list with columns** → **edit a cell** and have it commit back to Jira. No plugins, no AI/MCP/Whisper/Lua, no offline-sync, no multi-view. Standard issue fields only.

**Intended outcome — the one-sentence "after this lands, X is true"**: *an Android device running a Smatchet `.so` host loads a JQL via the existing `JiraClient::FetchIssuesStreamed` data path and renders + edits the result through the existing `TicketGridColumnsBuilder` / `SmatchetGridFieldEditPipeline`, with zero divergence in the shared `Source/Core` logic.*

Originating thread: this session's feasibility Q&A (no GitHub issue yet — a tracking Issue should be cut when Phase 0 starts, per `AGENTS.md` § Issue triage). Builds on the shipped cross-platform CMake work which **explicitly deferred** Android/iOS toolchains as out-of-scope (`docs/plans/shipped/generic-cmake-cross-platform.md:150`) — this plan is the follow-up.

## Approach

**Android-first, three seams, in-repo.** The grounded evidence (5 adversarial agent reports + a triple-check pass, this session) is decisive on the shape of the work:

1. **Core ports — but its non-Windows side has never been compiled.** `CORE_SOURCES` (`CMakeLists.txt:801`, `GLOB Source/Core/src/*.cpp` minus the two embedding-host TUs at `:802-803`) is already compiled twice from one set — `SmatchetStandalone` (GLFW/GL, `:1388`) and `SmatchetCore_DX12` (DX12, `:1144`). Every `<windows.h>` / COM / WIC use in Core is `#if defined(_WIN32)`-guarded, there is **zero** `std::filesystem` (portable `ghc::filesystem` instead), and Core makes **zero** raw `gl*` calls — all real GL/render-host code lives in `SmatchetImGuiHost.cpp` (excluded from `CORE_SOURCES`) and `Source/Standalone/`. So structurally the mobile target is a **third sibling** linking the same `CORE_SOURCES`, exactly as DX12 is. **The sharp caveat (triple-check, HIGH)**: *both* existing consumers define `_WIN32`, and the only required CI build is Windows+MSVC — so the entire `#else` side of Core (POSIX `SubprocessCapture`, plaintext-secret passthrough, XDG paths) **compiles for the first time** under NDK clang. That is a correctness risk, not merely a `/WX` warning wall, and Slice 0b front-runs it on Linux clang *before* the NDK adds variables.

2. **The data path is renderer-agnostic and already worker-threaded.** `TrackerConfig.JqlQuery` → `JiraClient::FetchIssuesStreamed` (`JiraIssueSearch.cpp:270`) → `TrackerGetLogged`→`cpr::Get` → `AppendCachedTicketFromJiraSearchIssue` → `vector<CachedTicket>`, delivered via `onBatch` on a `std::thread` spawned by `TicketSyncService` (`:567`). Cell edits commit through `SmatchetGridFieldEditPipeline` (`EnqueueGridFieldEdits`→`PumpGridFieldEdits`→`RunCommitWorker` off-UI-thread→`PostToMainThread`) and route to an HTTP **PUT** (`JiraClient::UpdateField`→`TrackerPutLogged`, `JiraIssueMutation.cpp:229`). Both are standard C++14 that runs on Android unchanged. Mobile injects nothing here — it reuses the `ITrackerBackendFactory` / `AppController::SetBackendFactory` DI seam (`AppController.cpp:399`) that was built for embedding hosts.

3. **The work is three host-shell seams + a handful of small infra/Core edits.** Seam A: a new **EGL/`ANativeWindow` + `imgui_impl_android` render+input host** modelled on `SmatchetImGuiHost.cpp` (the existing GLFW-free C-ABI host — it already drives ImGui purely via `ImGuiIO`), **including an explicit EGL surface-lost/context-recreate path** (Android frees the GL context on background/rotate — guaranteed, not edge). Seam B: the **cpr/libcurl TLS-backend provisioning** — the one hard blocker (below). Seam C: **CMake target-kind + toolchain + preset + CI** (`add_library SHARED` not `add_executable`, NDK toolchain file, `android-ndk` preset, Android compile job). The Core edits are bounded: a bundled-asset font branch, density/DPI scaling, an Android config-path provider, and Android Keystore secret storage.

**The non-obvious trade-off that shaped the choice**: Android before iOS *not* by preference but because **iOS CI cannot run on the current runners** (every job is `windows-2022`/`ubuntu-latest`; iOS needs a `macos-*` runner that doesn't exist) — Android NDK compiles on the existing Ubuntu runner. Android-first de-risks the shared infra (TLS cross-build, EGL host, density scaling) on the cheaper CI path before paying the macOS-runner tax. This matches the user's stated order.

**The gating risk, restated after the triple-check**: the adversarial "deps cross-compile unchanged" claim was **REFUTED** — cpr 1.9.2 with `CPR_FORCE_USE_SYSTEM_CURL OFF` (`CMakeLists.txt:165`) builds bundled curl and runs SSL auto-detect, whose non-Win/non-Apple else-branch `message(FATAL_ERROR "No valid SSL backend found!")` at `cpr-src/CMakeLists.txt:112` fires at **configure** time on the NDK. Critically, **this is a configure-time FATAL that fires whenever cpr is in the CMake graph at all** — and cpr is a *type* dependency (`cpr::Response/Header/Error` in PUBLIC headers, consumed by ~20 Tracker TUs that GLOB into `CORE_SOURCES`). So the previously-stated "swap two helper bodies via JNI" fallback **does not clear the gate** — the FATAL and every cpr type stay in the build. The real fallback is heavier (§ Risks [HIGH cpr]). **Phase 0 Slice 1 (configure) + Slice 2 (compile/link) jointly gate the plan.**

### Slice breakdown (Phase 0 — Android MVP)

Each slice ends buildable. A slice that can't clear its exit-gate **stops the plan** for re-scoping (don't push past a red spike). Effort bands are rough engineer-day estimates for one engineer, greenfield.

- **Slice 0 — desktop pre-flight, MSVC** *(~0.5d)*: configure the Android preset's *feature shape* on desktop first — verify the `_smatchet-light-features` (MCP/AI/Whisper OFF) **+ `SMATCHET_WITH_LUA_AUTOMATION=OFF`** (file #3) union compiles + links the **plain (non-asan) `SmatchetStandalone`/`SmatchetCore_DX12` dual-target**. *Correction (triple-check Pass 3): Lua-OFF is **not** an un-CI'd flag — `build-and-test.yml:581` (ninja-msvc-asan) / `:669` (ninja-clang-asan) + `sanitizer-nightly.yml:70` already build+ctest with Lua OFF. So this slice is a cheap **confirmation**, not a novel de-risk; its residual value is exercising the light+Lua-OFF union on the **default (non-asan) MSVC dual-target** (the asan jobs don't replicate that exact preset) and catching any non-flag-guarded Lua include before the NDK adds variables.* Exit-gate: dual-target green with Lua off. Caveat: MSVC/`_WIN32`-only — exercises none of the `#else` side, hence Slice 0b.
- **Slice 0b — Linux-clang `#else`-side compile (no NDK, no mobile)** *(~1–2d)*: compile `CORE_SOURCES` with host **Linux clang** (Ubuntu CI runner or WSL) — the cheapest way to exercise every `#if defined(_WIN32)` `#else` branch (POSIX `SubprocessCapture`, plaintext-secret passthrough, XDG path resolution) **before** the NDK toolchain adds ABI/sysroot variables. Exit-gate: `CORE_SOURCES` compiles under non-`_WIN32` clang (TLS/cpr may still be stubbed here — this slice is about Core C++ portability, not deps). *Front-runs the Slice-2 correctness risk on the cheapest possible target.*
- **Slice 1 — TLS configure spike (the gate)** *(~2–4d, hard-timeboxed at 4 working-days)*: provision a per-ABI prebuilt OpenSSL (or MbedTLS/BoringSSL), set `CPR_FORCE_OPENSSL_BACKEND` + `CMAKE_FIND_ROOT_PATH` (file #1), and get cpr/curl past the `cpr-src/CMakeLists.txt:112` configure-FATAL. Exit-gate: `cmake --preset android-ndk` **configures** (no compile yet). **Fallback trigger**: if 4 working-days close with configure still red → invoke the heavy fallback (§ Risks [HIGH cpr]): `CPR_ENABLE_SSL=OFF` so configure passes + cpr types still resolve, then JNI-route *every* HTTPS egress (not two helpers). *This slice + Slice 2 jointly gate everything downstream.*
- **Slice 2 — empty `.so` configure+link+`#else`+warning pass + CI** *(~3–5d)*: add the toolchain (#2), preset (#3), glfw guard (#4), `SmatchetMobile` SHARED target (#5), mobile ImGui lib (#6), Android link arm (#7), mobile configure-fn fork (#8), and the Android NDK CI compile job (#16, advisory) — link an **empty `android_main`** against full `CORE_SOURCES`. This is where `CORE_SOURCES`' `#else` side hits the **NDK** toolchain for the first time (Slice 0b proved host-clang; this adds the Android sysroot/ABI). Cross-compile checklist beyond cpr: `sqlite3` + `SQLiteCpp`, `ghc::filesystem`, `stb`, `nlohmann` (header-only, low-risk). Budget the `/WX`+`-Werror` cleanup pass here (fix at source / ABI-guard, never disable `-Werror`). Exit-gate: `libSmatchetMobile.so` builds + links clean on the CI Ubuntu runner for `arm64-v8a`.
- **Slice 3 — host shell (render + input + lifecycle)** *(~5–8d)*: EGL/`ANativeWindow` render loop + `imgui_impl_android` (file #9) **with an explicit surface-lost/context-recreate path** (`APP_CMD_TERM_WINDOW`/`INIT_WINDOW` → rebuild EGL surface + `ImGui_ImplOpenGL3_Destroy/CreateDeviceObjects` to re-upload the font atlas); touch→`ImGuiIO` + **soft-keyboard IME as a first-class deliverable** (file #10, its own exit-gate); font-bytes injection (#12), density scaling (#13), Android config-path provider (#14, **sequenced before Slice 4**) + the Gradle/Kotlin Activity + manifest host (#11). Exit-gates (all required): (a) a blank ImGui frame renders + accepts touch; (b) tapping a text field shows the soft-keyboard and UTF-8 reaches `ImGuiIO`; (c) **survives background→foreground + rotation without losing the font atlas or crashing**.
- **Slice 4 — wire the data path (the MVP)** *(~3–5d)*: feed `TrackerConfig{Domain,Email,ApiToken,JqlQuery}` in (interim plaintext + on-screen warning, #15), call `JiraClient::FetchIssuesStreamed` via `TicketSyncService` on its worker thread — **passing BOTH a `configOverride` AND a `viewsOverride`** so the worker triggers neither the `ConfigManager::Load` disk read (`JiraIssueSearch.cpp:280`) nor the `LoadViewsOrBootstrap` bootstrap-WRITE to an unprovisioned path (`JiraIssueSearch.cpp:301`) — render the `CachedTicket` batches through `TicketGridColumnsBuilder`, and commit a cell edit through `SmatchetGridFieldEditPipeline` (the commit is an HTTP **PUT** — confirm the fallback, if used, covers Put). Exit-gate: load a real JQL → see columns → edit a cell → confirm the Jira write. **Smoke env (name it now, don't defer)**: a throwaway Atlassian Cloud free-tier site + a scoped API token in an env var (never committed), a fixture JQL like `project = SMTEST ORDER BY updated DESC`, against an `arm64-v8a` emulator (`reactivecircus/android-emulator-runner`) or a physical device. On-device run = manual residue until the emulator harness lands (§ Verification).

## UX Pillar callouts

- **Pillar 1 (perf, 144 Hz / 6.94 ms steady-state)**: the grid draw + ImGui render is the same immediate-mode code that already meets budget on desktop; mobile GPUs are weaker but the ES3 path renders the *same* draw lists. Risk is incidental, not structural — measure on a mid-tier device (Phase 0 verification). Density scaling (`ScaleAllSizes`) changes layout sizes, not per-frame cost.
- **Pillar 2 (UI-thread never blocks > 100 ms without visible cue)**: the JQL fetch (`cpr::Get`, synchronous-blocking) **already** runs on the `TicketSyncService` worker thread, and cell commits already run on `RunCommitWorker` off-thread with `CellWriteFeedback{Saving}` cues. Mobile inherits both. **No new sync I/O is added on the UI thread** — the only new UI-thread code is the EGL render loop + touch dispatch (non-blocking) and the soft-keyboard JNI calls (must be fire-and-forget, not blocking the frame on the IME round-trip — verify in Slice 3).
- **Pillar 3 (never crash)**: the host shell uses RAII for EGL/`ANativeWindow` handles (`// C-ABI handle` markers per `cpp-rules.md`); the surface-lost/recreate path (#9) is itself a crash-avoidance requirement (use-after-free of a freed GL context = the default failure mode without it). Graceful degradation on fetch failure reuses the existing offline-queue fallback (`TryPrepareOfflineFieldEdit`). New POSIX `#else` branches in Core get a first-compile pass in Slice 0b (host clang) + Slice 2 (NDK) and a sanitizer pass where runnable.
- **Pillar 4 (accessibility — keyboard nav / font scaling / WCAG AA)**: **known hard wall** — ImGui draws to a GPU canvas with no native view tree, so Android TalkBack / screen-readers cannot introspect it. This is the same aspirational-backlogged gap as desktop (Pillar 4 has no auto-fail today). Font scaling **is** addressed (density scaling, file #13). Screen-reader support is an explicit **non-goal** for Phase 0 (and a flagged Phase-1 research item) — surfaced here so it isn't assumed.

## Risks / non-goals

**Risks** (severity from the grounded adversarial reports + triple-check):

- **[HIGH] cpr/libcurl TLS-backend configure FATAL — and the fallback is not "two functions".** `cpr-src/CMakeLists.txt:112` `message(FATAL_ERROR "No valid SSL backend found!")` fires at **configure** on NDK (`CPR_FORCE_USE_SYSTEM_CURL OFF`, no OpenSSL/MbedTLS in sysroot, Jira HTTPS-only), before any target compiles, whenever cpr is in the CMake graph. cpr is a **type** dependency — `cpr::Response/Header/Error` live in PUBLIC headers (`TrackerHttpUtils.h`, `TrackerHttpClient.h`, `JiraClient.h`, `Sync/NetworkUsageTracker.h`) consumed by ~20 Tracker TUs that GLOB into `CORE_SOURCES` — so the configure-FATAL and every cpr type stay in the build no matter which function *bodies* you swap. **Primary mitigation**: Slice 1 spike provisions a per-ABI TLS lib + `CPR_FORCE_OPENSSL_BACKEND` (file #1) and clears the configure gate honestly. **Fallback (heavier, multi-day)**: set `CPR_ENABLE_SSL OFF` so configure passes and cpr's *types* still resolve, then JNI-route **every** HTTPS egress at all six logged overloads (`TrackerHttpUtils.cpp:112/116/128/139/150/238`, Put mandatory) **plus** the two direct-cpr sites (`SmatchetFieldIconRender.cpp:185`, `JiraIssueMutation.cpp:619`) — file #18 — guarded by a lint gate banning `cpr::` outside the transport helper. *This risk (Slice 1 + Slice 2 jointly) gates the whole plan.*
- **[HIGH] `CORE_SOURCES` `#else` side has never been compiled by a non-MSVC / non-`_WIN32` toolchain.** Both existing consumers define `_WIN32`; the only required CI build is Windows+MSVC. So the entire POSIX `#else` side (`SubprocessCapture`, plaintext-secret passthrough, XDG paths) compiles for the **first time** under clang in this plan — a correctness risk (not the "/WX warning wall" alone). **Mitigation**: Slice 0b compiles `CORE_SOURCES` under host Linux clang (cheapest non-`_WIN32` target) before the NDK; Slice 2 adds the NDK sysroot/ABI on top.
- **[HIGH] EGL/GL context-loss on the Android activity lifecycle.** On background/lock/rotate, Android frees the EGL surface + GL context, including the ImGui font-atlas texture. Without a recreate path the first background → black screen or use-after-free crash. A naive Slice-3 "blank frame renders" gate passes while leaving this latent. **Mitigation**: file #9 includes the surface-lost/recreate path; Slice-3 exit-gate (c) explicitly requires surviving background→foreground + rotation.
- **[HIGH] Mobile build is greenfield** — no toolchain file, no Android preset, the shipped cross-platform plan deferred exactly this (`generic-cmake-cross-platform.md:150`). **Mitigation**: Slices 0b→2 prove the path incrementally (host-clang → empty `.so` link) before any feature work.
- **[HIGH] iOS CI has no runner** — every job is `windows-2022`/`ubuntu-latest`; iOS needs `macos-*`. **Mitigation**: Android-first (this plan); iOS runner cost is the Phase-2 gate (§ Phase 2, slice P2.0), not a Phase-0 blocker.
- **[MED] SQLite stack still cross-compiles even though offline-sync is "out of scope".** The cell-edit commit reaches SQLite via `OfflineQueueService::QueueFieldEditOffline` → `LocalCacheManager` (`SQLite::Database`) on the write path — "no offline-sync" means no *replay UI*, not no SQLite. (`BackendAuditTrail` is **not** SQLite — it's fstream/NDJSON; `LocalCacheManager` is the only SQLite touch.) `SQLiteCpp` + `sqlite3` are linked **unconditionally** (`CMakeLists.txt:988-994`, no offline flag), so they're on the Slice-2 cross-compile checklist, and the DB file must open under the Android `filesDir` (file #14). **Mitigation**: named in Slice 2; if SQLite write-on-edit is undesired for MVP, gate it — but verify the edit still commits.
- **[MED] `/WX` + `-Werror` first-compile wall** — `CMakeLists.txt:266-268`; NDK/Apple clang emit new warning classes (format specifiers around Win32 types on the `#else` side, `-Wunused` on empty non-Win32 stubs, 32-bit-ABI narrowing) that are **fatal** despite `_WIN32` guards being correct. **Mitigation**: budget a warning-cleanup pass in Slice 2; do **not** disable `-Werror` (that would erode the gate for desktop too) — fix at source, ABI-guard where genuinely platform-specific.
- **[MED] API token plaintext at rest** — non-Windows is plaintext passthrough (`ConfigManager_PathUtils.cpp:238`/`#else` `:331-332`). **Mitigation**: MVP ships plaintext **with an on-screen warning** + a Phase-1 Android Keystore blocker (file #15). *Accepted for MVP only* because the alternative blocks the demo; not acceptable for any public release.
- **[LOW] sol2/Lua on a mobile ABI untested** — `_smatchet-light-features` keeps Lua ON; sol2's heavy template instantiation needed GNU-only `-mbig-obj` workarounds that don't apply to NDK clang. **Mitigation**: the Android preset sets `SMATCHET_WITH_LUA_AUTOMATION=OFF` (file #3) — Lua isn't in the MVP anyway.
- **[LOW] Large JQL result truncation** — `JiraIssueSearch.cpp:321` `kMaxPages=50` × `maxResults=100` → silent ~5000-issue cap with only a WARN. **Mitigation**: pre-existing desktop behaviour, inherited unchanged; surface the WARN in the mobile UI as a follow-up.
- **[LOW] WIC attachment-decode is Windows-only** — `CMakeLists.txt:1092-1095`, `WIN32`-gated. Android has **no** attachment-bitmap decode path (functional gap, not a link break). **Mitigation**: attachments are out of MVP scope; wire `stb_image`/platform decode in Phase 1.

**Non-goals (Phase 0)**: offline-sync *replay UI* (SQLite write-on-edit still compiles — see MED row); multiple saved views; multi-backend (Plane/GitHub) on mobile; attachments/image preview; AI chat / MCP / Whisper / Lua console; screen-reader accessibility; iOS; tablet-optimized layout; push notifications. Phase 1/2 design lives in their own sections below.

(Host glibc takes the `clearenv()` `#if` side and never compiled this arm — surfaced only on the NDK.)
- **Gate-coverage learning (recorded for Slices 3–4)** — `SmatchetCore_PosixCheck` runs host Linux clang, which defines `__GLIBC__` and so compiles the **glibc** side of any `#if defined(__GLIBC__)` split; it **cannot** proxy a bug living only in a non-glibc (`#else`) Bionic arm. Only the `android-ndk-arm64` job compiles those. posix-core-check de-risks `_WIN32`-vs-POSIX divergence, **not** glibc-vs-Bionic divergence — the latter needs the NDK job. The `SubprocessCapture.cpp` fix is the worked example.

**Slice 3a (PR A) — Core host-injection seams #12/#13/#14** *(authored this PR; not yet merged — these are design deviations, the build/test result lands in § Verification at closeout):*
- **#13 realized as `SmatchetTheme::ApplyUiDensityScale(float)`, a new member the host calls *after* `ApplyStyle`** — plan #13 said *"wire at the existing style-init site, do not add a parallel one"*. The style-init site (`SmatchetTheme::ApplyStyle`) does exist, but it opens with `style = ImGuiStyle{}`, which wipes any sizes set before it — so density scaling has to run **after** `ApplyStyle` completes, not inside it. Hence a new `SmatchetTheme` member the host invokes post-`ApplyStyle`, rather than an edit inside `ApplyStyle`. A grep (`ScaleAllSizes|DisplayFramebufferScale` across `Source/Core`) confirmed nothing already scales sizes, so there's no double-scaling. No-op when `densityScale <= 0`/NaN; desktop never calls it (scale stays 1.0), so the seam is inert and fully desktop-compilable.
- **#12 injected-font path omits the FA / Segoe-symbol / markdown-variant / redaction merges** — those builders (`MergeFontAwesomeSolid`, `BuildMarkdownVariantFonts`, `BuildRedactionFont`) live **inside** the `#if _WIN32` block, so the cross-platform injected path cannot call them. `TryBuildInjectedFont` loads the body TTF + glyph ranges only, with graceful null-fallthrough to the per-platform default if the blob fails to parse (Pillar 3 — never leave a null `FontDefault`). FA-glyph merge from an injected blob is a Phase-1 follow-up (mobile icon glyphs).
- **Three host-injection setters added (runtime injection, not `#ifdef __ANDROID__`)** — `SmatchetSetInjectedFontBytes(const void*, int, float)` (copies into a Core-owned buffer, `FontDataOwnedByAtlas=false` to avoid double-free), `SmatchetTheme::ApplyUiDensityScale`, and `ConfigManager::SetPlatformSharedUserDataDirectoryOverride(const std::string&)` (override returned first by `GetPlatformSharedUserDataDirectory`, ahead of the per-OS `#if` arms). **Slice 3b + Slice 4 (PR B) — host shell + data path** *(authored this PR; build/test result in § Verification at closeout):*
- **TLS arming is a baked compile-time `CURL_CA_BUNDLE` define, NOT the runtime env var** — the design assumed the host would point libcurl at the materialized `cacert.pem` via `setenv("CURL_CA_BUNDLE", …)`. Live debugging proved the NDK-built libcurl **ignores** the `CURL_CA_BUNDLE` *env var* (only the curl CLI reads it); the load-bearing mechanism is the compile-time `CURL_CA_BUNDLE` define (the on-device private-dir path, set in `cmake/SmatchetThirdParty.cmake`) = libcurl's default `CAINFO`. `CURL_CA_PATH "none"` does **not** survive (cpr's own `CMakeLists` re-sets it to the system store after our block via `add_subdirectory(cpr)`) but is harmless — an explicit cafile is consulted at verify time regardless of any CApath. `android_main.cpp`'s job is to **materialize** the APK-bundled `cacert.pem` at the baked path; its `setenv` calls are belt-and-suspenders only (`SSL_CERT_FILE` is OpenSSL's secondary net via `CURL_CA_FALLBACK ON`). Comments in all three sites (`THIRD_PARTY_LICENSES.md`, `SmatchetThirdParty.cmake`, `android_main.cpp`) corrected to match. Proven live: read HTTP 200 + write PUT HTTP 204.
- **Unplanned Core edit — `MainThreadDispatcher.h` constexpr member → constexpr function** — `static constexpr std::chrono::microseconds kDrainBudget{4000}` is ODR-used when bound by reference (`time_point + duration`), which in C++14 needs an out-of-line definition; MSVC and optimized Clang fold the constant, but the `-O0` Android debug build emits the reference → `libSmatchetMobile.so` fails to link. Swapped to a `static constexpr … DrainBudget()` function (implicitly inline, no ODR-use of a static data member); two call sites updated.
- **Unplanned Core edit — `SubprocessCapture.cpp` block-scope `extern char** environ` → `::environ`** — a block-scope `extern` inside the anonymous namespace mints a *new* internal-linkage entity (C++14 [basic.link]/6) → unresolved on Bionic (host glibc takes the `clearenv()` `#if` side and never compiled this `#else` arm). Switched to `::environ` from `<unistd.h>`. This is the **second** fix to the same Bionic `#else` arm (the first — the string-ctor swap — shipped in #1021); recorded as a worked example that the `android-ndk-arm64` job is the only gate compiling it.
- **`native_app_glue` + `-u ANativeActivity_onCreate` replaced the Slice-2 `-Wl,-z,undefs` placeholder** — Slice 2 linked the empty `.so` with `-Wl,-z,undefs` and a `TODO(Slice-3)`. Slice 3b drops it: `MOBILE_SOURCES` now globs the real host shell, `native_app_glue` is built as a STATIC lib (PUBLIC include dir), and the entry symbol is force-kept with `target_link_options(SmatchetMobile PRIVATE -u ANativeActivity_onCreate)` so the linker doesn't GC the glue's `ANativeActivity_onCreate`.
- **#13 density re-asserted across `ApplyStyle` rebuilds (`SmatchetTheme.cpp`)** — Slice 3a's `ApplyUiDensityScale` set the scale once at boot, but `ApplyStyle` (which `drawApplyAppearanceSettings` fires on frame 1 post-Load) opens with `style = ImGuiStyle{}` and wipes it. Inert on desktop (scale stays 1.0).
- **#15 realized as a non-`_WIN32` amber `TextWrapped` in `DrawTrackerBackendConfig`** — plan said "on-screen warning"; concrete form is an amber wrapped note ("token is stored unencrypted … use a scoped, revocable token") gated `#if !defined(_WIN32)` so only the platforms with plaintext passthrough (Android included) show it; desktop Windows (DPAPI) never does.
