- 2026-05-20 · orchestrator · [process] · P2 — ADR 0006 hole: merge-gates poller on draft PR never gets a real CodeRabbit signal
  Details: ADR 0006 (PR #326) reverts #319 and re-establishes "orchestrator opens `gh pr create --draft`, merge-gates poller flips ready on pass". But CodeRabbit's `auto_review.drafts: false` config (the same setting that motivated #319 in the first place) means CR will never review a draft PR. The poller's CR-installed grace-window logic (#320, `MERGE_GATES_CR_GRACE_POLLS=10`) then ALWAYS fires for draft PRs — gate sits at `NONE+pending` for 10 polls (~10 min default), logs the `WARN: CodeRabbit grace window ... expired` line, and falls through to pass with no actual CR review. Net effect under the contract-as-written: every orchestrator PR with `MERGE_GATES_AUTO_MERGE` waits 10 min and merges without any CR review. The CR gate is structurally bypassed even though `.coderabbit.yaml` is checked in. PR #326 happened to escape this (PR showed `isDraft: false` on read despite the `--draft` flag at create time; root cause not yet diagnosed) so the gate hit the normal review path, but the contract hole is real for the next orchestrator PR that lands as actually-draft.
  Concrete next action: amend ADR 0006 + `scripts/dev/merge-gates.sh` to close the hole. Two viable shapes — (a) **flip-ready-on-poll-start**: when the poller starts AND `MERGE_GATES_AUTO_MERGE` is set AND CR is installed AND `isDraft: true`, call `gh pr ready <pr>` as the first action of poll 1 so CR can fire immediately. Trade-off: PR shows ready before the gate has actually run; reviewer-UX signal is the wrong way around for the brief window between poll-start and gate-pass. (b) **gate-pass-via-ready-flip**: keep poller on draft PR, but the grace-expired fall-through path performs `gh pr ready` THEN re-polls one more time (post-flip CR has a chance to fire); only fall through to pass after a second grace window. Trade-off: doubles the worst-case wait to ~20 min but preserves draft-as-WIP until the gate is satisfied. (c) **abandon ADR 0006**: revert this revert and re-accept #319's "open ready when user authorised auto-merge" logic — the simplest fix; surfaces the same trade-off discussion again. Suggest (a) since the structural bypass under the current contract is worse than a brief reviewer-UX glitch. - 2026-05-20 · orchestrator · [process] · P3 — Default to `git merge` not `git rebase` for squash-merge-destined PR branches
  Details: PR #313's feature branch was 1 commit behind `origin/develop` (PR #312 added the pure-docs-skip block to AGENTS.md while #313 was open). `git rebase origin/develop` started replaying the 10-commit feature history one-by-one and immediately hit a `modify/delete` conflict on `Source_Core/src/AiChatTextEditorRender.cpp` (slice 1 of #311 modified the file; slice 5 of #311 deleted it; develop's merge of #311 then saw the deletion). For branches destined for squash-merge (the standard Smatchet pattern), `merge` is strictly cheaper.
  Concrete next action: extend AGENTS.md § Project rules with a **"Catch-up sync for PR feature branches"** sub-rule: "When `origin/develop` advances while a feature branch is open + the branch needs to sync (e.g. CI says `CONFLICTING`, or before opening the PR), default to `git merge origin/develop --no-edit` rather than `git rebase origin/develop`. Squash-merge will collapse the merge commit; the only saving from rebase is a linear local history, which is moot post-squash. The rebase form's per-commit conflict replay is strictly more work than the merge form's single resolution. Use rebase only when (a) the branch is destined for a non-squash merge, OR (b) the per-commit history is being preserved for some other reason (rare in Smatchet today)."
