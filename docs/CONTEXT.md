## Tracker interface

The agentic-flow (triage + handoff) C++ runtime was removed by v1 PR1 of [`plans/shipped/github-tracker-backend.md`](plans/shipped/github-tracker-backend.md) (`b1d241bc`, 2026-05-21). Glossary entries for `AgentProposal` / `ImplementIssue` / `Triage half` / `Handoff half` / `Coding harness runner` / `Sentinel files` / `Handoff envelope` / `HarnessRunState` / `PR iteration budget` were retired with that ripout. The future `smatchet-merge-watcher` host daemon ([`plans/shipped/smatchet-merge-watcher.md`](plans/shipped/smatchet-merge-watcher.md)) revives a slim subset of these ideas in a different shape — concepts there get their own glossary entries when the watcher Phase-1 ships.

Two terms survive because v1 PR2's tracker rewrite uses them:

- **`UpdateField` semantics — set-replace** — the `ITrackerIssueMutations::UpdateField(issueId, field, values)` contract (returns `TrackerError` since #21b Slice 4) is **set-replace** for multi-value fields (labels, assignees, components): `values` is the **intended full set** after the edit, not a delta. Jira / Plane / Linear native APIs are set-replace (Linear's `issueUpdate` takes the full `labelIds` array); the virtual reflects them. GitHub's native API is additive (per-name add / remove); `GitHubClient::UpdateField` reconciles internally — it pre-fetches the current set, computes a diff via `smatchet::github::ComputeLabelEditDiff` (`Source/Core/include/Tracker/LabelEditDiffPure.h`), then issues add / remove calls per element. The pre-fetch HTTP cost lives inside GitHub's impl; callers see one virtual call.
- **TrackerIssueKey** — canonical issue identifier carried across `ITrackerBackend` virtuals. Per-backend shape: GitHub `owner/repo#N` (parsed via `smatchet::github::ParseGitHubIssueKey` in `Source/Core/include/Tracker/GitHubClientHelpers.h`); Jira `PROJ-N` (uppercase project + numeric); Plane `<issue-uuid>` (workspace + project + UUID resolved by the client); Linear `TEAM-N` (Linear's `Issue.identifier` — a team key starting with an ASCII letter plus a positive integer, e.g. `ENG-42`; parsed via `smatchet::linear::ParseLinearIssueKey` in `Source/Core/include/Tracker/LinearClientHelpers.h`, whose `TeamKey` doubles as the draft scope since Linear's draft scope is the Team, not the `project` issue field). Callers treat the string as opaque between fetch + write; only the backend impl parses it. Cross-backend dispatch relies on the per-backend `GetTrackerType()` to pick the right parser before any URL composition.

## Plan locks

Four lock-related terms appear across `docs/plans/shipped/git-ref-plan-locks.md`, `AGENTS.md` § Orchestrator delegation packet, and the `agents/scripts/core/lock-*.sh` helpers. They are **role-distinct**, not synonyms — feedback that flagged them as inconsistent was conflating function with naming.

- **Plan-lock** — the **object**. A claim on a planned write set held in `refs/locks/<slug>` on origin. One ref per active slice. Surfaced in `docs/plans/active/_plan-locks.generated.md` (auto-regenerated by `.github/workflows/locks-render.yml`). Released automatically on PR merge via the `lock-slug:` line in the PR body + `.github/workflows/lock-cleanup.yml`. Authoritative source for "what writes are in flight right now".
- **Lock-slug** — the **identifier field**. Kebab-case slug matching the slice / feature name (e.g. `agent-contract-alignment`). Used as the ref-name suffix (`refs/locks/<slug>`), as the script argument to `lock-claim.sh` / `lock-claim-update.sh` / `lock-release.sh`, and as the line key in PR bodies (`lock-slug: <slug>`). One slug per plan-lock.
- **Lock-claim** — the **action** of acquiring a plan-lock, **and** the script that performs it (`agents/scripts/core/lock-claim.sh <slug> <write-set-file>`). Reads `AGENT_ID` / `LOCK_BRANCH` / `LOCK_PLAN` / `LOCK_NOTES` from env, packages them into a `claim.json` blob, and pushes the lock ref. Failure mode: ref-update conflict if another agent claimed the same slug since the last `locks-show.sh` call.
- **Holds-lock** — the **predicate**. "Agent X holds-lock Y" = the plan-lock with slug Y has `claim.json` `owner=X`. Surfaced by `bash agents/scripts/core/locks-show.sh` (table form) or the rendered `docs/plans/active/_plan-locks.generated.md` (markdown form). Used in orchestrator delegation packets to refuse delegation that overlaps an active claim.

The four roles do not overlap: a `plan-lock` is the object; `lock-slug` is its identifier; `lock-claim` is the action that brings one into being; `holds-lock` is the predicate that names its current owner. Cross-link: full operational rules live in [`docs/plans/shipped/git-ref-plan-locks.md`](plans/shipped/git-ref-plan-locks.md) § Terminology.

## Quality Pillars

Five north-star quality invariants documented in [`AGENTS.md`](../AGENTS.md) § Quality Pillars, in two sub-groups: **UX Pillars** (1-4, user-facing) + **Engineering Pillars** (5: DRY, code-maintainability). UX 1-3 + Engineering 5 are **agent-enforced** (orchestrator + code-review agent + `merge-gates.sh` + per-pillar specialist agents; DRY is a blocking delta-gate, graduated from WARN-first 2026-06-21 per ADR-0015); GitHub-side enforcement of each pillar is partial today (see § Enforcement matrix below). Pillar 4 (Accessibility) is aspirational.

### Enforcement matrix (current state)

| Pillar | Agent enforcement | GitHub required-status-check | Target |
|---|---|---|---|
| 1 — Performance | `perf-detective` + `perf-gatekeeper` + `merge-gates.sh` reads `.github/workflows/perf-pr-fast.yml` artifact | NOT required on `develop` branch protection | Promote `Perf PR-fast (windows-2022)` to required after baseline coverage hits all 15 scenarios |
| 2 — UI never freezes | `code-review` CRITICAL on sync I/O reaching UI thread; `pillar2-scan.sh` static check | NOT required on `develop` | Promote `Pillar 2 scanner` to required after the script is wired into a workflow |
| 3 — Never crash | `debug-detective` runs ASan / UBSan on suspect investigations; RAII rule enforced by code-review | Build-only required (3 MSVC variants); sanitizer build NOT required | Promote sanitizer preset to a required CI job |
| 4 — Accessibility | None (aspirational) | None | None |

Cross-link: [`docs/plans/shipped/gate-enforcement-hardening.md`](plans/shipped/gate-enforcement-hardening.md) drives the agent-enforcement → GitHub-enforcement promotion sequence.


- **Frame budget** — **6.94 ms** per UI-thread frame, derived from `1000 / 144`. Steady-state mean per-frame work above the budget is a Pillar-1 violation; `perf-detective` regression-fails any commit that lifts the mean. Floor: no single frame > **10.0 ms** (100 Hz) in normal operation; outliers above the floor are tracked at p99 by `spike-hunter`.
- **Pillar 1 — Performance** — sustain ≈ 144 Hz. Enforced via `perf.reset` → `scenario.run` → `perf.snapshot` loop in `docs/guides/perf-workflow.md`. Owner agent: `perf-detective` for sustained load; `spike-hunter` for intermittent stalls.
- **Pillar 2 — UI never freezes** — any op estimated > 100 ms moves to a worker thread; if a UI-thread block is genuinely unavoidable, a visual cue (spinner / progress widget) must appear within 100 ms. Synchronous I/O (HTTP, SQLite, p4, filesystem, blocking lock) reaching the UI thread = `code-review` CRITICAL. Worker → UI handoff goes through `MainThreadDispatcher` (`Source/Core/include/MainThreadDispatcher.h`); never touch ImGui state from a worker.
- **Pillar 3 — Never crash** — RAII enforced (no raw `new` / `delete`), bounds-checked (`.at()` / explicit length checks), no silent UB (nullptr deref / unsigned wrap-around / use-after-free are merge-blocking). Ship builds degrade gracefully — assertions in dev become `LOG_ERROR` + safe default returns in ship; the app never aborts on a recoverable bad state. `debug-detective` runs the ASan / UBSan sanitizer build (`cmake --build --preset ninja-test-msvc`) for every crash-suspect investigation.
- **Pillar 4 — Accessibility (aspirational)** — locked in-scope: keyboard navigation, font-size / zoom via `ImGuiIO::FontGlobalScale`, WCAG AA contrast (4.5:1 body, 3:1 large). No enforcement gates today — flagged in `docs/self-improvement/AGENT_SELF_IMPROVEMENT.md` (category `process`) until the supporting infra lands.

## Source control (dual-VCS)

Terms introduced by the Perforce opt-in layer ([`docs/plans/shipped/git-to-perforce-migration.md`](plans/shipped/git-to-perforce-migration.md) Phases 2–6). git/GitHub stays the canonical ship-line; these names cover only the p4-side primitives Smatchet uses for agentic-WIP work.

> **Forward-reference note**: the `scripts/dev/p4-task-stream*.sh` paths cited below are owned by PRs #380 (allocator + GC) and #382 (submit-to-PR bridge); they land on `develop` when those PRs merge. Until then, references resolve at the PR branch but not at `develop` HEAD. This is intentional — Phase 6's glossary docs ship alongside the agent-wiring rules they describe, regardless of merge order.

- **Task stream** — a Perforce stream of type `task` parented to `//smatchet/main`. Single-segment depot path (`//smatchet/task-<agent-id>`) because the depot has `StreamDepth: //smatchet/1`. Lazy-branched: holds zero revs until `p4 populate` seeds it from parent. Allocated by `bash agents/scripts/project/p4-task-stream.sh <agent-id>` as the p4 sibling of `git worktree add .claude/worktrees/<id>`. GC'd by `bash agents/scripts/project/p4-task-stream-gc.sh` once stale (default 14 d, refuses to purge while pending CLs exist).
- **Shelf** (verb: **shelve**) — a server-side stash of changes against a pending CL via `p4 shelve -c <cl>`. Visible to every client on the same server; survives the originating client's disconnect. Contrast with `git stash`, which is local-only. Smatchet uses shelves for cross-machine WIP handoff; routine WIP can stay in git stashes.
- **Pending CL** — a Perforce changelist that's been opened (`p4 edit` / `p4 add` / `p4 integrate`) but not yet `p4 submit`ted. Survives client disconnect. Numbered (`@6`) or `default` (the implicit one). The `agents/scripts/project/p4-task-stream-to-pr.sh` bridge refuses to start when the canonical client has pending CLs (leftover from a prior failed run) — auto-reverting would silently discard work that might be unrelated to the current invocation.
- **p4 counter** — a server-side typed key/value pair (string-valued, integer-incrementable via `p4 counter -i`). Smatchet uses counters as the storage layer for the Phase 4 plan-lock backend: `smatchet_lock_<slug>` holds state (`0` / `1`) via the `--from=<old> --to=<new>` compare-and-swap; `smatchet_lock_<slug>_meta` holds the JSON claim record. CAS detail: `p4 counter` treats "non-existent" as distinct from "value 0" — first-ever claim needs a one-shot `p4 counter <name> 0` bootstrap step before the CAS will fire. Race-safe (concurrent bootstraps both set to 0; only one subsequent CAS 0→1 wins).
- **+l filetype modifier** — Perforce filetype attribute on a file open (`p4 edit -t +l <file>`) that marks the file as exclusively locked by the opening client. Other clients attempting `p4 edit` on the same file get `file - already locked by <user>@<client>` and refuse to open. Lock releases on `p4 submit` (edit lands) or `p4 revert` (edit abandoned); persists across client disconnect. Surfaces as `*exclusive*` in `p4 opened -a` output (NOT `*locked*` — that's for deliberate `p4 lock` actions, a different mechanism).
- **Dual-VCS reconciliation** — the rule that `git status --porcelain` and `p4 reconcile -n //smatchet/main/...` must always agree on what's modified in the canonical workspace. The `text+w` typemap rule (every text file always-writable) is load-bearing for this — without it, p4 sets Windows `ReadOnly` post-submit and the next git-only `Edit` fails with `EPERM`. Discovered during Phase 1 baseline import; encoded in [`docs/perforce/SETUP.md`](perforce/SETUP.md) § 5.

## Performance monitoring

Vocabulary for the perf workflow. See [`docs/guides/perf-workflow.md`](guides/perf-workflow.md) for the operational ladder.

- **Steady-state mean** — average per-frame UI-thread work over a representative scenario run, reported by `perf.snapshot`. The Pillar-1 enforcement metric.
- **p99 / outlier** — 99th-percentile per-frame work. Pillar-2 spikes — frames > 100 ms — are tracked here. `spike-hunter` regression-fails any commit that introduces a new p99 > 10.0 ms on a previously-clean scenario.
- **Sustained load** — perf measured over N frames of a repetitive scenario (e.g. `priority-grid-scroll`); contrast with **spike** (single-frame outlier). Different agents own each: `perf-detective` for sustained; `spike-hunter` for spikes.
- **`SMATCHET_UI_PERF_SCOPE`** — RAII macro from `Source/Core/include/UiPerfMonitor.h` that records a scoped block's wall-clock under a string-literal name. Overhead ~200-500 ns per call (two `steady_clock::now()` + mutex lock + linear scan). Markers prefixed `perf_temp:` are stripped between perf rounds; permanent markers stay.
- **`perf.snapshot`** — CLI command that returns top-N rows by `lastTotalMs` from `UiPerfMonitor`. Standard loop: `perf.reset` → `scenario.run` → `perf.snapshot`. Run by `perf-measure` against a named scenario.
- **Scenario** — a registered repro under `Source/Core/src/Commands/Scenarios/` that drives the app for a fixed number of frames or until a state condition. Deterministic (no live HTTP). Examples: `priority-grid-scroll`, `lua-recorder-fuzz`, `ui-test`. Adding a scenario is the canonical fix when `perf-measure` reports a `cli-gap` halt.

## Concurrency & lifetime

Vocabulary for off-UI-thread work and the object-lifetime rules that keep it crash-safe (Pillar 3).

- **Background task pool** — `AppController::LaunchBackgroundTask` + `JoinBackgroundTasks` (both in `Source/Core/src/AppController.cpp`). The joined fire-and-forget worker mechanism: each task runs on a `std::thread` appended to `backgroundWorkers_` and is **joined at shutdown** (before `~AppController` tears down app state). UI hand-back goes through `MainThreadDispatcher::PostToMainThread` — never touch ImGui state from a worker. This is the canonical replacement for raw `std::thread(...).detach()`, which is forbidden first-party-wide by the `no-detach` lint rule. Because the pool joins **only at shutdown**, a worker that must survive a *live* resource swap (e.g. the tracker backend changing) cannot rely on the join alone — it must additionally hold a `shared_ptr` to that resource (see *Active tracker backend* + ADR 0012).
- **Active tracker backend** — the live `std::shared_ptr<ITrackerBackend> AppController::Backend`, built once in `Initialize` and **reassigned live** on a tracker switch (`TicketSyncService::SyncWithBackend` → `SetBackend`). Shared-owned (not `unique_ptr`) specifically so an in-flight background worker that captured a `shared_ptr` copy keeps the *old* backend alive until it finishes, even though a Jira→Plane switch has already swapped `Backend` to the new object. Rationale + rejected alternatives: [`docs/adr/0012-shared-ownership-active-tracker-backend.md`](adr/0012-shared-ownership-active-tracker-backend.md). Worker-spawning UI gets the strong reference via `AppController::BackendShared()`.

## Plugin architecture

Optional Smatchet plugins gated by compile-time flags. See `Source/Plugins/` directory + `AGENTS.md` § Optional plugins.

- **MCP server** — JSON-RPC HTTP server in `Source/Plugins/Mcp/` (gated `SMATCHET_WITH_MCP=1`, Standalone only). Exposes commands from `CommandRegistry` as MCP tools — define a command once, surface everywhere. Lifecycle managed by `SmatchetMcpServerUi` (UI) + `McpServerStatus` (model).
- **Lua automation host** — sandboxed Lua 5.3 + sol2 binding layer (gated `SMATCHET_WITH_LUA_AUTOMATION=1`). Bindings in `AppController_LuaBindings.cpp`; mirror stubs in `AppController_LuaStubs.cpp` (built when flag is OFF). Sandbox enforces `lua_sethook` instruction-count timeout; per-call marshalling cost ~50-60× C++ — don't expose bindings on per-cell hot paths.
- **`SMATCHET_WITH_*` gates** — compile-time `#if` guards for optional features (`SMATCHET_WITH_MCP`, `SMATCHET_WITH_LUA_AUTOMATION`, `SMATCHET_WITH_AI`, `SMATCHET_WITH_WHISPER`). Stub-side TUs (e.g. `AppController_LuaStubs.cpp`, MCP stub shims) must compile cleanly when the flag is OFF — DX12 in particular often has flags OFF. The `SMATCHET_WITH_AGENTIC` gate was retired by v1 PR1 of `plans/shipped/github-tracker-backend.md` (`b1d241bc`).
- **Light feature profile** — the shared release/embed compile profile: Lua automation + command palette + unified `CommandRegistry` ON; MCP, AI implementation, and Whisper OFF. Encoded as hidden CMake preset `_smatchet-light-features`; consumed by `ninja-publish-light-msvc` (standalone) and `ninja-iter-unreal-msvc` (DX12 package). The palette lists **only commands for enabled features** — no stub entries for disabled MCP/AI/Whisper (grill Q3). Light standalone keeps full **`cmd` CLI** via in-process dispatch (grill Q1 revision, 2026-05-24).
- **Standalone CLI in-process mode** — when `SMATCHET_WITH_MCP=OFF`, `Smatchet-Light.exe cmd …` uses ephemeral-style hidden boot (GLFW + GL + `AppController::Initialize`), then `CommandRegistry::Dispatch`. Meta cmds skip the render loop; `scenario.run` spins until complete (grill Q8). JSON stdout + same exit codes as attach mode.
- **Static plugin** — Smatchet plugins are static-linked at build time via `PluginHost`, not runtime-loaded DSOs. No `dlopen` / `LoadLibrary` paths.
- **sol2 bindings** — C++ ↔ Lua glue. `state.new_usertype<T>(name, ...)` takes name + alternating method-name + member-ptr pairs (no `sol::no_constructor` sentinel). Use `sol::optional<T>` for nullable args, `sol::protected_function` for callback storage. `decode_json` can leak a C++ `parse_error` past the protected call on malformed input — wrap defensively on untrusted strings.

## Test taxonomy

Five testing buckets per `AGENTS.md` § Verification automation + `agents/core/test-author.md`. Every plan's `## Verification` step must classify into one bucket. Manual residue must come with a deferred-automation entry.

- **Bucket A — CLI / unit** — pure-logic doctest cases under `tests/Core/<Unit>.test.cpp`, or bash assertions over `Smatchet.exe cmd <name>` output. Fast, deterministic, the canonical home for parsers / classifiers / pure helpers. Owner agent: `test-rig`.
- **Bucket B — Scenario** — `scenario.run --name=<scenario>` exercises a registered scenario class from `Source/Core/src/Commands/Scenarios/`. Asserts on `perf.snapshot` rows, log output, or screenshot capture. Deterministic, no live HTTP.
- **Bucket C — Screenshot diff** — `ImGui::Render` capture compared against a golden PNG via stb_image_write. L∞ diff tolerance ≤ 4. Used for dock-gap detection (pink-clear scan) + theme color verification. Requires a GL context on the runner — bucket-C gates are dev-machine-only today (CI runners headless).
- **Bucket D — Sanitizer** — ASan / UBSan / TSan / MSan build via `ninja-test-msvc` + sanitizer-specific presets. Required on any `Source/Core/` C++ PR per Pillar 3.
- **Bucket E — ImGui Test Engine** — bucket-E tests under `tests/ui/*.test.cpp` drive ImGui interactions programmatically (drag, hover, focus, type). Spawn-mode requires a GL context; same headless-CI limitation as bucket-C. Wired but not all surfaces covered — manual residue without a bucket-E entry is a `test-author` failure.
- **Fixture** — a reusable setup harness under `tests/support/` (e.g. `FakeOfflineQueueDeps`, `LuaHostFixture`, `GoldenImage`). Tests link the fixtures they need; production-side adapters (e.g. `AppControllerDepsAdapter.cpp`) are deliberately NOT linkable into tests — they drag unresolved `AppController::*` symbols.
- **Golden image** — PNG under `tests/golden/` captured by bucket-C scenario via stb_image_write. Re-bootstrap via `bash scripts/dev/test-screenshot-diff.sh --bootstrap` whenever the theme / layout deliberately changes.

## Harness concepts

Terminology for agentic-harness wiring — see [`docs/harness/SETUP.md`](harness/SETUP.md) + `AGENTS.md` § Harness adapter for the operational shape.

- **Harness adapter** — per-harness directory (`.claude/`, `.codex/`, `.cursor/`) gitignored at the repo root, regenerated locally from canonical `agents/` tree via `bash agents/scripts/core/setup-harness.sh <name>`. Edits to `agents/*.md` propagate immediately via directory junctions / symlinks (file-level on Windows often falls back to copy — see SETUP.md § Worktree base for the known stale-HEAD pitfall and `link_file` short-circuit caveat).
- **Worktree** — git worktree under `.claude/worktrees/<id>/`, typically Claude Code SDK-spawned `claude/<id>` worktrees. The SDK-spawned path bases on parent repo's current local HEAD — pre-session `git switch develop && git pull --ff-only` keeps it on develop. The `agent/<proposalId>/<short-slug>` shape from the deleted `ClaudeCodeLocalRunner` is gone (per v1 PR1 of `plans/shipped/github-tracker-backend.md`).
- **Semantic codebase search** — navigate by meaning before raw `Grep` / `Glob`, per AGENTS.md § Semantic codebase search. Harness-specific concrete tools (Claude Code: vexp `run_pipeline` (primary) → `Grep`; see `.claude/CLAUDE.md`); other harnesses substitute their equivalent via the capability table in AGENTS.md § Harness adapter. (The Sourcetrail `st_query.py` rung is retired — upstream discontinued, no symbol DB in fresh checkouts.)
- **Capability tag** — a closed-set role declared in an agent's frontmatter `capabilities:` list (`semantic-code-search`, `file-skeleton`, `file-read`, `file-edit`, `text-search`, `file-glob`, `shell`, `web-fetch`, `git-history`). Maps per-harness to concrete tools via the AGENTS.md § Harness adapter table.
- **Telemetry hook** — `agents/_shared/token-tracking/agent-token-log.py` (canonical) + `.claude/hooks/agent-token-log.py` (Claude Code runtime copy). Appends one JSONL line per subagent call to `.claude/.agent-tokens.jsonl` with token usage + tool count + `## Outcome:` classification. The classifier (`_infer_outcome`) reads the explicit tag, falls back to halt-keyword detection, defaults to `partial` (was `applied` before the contract-alignment tightening — see `docs/plans/shipped/agent-contract-alignment.md`).

## Autonomous debugging

Terminology for the end-state credential-free + user-input-free debug loop — see [`docs/plans/shipped/autonomous-debugging-no-creds.md`](plans/shipped/autonomous-debugging-no-creds.md) for the multi-slice plan that delivers it.

- **Autonomous debug loop** — the end-state where a bug surfacing with a *concrete enough description to reproduce* (see *Concreteness check*) is diagnosed end-to-end by `agents/core/debug-detective.md` without live credentials or user input during the loop. The loop's entry points are CI failures (sanitizer, perf regression, golden-image diff), orchestrator-discovered in-session failures, external bug reports, and `coderabbit-triage`-routed PR findings. The loop's exit is a fix handed to the matching subsystem specialist. **At most one user-input point** — the slice-10 phase-0 threshold-check, fired only when the bug description is under-specified.
- **Concreteness check** (phase 0) — debug-detective's threshold-check before any other phase. Classifies the incoming bug description by whether it names (a) the breaking surface (component / scenario / file), (b) an observable failure (assertion, log line, sanitizer report, screenshot diff, perf delta, or user-described symptom with file:line), and (c) the input shape (CLI args, scenario name, fixture path, or a registered bucket-E action). If any of the three is missing, the agent emits exactly one `AskUserQuestion` at this phase; once concrete, phases 1+ never ask again.
- **Reproducer-first contract** — debug-detective's hard refusal of "user opens X and observes Y" bug descriptions inside the debug loop. If no deterministic reproducer (CLI command / `scenario.run --name=<x>` / Lua snippet / failing-doctest name / registered bucket-E action) is supplied or discoverable, the agent's first action is to **add a scenario** (see *Bug-class*) that reproduces the bug — on the same branch as the fix. The contract is verified by a `agents/scripts/core/test-agent-contract.sh` literal-grep check on `agents/core/debug-detective.md`.
- **Bug-class** — the smallest grouping that shares an injection point (which `ITrackerBackend` / `IAiClient` / UI panel) + a render path (which scenario's `OnFinish` rows[] would have caught the regression). debug-detective phase 0.5 (existing-scenario reuse) searches `Source/Core/src/Commands/Scenarios/` for an existing scenario that covers the incoming bug's class; when found, the existing scenario is *parametrized* (new CLI arg / fixture variant / new sub-case in `OnTick`) rather than forked into a near-duplicate. Forking is allowed only when the existing scenario's render path is genuinely orthogonal.
- **Live-process evidence** — evidence obtained by observing a Smatchet process that is already running, over the command surface: log read-back (`debug.log_tail`), an on-demand self-minidump (`debug.dump_self`), `perf.snapshot`. Distinct from *reproduction* evidence (re-running a scenario forward) and *post-mortem* evidence (a crash dump, a sanitizer report), and the only tier that reaches a process which has **wedged without crashing** — see [`docs/plans/autonomous-debug-live-evidence.md`](plans/autonomous-debug-live-evidence.md). Only commands that do **not** marshal to the UI thread qualify during a hang; the marshalling ones (`debug.dock.dump`, `debug.dock.reset`, `debug.window.resize`, `debug.window.screenshot`, `debug.grid.edit-burst`) block forever, because `RunOnUiThreadAsCommandResult` has no timeout.
- **Orphan-scenario** — a registered scenario where **all three** hold: (i) no PR has cited the scenario name in the last 60 days (`git log --grep=<name> --since=60.days.ago` returns zero), (ii) it's not named in any curated set (`scripts/dev/perf-pr-fast-set.json`, `agents/core/perf-gatekeeper.md` § Curated diff → scenario map, `tests/golden/` filenames), (iii) no failing test references it (`grep -r <name> tests/` returns zero). `agents/core/git-janitor.md` end-of-session sweep step 10.5 surfaces orphan candidates via `AskUserQuestion` with options [keep / archive to `docs/reference/<name>.md` / delete `.cpp` + registry line]. Default = keep (orphan detection is advisory).

## Agent layer

Terminology for the agent-surface extraction (plan: [`docs/plans/agent-surface-extraction-repo.md`](plans/agent-surface-extraction-repo.md); decision: [`docs/adr/0025-agent-surface-extraction-submodule.md`](adr/0025-agent-surface-extraction-submodule.md)).

- **Agent layer** — the portable agentic surface as a concept: agents, agent-rules docs, harness adapters, the self-improvement *framework*, the generic gate scripts, and `AGENTS.md`'s structure. Distinct from the project-specific content that consumes it (plans, backlog entries, glossary, ADRs, subsystem agents' subject matter). The portable/project boundary itself is defined in [`docs/STRUCTURE.md`](STRUCTURE.md) § The boundary.
- **Layer repo** — the standalone repository (`the-unwilling-agentic-bunch`) that holds the agent layer once extracted. It has its own CI, review gates, and `project.config.json`; Smatchet consumes it rather than containing it.
- **Host** — a project that consumes the layer repo (Smatchet is the first). The host owns everything project-specific — source tree, plans, backlog, self-improvement *entries* — and mounts the layer at a fixed directory (`agent-layer/`).
- **Pointer bump** — a host-side commit that advances the mounted layer to a newer layer-repo revision. The bump is the only way layer changes reach a host; until it lands, the host keeps running the older layer.
