# Preferences taxonomy lives in a static descriptor table, not in self-registering draw call-sites

**Status:** accepted (2026-08-04)

**Plan:** [`docs/plans/preferences-ia-resegmentation-and-search.md`](../plans/preferences-ia-resegmentation-and-search.md) (tier-less ref) · **Relates to:** Quality Pillar 5 (DRY, [ADR-0015](0015-dry-quality-pillar-duplication-gate.md)), the `unused-symbol-under-config-guard` WARN rule (root `AGENTS.md` § Enforcement contract-card).

The Preferences window has no settings registry: every label, clamp, and config binding is hardcoded inline in its `Draw*` function across 7 TUs, so nothing can enumerate "all settings" — which is why search exists only inside the Keyboard Shortcuts tab and why the tab taxonomy has drifted (update settings under Appearance, Perforce paths under Annotate). Re-segmenting the window into 8 categories / ~22 sections **and** filtering live widgets in place across all of them both need one enumerable list of settings. We put that list in a **static descriptor table** (`PreferencesSchema.{h,cpp}` — `PrefsCategoryDesc` / `PrefsSectionDesc` / `PrefsSettingDesc`, data only, no ImGui include) that is a *second* source of truth alongside the draw code, and we pay for the duplication with an automated **drift guard** (a bucket-E test asserting the set of ids passed to `ShowSetting` during a full walk equals the descriptor set).

The non-obvious part — and the reason this is an ADR rather than a routine data-table refactor — is that a future reader will see ~80 setting ids written down twice (once in the table, once at the call site) plus a test whose only job is to prove the two agree, and reasonably ask why the draw code doesn't just register itself. It can't, and the reason is not obvious from either file.

## Considered options

- **Self-registration at draw time** (`if (st.Filter.Setting("id", "Enable vsync", "display screen")) { ImGui::Checkbox(...); }` — the call site is the only source of truth). *Rejected.* Drift becomes structurally impossible and the feature-gate skew problem vanishes (one `#if` guards both the row and the widget), but the index only knows what has been **drawn**, and exactly one category draws per frame. Cold-start search would return nothing outside the currently-open category — which defeats the user request that motivated the work ("search should work on all tabs"). This is unmitigable rather than merely expensive.
- **Self-registration + an invisible warm-up pass** over all 8 categories on first open (zero-alpha or `BeginDisabled` draw to populate the index). *Rejected.* It runs every widget's side-effect code once per session — the Whisper and MCP sections drive live device/server state, and several sections own `static` frame-local state — to buy an index we can have for free from a table. Strictly worse than the duplication it avoids.
- **Table for ids only, with a debug-build `assert` at each call site instead of the bucket-E guard.** *Rejected as the primary guard, kept as a complement.* An assert fires only on a code path someone actually executes in a debug build; the failure mode we care about is a setting nobody navigates to and therefore nobody can find by search — precisely the path an assert never reaches. The bucket-E walk covers all 8 categories deterministically in CI. A debug assert may be added as a cheap early-warning, but it does not replace the guard.

## Consequences

- **The drift guard is load-bearing, not optional.** Without it the table rots silently and the failure is invisible (a setting that draws fine but cannot be found by search, or a table row pointing at a widget that no longer exists). It must not be weakened to a smoke test, and a red drift guard is a real break, not flake.
- **`ShowSetting` on an unknown id returns `true` (fail-open).** A typo'd or missing id shows the setting rather than hiding it forever — an unfindable setting is worse than an unfilterable one. The guard, not the runtime, is what catches the typo.
- **Feature-gated rows must carry the same `#if` as their widget.** MCP / Assistant / Whisper descriptor rows sit inside `SMATCHET_WITH_MCP` / `_AI` / `_WHISPER`; a row compiled in while its widget is gated out fails the drift guard **only in the feature-OFF build**, which is why that configuration is an explicit verification step. This is the failure class the `unused-symbol-under-config-guard` WARN rule watches.
- **Granularity is per *value*, not per widget** — the list editors (`DurationSuggestions`, the three template lists, `PathRemaps`, `MobileNavPages`, `recentProjects`) get one descriptor for the whole editor; their per-row `InputText`s are deliberately not individually filterable. Changing this later is cheap (add rows); it is called out so nobody reads the coarse rows as an oversight.
- **Re-parenting a section becomes a one-field edit** (`PrefsSectionDesc::CategoryId`) rather than moving code between `BeginTabItem` blocks. This is what makes the plan's 2a/2b slice split cheap, and it is the payoff that justifies the duplication.
- **Save semantics move onto the section descriptor** (`SaveSemantics`), because the per-tab footer switch cannot survive a category holding two save paths (the new Connections category mixes `MarkPrefsDirty` with Annotate's detached `PersistAnnotateCfg`).
