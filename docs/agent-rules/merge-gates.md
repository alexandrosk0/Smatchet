Before the orchestrator, `git-janitor`, OR `smatchet-merge-watcher` (the host daemon per [`docs/plans/shipped/smatchet-merge-watcher.md`](../plans/shipped/smatchet-merge-watcher.md)) squash-merges a PR, it polls three conditions via one `gh api graphql` call (`agents/scripts/core/merge-gates.graphql`):

1. **CI** — every required check (`isRequired(pullRequestNumber: $pr) == true`) on `pullRequest.commits(last:1).commit.statusCheckRollup.contexts` must reach a passing terminal state.
   - **CheckRun**: pass = `status == "COMPLETED"` AND `conclusion in {SUCCESS, NEUTRAL, SKIPPED, STALE}`. Block = `conclusion in {FAILURE, TIMED_OUT, CANCELLED, ACTION_REQUIRED, STARTUP_FAILURE}`. Any non-COMPLETED status counts as pending.
   - **StatusContext**: default rule — any required context with `state != "SUCCESS"` blocks. `FAILURE` / `ERROR` fail; `PENDING` / `EXPECTED` pending.
   - **Block-on-any-red (all-gates-blocking flip)**: non-required checks block **exactly like required ones** — `MERGE_GATES_BLOCK_ALLOWLIST_RE` is `"."` (matches every name), so `$failing`/`$blocking` cover ALL contexts, red **or still-pending**. The single exemption: a check whose name contains `advisory` (case-insensitive) — the sanctioned, name-visible convention for a deliberately non-gating lane; **no production lane carries the token** (the flip's rename sweep removed it everywhere). History: the scope started as a curated allow-list added after the #923 gate-escape (watcher auto-merged past a red non-required `Coverage`; see `postmortems.md` 2026-06-06 "#923") and grew one escape class at a time (`Perf PR-fast` 06-07, `Android security gate` 06-09, `Fuzz smoke` 06-16/#1301, `Bucket launch-smoke` 06-18, `Intent section`, `Plan-lock gate`) until the flip retired the curation — the next #923-class escape is impossible by construction. Four **step-level** masks survive inside otherwise-blocking checks by design (each documented at its step; every lane's broken-harness teeth still red the check): fuzz-smoke's stochastic fuzz step (#1301 — the deterministic build/ctest still reds the check), bucket-C's per-scenario golden-diff step (per-developer GPU goldens are non-authoritative under llvmpipe; lane-integrity + `Bucket launch-smoke` carry the teeth), bucket-E's per-test ImGui run (render-dependent failures under llvmpipe — a good run is ~71/74; the broken/passed-nothing class hard-fails), and cpp-lint's cppcheck report step (compile-DB-free cppcheck carries unavoidable false positives; the lint-catch-all [error] tier is the job's blocking half). The `advisory`-name exemption has exactly one PR-lane user: `Mobile texture-guard smoke (Mesa headless GL, advisory)` — the all-gates-blocking flip tried to graduate it but the lane's `--spawn` child hangs under llvmpipe on ~half of runs (a real product/harness deadlock, not a retryable flake); it runs advisory (step mask + advisory name) pending a fix + re-graduation (infra backlog 2026-07-05). The schedule-only `Issue sweep (advisory)` job also carries the token but never lands on a PR head.
2. **CodeRabbit** — identity match is `author.login in {"coderabbitai", "coderabbitai[bot]"}` (REST returns the `[bot]` suffix; GraphQL may strip it). State combines the latest CR review's `state`, its `commit.oid` (vs `headRefOid`), and its `body` (CR's `Actionable comments posted: N` first-line header) into one of these outcomes:
   - `NONE` — no review ever submitted. The poller pre-detects whether CR is installed for this repo by probing for a checked-in `.coderabbit.yaml` / `.coderabbit.yml` (one-shot at gate start; override via `MERGE_GATES_CR_INSTALLED=true|false`). Behaviour splits:
     - **CR not installed** (no config file) → **pass** immediately (legacy behaviour for repos that never integrated CR).
     - **CR installed, StatusContext SUCCESS + at least one CR review-thread comment on the current head** → **pass** (C4 prong 2 — the placeholder status is corroborated by real CR review activity on this commit; the inline comment proves CR actually reviewed the current head).
     - **CR installed, StatusContext SUCCESS but ZERO inline CR comments on `headRefOid`** → **block within the grace window**; after `MERGE_GATES_CR_GRACE_POLLS` (default 10) expires, fall through to pass with a `WARN: ... status=SUCCESS but no inline CR comments on head after grace ...; possible status-only config OR C4 bypass` line. The grace-then-pass keeps status-only CR integrations (no inline reviews ever emitted) viable, while the WARN names the suspicious shape so the operator can catch a real C4 bypass case where CR's `auto_review.drafts:false` skipped the review but the placeholder StatusContext still fired SUCCESS.
     - **CR installed, StatusContext SUCCESS + description `Review skipped` (generic — NOT the too-many-files size-skip below)** → **pass immediately, no grace wait**. CR processed the PR and deliberately declined an *incremental* review (docs-only / path-filtered / trivial diff per `.coderabbit.yaml`); the `Review skipped` StatusContext **description** is CR's *terminal* signal that no inline review will ever land, so sitting in the status-SUCCESS-waiting-for-inline grace above is pointless. Printed as `NONE+review-skipped (CR terminal skip — no incremental review for this diff)`. Read from the `CodeRabbit` StatusContext `description` (gate filter field 23, `crReviewSkipped`), ordered AFTER the too-many-files size-skip block so an over-limit skip can never reach this pass path. Motivating miss: PR #976 (docs-only) sat ~10 grace cycles in `NONE+status-SUCCESS-waiting-for-inline` before the passive grace-then-pass fired, and the misleading `skipped`/`NONE` cell was relayed to the user as "CR skipped" instead of CR's actual 0-actionable verdict (see the reporting rule below).
     - **CR installed, no review yet, no SUCCESS status** → **block** until the grace window expires. After the window, the poller logs a `WARN: CodeRabbit grace window ... expired` line and falls through to pass so a stuck integration never wedges the ship-loop indefinitely.
     - **CR=NONE early-nudge** (default **OFF** — `reduce-coderabbit-review-spend` Slice 2): when `MERGE_GATES_NONE_NUDGE_POLLS` > 0, after that many consecutive blocking `NONE` polls on a head (CR installed, `cr_pass=false`, within grace, no CR context yet) the poller posts `@coderabbitai review` once per HEAD. **Default `0` = disabled**, because `.coderabbit.yaml` `auto_review` already reviews every push, so the nudge was redundant and — when it fired on the *first* NONE poll — raced ahead of auto_review (the per-PR redundant `@coderabbitai review` the last-10-PRs audit measured). Shares the once-per-HEAD guard with the STALE re-review trigger (never double-posts). The grace-then-pass backstop above + the STALE trigger remain the safety nets, so disabling the NONE nudge loses no review coverage.
     - **CR review-skipped (too many files)** → **block** unless `cr-out-of-band` is applied. When a PR exceeds CodeRabbit's configured file limit, CR does *not* submit a review object — it posts an auto-generated PR **conversation (issue) comment** whose body carries the stable HTML marker `<!-- ... skip review by coderabbit.ai -->` plus a `> ## Review skipped` / `Too many files!` callout. Detection requires either that HTML marker **or** the structural `## Review skipped` heading together with `too many files` — **NOT** a loose `contains("Review skipped") AND contains("Too many files")` over the whole comment body. That loose form false-positived on any PR whose own diff/walkthrough merely *discusses* CR size-skip (CR echoes the phrases into its summary walkthrough), wrongly hard-blocking a clean PR as a size-skip (observed on PR #980, whose subject is this very change). Because there's no review object, `reviewDecision` stays `NONE` and `cr_state` computes to `NONE`, so the passive NONE grace-then-pass backstop would otherwise wave a completely-unreviewed PR straight through (this is exactly the hole that let a 638-file reorg merge with zero CR review). The poller detects the marker in any `coderabbitai` / `coderabbitai[bot]`-authored conversation comment and treats it as a **hard block** that overrides the grace counter — printed as `NONE+size-skip (CR skipped review — too many files)`, with `BLOCK: CodeRabbit skipped review — too many files (exceeds CR file limit); split the PR (coderabbit review --dir <path> / --base) or apply the 'cr-out-of-band' label to merge without CR review.` on stderr. The futile `@coderabbitai review` early-nudge is **suppressed** for this case (re-triggering review on an over-limit PR just makes CR skip again + spams the thread). The detection is consulted **only when `cr_state == NONE`** (no review object on any commit), so if the PR is later reduced/split and CR posts a real on-head review, the most-recent CR signal (`APPROVED` / `COMMENTED` / `CHANGES_REQUESTED` / `STALE*`) takes precedence and the stale skip comment is ignored. Override: `cr-out-of-band` downgrades it to a pass with `WARN: cr-out-of-band — CR skipped review (too many files) overridden`.
   - **On-head review** (`commit.oid == headRefOid`):
     - `APPROVED` → **pass** unconditionally (approval trumps body).
     - `COMMENTED + body has "Actionable comments posted: N" with N > 0` → **block** (CR found real findings the user must address before merge). The previous "COMMENTED == pass" rule shipped 5 unaddressed CR findings to develop on PR #357 — see `docs/self-improvement/categories/process.md` P1 (2026-05-21) for the post-mortem.
     - `COMMENTED + N == 0` → **pass** (CR explicitly said no findings).
     - `COMMENTED + no Actionable header in body` → **pass** (placeholder review / older CR template; conservative).
     - `CHANGES_REQUESTED` / `DISMISSED` → **block**.
   - **Stale review** (CR reviewed a prior commit; force-push or post-review commit moved HEAD past the review):
     - `STALE_WITH_FINDINGS` (prior body had `N > 0`) → **block** + DO NOT fall through to pass on timeout. The timeout-fallthrough path on stale-with-findings is what dropped #357's 5 findings; the prior review body must be surfaced + the user explicitly authorises any force-merge.
     - `STALE_RESOLVED` (prior body had `N > 0` BUT every CR review thread is resolved AND the on-head `CodeRabbit` StatusContext is `SUCCESS`) → **pass**. CR's accept signal for a fixup commit is *thread resolution* on re-review; it does not always re-issue a clean "Actionable comments posted: 0" review body. Both signals are required together — `cr_open == 0` alone could be user-driven thread resolution without CR judgement; `StatusContext == SUCCESS` alone could be a stale placeholder. Together they unambiguously mean "CR re-evaluated the current head and accepted the fix." Codified per the recurring stuck-queue pattern hit on PRs #421/#422/#423/#425 on 2026-05-23.
     - `STALE_CLEAN` (prior body had `N == 0`) → **pass** (prior review was clean; on-head changes likely still clean modulo new edits).
     - `STALE_UNKNOWN` (prior body absent or no `Actionable` header) → **block** as safe default (caller can't distinguish "0 actionable" from "no header", so the safer assumption is "could have findings").
   - Additionally: zero unresolved non-outdated review threads contain a CodeRabbit comment (under the same login match). CR sometimes leaves per-line review threads `isResolved:false` on prior commits even after its overall review on the new head is SUCCESS, which kept `cr_open > 0` and wedged merges historically (2026-05-22 PRs #408/#410). `smatchet-merge-watcher` exposes a default-on side-channel — `MERGE_WATCH_RESOLVE_CR_THREADS` (default `true` as of 2026-05-28; set `false` / `0` / `no` to opt out) — that calls GraphQL `mutation resolveReviewThread` per stuck CR-authored thread after an auto-act push lands on a new head (gate logic detailed in `docs/plans/shipped/smatchet-merge-watcher.md` § decision 7). Manual unblock: `gh api graphql -f query='mutation($id:ID!){resolveReviewThread(input:{threadId:$id}){thread{id}}}' -F id=<thread-id>`.
3. **User comments** — zero unresolved non-outdated review threads with any non-bot non-self comment, AND zero conversation-tab comments from a non-bot non-self author. Bot detection uses GraphQL `author.__typename == "Bot"` (covers all integrations). Self matched via `$ORCH_USER`, lower-cased on both sides.
4. **Cursor Bugbot** — identity match is `author.login in {"cursor", "cursor[bot]"}` (REST returns the `[bot]` suffix; GraphQL may strip it). Bugbot posts line-anchored inline findings (→ `reviewThreads`) plus an always-`COMMENTED` summary review (it never emits `CHANGES_REQUESTED`, so it never moves `reviewDecision`), and usage-cap status notices on the conversation tab. The gate therefore guards on **unresolved non-outdated `cursor[bot]` inline-finding threads** (`bb_open`) only — there is no review-state verdict to read. The poller folds Bugbot's signals into a single `bb_state` token (gate filter field 24): a review state (`COMMENTED`) when Bugbot reviewed the current head, else `TERMINAL` (a `couldn't run` / `usage limit` conversation comment), else `STALE` (Bugbot reviewed a prior commit only), else `ABSENT` (no `cursor[bot]` review anywhere). Decision tree (ORDER is load-bearing):
   - `bb_open > 0` → **block** (any unresolved `cursor[bot]` finding blocks — Bugbot already self-filters to High/Medium, so there is no severity floor). `bugbot-out-of-band` downgrades this to a WARN/pass.
   - else `bb_state == TERMINAL` → **pass** (no-wedge short-circuit, **skips grace**). A spend-capped or "couldn't run" Bugbot that produced no findings must never wedge a merge. **Reached only after the `bb_open > 0` branch falls through**, so a `usage limit` comment that coexists with real open findings still **blocks** — the no-wedge guarantee covers a *no-verdict* Bugbot, not *findings-then-cap* (resolve the threads or apply `bugbot-out-of-band`).
   - else `bugbot-out-of-band` label → **pass** (operator waiver — also short-circuits the grace wait).
   - else `bb_state == STALE` and `poll < MERGE_GATES_BB_GRACE_POLLS` → **block (PENDING)** — wait a full CR-style grace window for Bugbot to re-review the new head before passing. An `ABSENT` Bugbot (no artefact at all — Bugbot-free PR / not engaged) is **never** waited on (passes immediately), so a repo where Bugbot isn't active is unaffected.
   - else → **pass** (a clean on-head review with `bb_open == 0`, a `STALE` review whose grace expired — logged, never wedge — or an `ABSENT` Bugbot).

   Three no-wedge escape hatches therefore guarantee a usage-capped or silent Bugbot can never block a merge longer than `MERGE_GATES_BB_GRACE_POLLS`: the **TERMINAL** short-circuit, the **`BB_GRACE_POLLS`-bounded STALE** wait, and the **`bugbot-out-of-band`** override. **Ops bootstrap**: `bugbot-out-of-band` must be created once on the repo (`gh label create bugbot-out-of-band --description "Downgrade Bugbot merge block to WARN" --color BFD4F2`) before it can override. Like the other out-of-band labels it MUST NOT stay on the PR post-merge.

**Self-improvement doc PR auto-exemption (CR gate #2 + Bugbot gate #4, NO label).** A PR whose diff is **entirely** under `docs/self-improvement/**` (the self-improvement backlog / postmortem ledger — per-entry `categories/<cat>/<date>-<slug>.md`, `postmortems.md`, `applied.md`, `AGENT_SELF_IMPROVEMENT.md`) is low-risk, never-compiled markdown that the user has chosen to **not** code-review (plan `self-improvement-pr-review-exemption`, decision 2026-06-20). The poller derives `selfImpOnly` (gate filter field 27) from the PR `files` list — TRUE iff every changed path starts with `docs/self-improvement/` AND the file page did not overflow (`pageInfo.hasNextPage == false`) AND the list is non-empty; any uncertainty (overflow, empty, absent) fails safe to FALSE → full gates. When TRUE:
   - **CodeRabbit (#2)**: the primary lever is `.coderabbit.yaml`'s `!docs/self-improvement/**` path_filter — CR has nothing reviewable, posts its terminal `Review skipped` status, and the gate fast-passes via `crReviewSkipped` (gate #2, line 16). A belt-and-suspenders downgrade in the poller also waives any *residual* CR block (e.g. a STALE review left from before the path_filter landed): `WARN: self-improvement doc PR — CR gate auto-skipped (...)`. It does NOT set `cr_override` (this is a documented auto-behaviour, not a label override — so the GATE_SNAPSHOT clean-merge contract is preserved and `postmortem-owed` never flags it).
   - **Cursor Bugbot (#4)**: `selfImpOnly` auto-downgrades a `bb_open > 0` block to a WARN (`WARN: self-improvement doc PR ... Bugbot gate auto-skipped`) and short-circuits the `STALE` re-review grace wait — symmetric with `bugbot-out-of-band`, but keyed on detection, no label.
   - **CI (#1) + user-comment (#3) gates still bind** — a failing required check (incl. the doc-validation `Doc anchors + agent contract` suite, which keeps the ledger docs valid) or an unresolved human comment still blocks. The heavy C++ build/test suite is already skipped for these PRs by `build-and-test.yml`'s `changes` job (it classifies `docs/*` as non-code), so the exemption is purely about the two review-bot gates.
   - **Bugbot still *posts* (Cursor spend) unless ignored at source.** The poller change stops Bugbot from *blocking*, not from *reviewing* — Bugbot has no in-repo config. To stop it reviewing these PRs entirely, add `docs/self-improvement/**` to Bugbot's ignore paths in the **Cursor dashboard** (Bugbot settings). This is the one manual ops step; the gate auto-skip holds regardless of whether it is set.

Additional pass conditions:
- `pullRequest.state == "OPEN"` (early-exit on closed/merged-externally).
- `pullRequest.reviewDecision in {"APPROVED", null}` (blocks on `REVIEW_REQUIRED` / `CHANGES_REQUESTED`).
- **Pagination ceiling**: GitHub GraphQL caps connections at 100. The query also fetches `pageInfo.hasNextPage` for every connection (checks, reviews, reviewThreads, per-thread comments, conversation comments). Any `hasNextPage == true` → block with `PAGINATION_OVERFLOW`. Hard block, not silent truncation.

`$ORCH_USER` resolved at session init via `gh api user --jq .login`.

**Override**: `SKIP_MERGE_GATES=true` at session init bypasses all gates. No per-merge skip. Subagent propagation: orchestrator must explicitly add `SKIP_MERGE_GATES` to any delegated `git-janitor` invocation's env (it does not auto-inherit through the subagent boundary).

**Per-PR overrides (label-based)**:
- `tests-out-of-band` — downgrades the test-delta gate from FAIL to WARN for that PR. Use when production code changes legitimately have no testable surface (e.g. perf optimisations that preserve behaviour but lack pure-logic seams).
- `perf-out-of-band` — downgrades the `.github/workflows/perf-pr-fast.yml` regression gate (slice 3 of `docs/plans/shipped/pillar-1-2-perf-review-system.md`) from FAIL to WARN. Use when a regression is intentional + the baseline-bump PR is queued. The label must NOT stay on the PR post-merge; the merge contract assumes the next PR clears the regression or bumps the baseline.
- `intent-out-of-band` — downgrades the `Intent section` doc-validation gate (a missing/empty PR-body `## Intent` section) from FAIL to WARN. The gate is on the meant-to-block allow-list (it blocks like Coverage/Sanitizer, not via `branch_protection` — see `docs/adr/0022-intent-gate-promotion.md` / `docs/plans/pr-intent-capture-hardening.md` #5). Use for a fresh worktree provisioned before the capture hook existed, or a non-Claude-Code harness relying on the hand-fill fallback (`docs/agent-rules/ship-loops.md` § Intent capture). **Not** the path for Dependabot bumps — bot-authored PRs are exempt in the job's `if:` (it skips, which counts as passing), so the label never has to be pinned on a routine bump. Like the other out-of-band labels, it MUST NOT stay on the PR post-merge.
- `bugbot-out-of-band` — downgrades a **Cursor Bugbot** block to WARN (pass). Scoped to the Bugbot gate ONLY: it waives unresolved `cursor[bot]` inline findings (`bb_open > 0`) and also short-circuits the `STALE` re-review grace wait. It does NOT touch the CI, CodeRabbit, or user-comment gates. Emits `WARN: bugbot-out-of-band label downgraded Bugbot block (<N> unresolved cursor[bot] finding(s)) to WARN` on stderr. Use when Bugbot's findings are knowingly acceptable / out-of-band (e.g. a follow-up PR addresses them). Must be `gh label create`d once on the repo (see § gate 4) and, like the other out-of-band labels, MUST NOT stay on the PR post-merge.
- `cr-out-of-band` — downgrades a **CodeRabbit** block to WARN (pass). Scoped to the CR gate ONLY: it waives the CR state verdict (`CHANGES_REQUESTED`, `COMMENTED + N > 0`, `DISMISSED`, `STALE_WITH_FINDINGS`, `STALE_UNKNOWN`, a still-blocking `NONE`, or a **review-skipped — too many files** comment), and any unresolved CodeRabbit-authored review threads (`cr_open`). It does NOT touch the CI gate (`ci_fail` / `ci_pend`) or the user-comment gate — a failing required check or an unresolved human comment still blocks. **REQUIRES a paired `cr-disposition:<reason>` attestation** (see next bullet) — `cr-out-of-band` ALONE is NOT honoured: without a disposition the block stands and the poller emits `WARN: cr-out-of-band present but NOT honoured — a cr-out-of-band downgrade also requires a 'cr-disposition:<reason>' label or PR-body marker … PR-3 cr-out-of-band-disposition-trail`. When both are present it emits `WARN: cr-out-of-band + cr-disposition label downgraded CR block (<state>) to WARN` on stderr (the review-skipped case emits the tailored `WARN: cr-out-of-band + cr-disposition — CR skipped review (too many files) overridden` instead). **The downgrade additionally requires EVIDENCE that CodeRabbit actually ran on the head** (merge-pipeline-04 residual): a review verdict (`APPROVED`/`COMMENTED`/`CHANGES_REQUESTED`/`STALE*`), a CR context on the head, a SUCCESS StatusContext, a terminal `Review skipped`, a too-many-files size-skip, or a rate-limit skip. If CR **never ran** (none of those), even a valid `cr-disposition` will NOT honour the override — the block stands with `WARN: cr-out-of-band + cr-disposition present but NOT honoured — CodeRabbit never ran on head … A disposition cannot waive a review that never happened …` — so a bogus attestation on a CR-untouched PR can't bypass review entirely. Use when CR's findings are knowingly acceptable / out-of-band (e.g. a follow-up PR addresses them) or when an over-limit PR legitimately can't be split. Like the other out-of-band labels, it MUST NOT stay on the PR post-merge.
- `cr-disposition:<reason>` — the **mandatory disposition trail** paired with `cr-out-of-band` (PR-3 cr-out-of-band-disposition-trail). It records WHY CR review was waived so the override is never reflexive and the override-merge ledger always carries the rationale. Supply it EITHER as a `cr-disposition:`-prefixed **label** (e.g. `cr-disposition:rate-limit-acked`, `cr-disposition:follow-up-pr`) OR as a grep-able `cr-disposition:<reason>` **marker line in the PR body** — the poller folds both into one detection (`gh pr edit <pr> --add-label 'cr-disposition:<reason>'`, or add the line to the PR description). The CR rate-limit skip on a CODE PR is the original case of this rule (PR-2 cr-rate-limit-code-pr-auto-pause); PR-3 generalises it to every `cr-out-of-band` waiver. Like `cr-out-of-band`, it MUST NOT stay on the PR post-merge.

**Override-label hygiene — never pre-apply**: apply a `*-out-of-band` label only **in response to a confirmed red check / CR block it names**, never defensively ("just in case" before CI finishes, or to pre-empt a gate that might fire). A pre-applied label on a merge where nothing was red records in the snapshot ledger as `overrideLabels` non-empty with `redChecks` empty, and audits as if a gate was bypassed when none was — the #1124 (`tests-out-of-band`, all checks green) / #1110 (`cr-out-of-band`, `redChecks:[]`) false postmortem nudges (2026-06-11). `postmortem-owed.sh` filters a **moot override** (its gated check passed on its own — not load-bearing) so it no longer owes a postmortem (live-fallback path; the snapshot ledger stays the lossless authority and is not re-judged against the lossy live rollup) — but the hygiene rule stands regardless of detector behaviour: if no gate is red, there is nothing to override; don't apply the label. Combined with the existing per-label rule that overrides MUST NOT stay on the PR post-merge, the invariant is: a label's lifetime is *confirmed-red → merge*, nothing wider. **Enforcement (PR-3):** `agents/scripts/core/issue-sweep.sh` carries a merged-PR out-of-band-label strip step — it lists recently-merged PRs (live `gh pr list --state merged` or a `MERGED_PRS_JSON` fixture) and, in `--apply`, removes any lingering `*-out-of-band` label (`gh pr edit <n> --remove-label …`) so an override never survives on a merged PR to skew the ledger; dry-run reports the strips as `OOB-STRIP #<n> remove-label '<label>'`.

**Status line per poll**:
```
Poll 3/60 — CI: 4/8 pass (1 fail, 2 pending, 1 warn-downgraded, 0 req-missing) | CodeRabbit: COMMENTED (3 actionable — block) (2 open) | Bugbot: COMMENTED (2 unresolved) (2 open) | User: 1 | reviewDecision: APPROVED
```

The `warn-downgraded` cell counts CheckRuns whose failing conclusion (`FAILURE`, `TIMED_OUT`, `CANCELLED`, `ACTION_REQUIRED`, `STARTUP_FAILURE`) was suppressed by a per-PR label override (`tests-out-of-band` / `perf-out-of-band`). Downgraded checks do NOT contribute to `fail` and do NOT block; an `WARN: out-of-band label(s) downgraded …` line on stderr names which checks were silenced for the operator's review.

The CR cell encodes the outcomes verbatim — examples: `APPROVED`, `COMMENTED (3 actionable — block)`, `COMMENTED (0 actionable)`, `COMMENTED (no Actionable header)`, `STALE_WITH_FINDINGS (5 actionable on prior commit — block + surface review)`, `STALE_RESOLVED (4 actionable on prior commit, all threads resolved + status SUCCESS — pass)`, `STALE_CLEAN (0 actionable on prior commit — pass)`, `STALE_UNKNOWN (no Actionable header — treat as block per safe-default policy)`, `CHANGES_REQUESTED`, `DISMISSED`, `NONE+pending (poll N/<grace>)`, `NONE+status-SUCCESS+inline-evidence`, `NONE+status-SUCCESS-waiting-for-inline (poll N/<grace>)`, `NONE+status-SUCCESS+no-inline-evidence`, `NONE+review-skipped (CR terminal skip — no incremental review for this diff)`, `NONE+grace-expired`, `NONE+size-skip (CR skipped review — too many files)` (all `WARN`/`BLOCK`-paired on stderr where noted).

**Reporting CR status — read CR's verdict, not the check label or the watcher cell.** When telling the user (or replying to CR) what CodeRabbit concluded, read CR's **actual posted verdict** — its review/summary body's `Actionable comments posted: N` line (or "No actionable comments were generated"), e.g. `gh pr view <pr> --json reviews` / `gh api .../issues/<pr>/comments`. Do **NOT** relay the `CodeRabbit` GitHub **check-run label** (`Review skipped`) or the watcher's `cr_state` cell (`NONE`, `NONE+...`) as CR's verdict — those are the *gate's* internal classification of CR's *signal shape*, not CR's review outcome, and they routinely diverge: CR can post "No actionable comments / 0 actionable" (a clean pass) while its status check shows `Review skipped` and the gate's cell reads `NONE` (PR #976 — relayed as "CR skipped" when CR had actually cleared the PR). Sibling of the AGENTS.md rule "never trust a CodeRabbit ✅ Addressed annotation blindly" — same root cause: the check/annotation layer is not CR's verdict; the posted review body is.

| Code | Meaning | `AskUserQuestion` options |
|---|---|---|
| 1 | Gates still blocked at MAX_POLLS | "Skip gates and merge anyway" / "Keep waiting (extend poll)" / "Abandon" |
| 2 | Wall-clock timeout (≥`MERGE_GATES_TIMEOUT_SECONDS`) | "Skip gates and merge anyway" / "Keep waiting" / "Abandon" |
| 3 | `gh` API failed 3 consecutive polls | "Retry now" / "Skip gates and merge anyway" / "Abandon" |
| 4 | PR `CLOSED` or `MERGED` externally | "Abandon (PR no longer mergeable)" — no skip option |
| 5 | Pagination overflow (any `hasNextPage`) | "Abandon (manual review required)" / "Skip gates and merge anyway (acknowledge risk)" |
| 6 | `gh pr ready` unknown failure (after positive-check fallback) | surface error to user; do not auto-merge |

Any "Skip gates and merge anyway" choice logs `LOG_WARN "user skipped gates: code=<n>"` before proceeding.

**Auto-`gh pr ready` + merge** apply only when the user has explicitly authorised this PR for merge (post-ship option 3 "Register with watcher", in-session "merge when green", OR any PR registered with `smatchet-merge-watcher`). Without that authorization, gate-pass is reported and the orchestrator stops without flipping draft state. Use REST merge per `agents/core/git-janitor.md` § Hard refusals:

```bash
gh api -X PUT "repos/$owner/$repo/pulls/$prNumber/merge" -f merge_method=squash
gh api -X DELETE "repos/$owner/$repo/git/refs/heads/$branch"
```

Conflicts, missing required checks, and branch-protection rules are enforced by GitHub on the REST merge call. We do not duplicate.

**Sanctioned non-admin merge path — `safe-merge.sh`, NOT a bare `gh pr merge --auto`.** The single sanctioned way to arm a non-admin squash-merge is `agents/scripts/core/safe-merge.sh <pr>` (PR-1 § intent-gate-safe-merge-wrapper). It runs the **full** merge-gates poll above and arms `gh pr merge --squash --auto` **only** on `GATES_PASSED`. A **bare `gh pr merge <pr> --squash --auto` is forbidden in the ship-loop**, and so is a **direct REST `PUT .../pulls/<n>/merge`** issued without first confirming the full gate set — because:

- GitHub auto-merge / branch protection only wait on the **branch-protection required contexts**. The **CodeRabbit**, **user-comment**, and **Cursor-Bugbot** gates are **not** GitHub-required check contexts (CR stays PR-advisory by design — see the merge-queue paragraph below). So `--auto` (or a direct `PUT`) can fire the moment CI is green while a real CR finding / unresolved human comment / open Bugbot thread is still outstanding — the precise gap `safe-merge.sh` closes (`auto-merge-poller-default`).
- **Any** non-required RED (or pending) check is invisible to GitHub auto-merge (non-required) but blocks the poller — the #923 escape class, now closed for every check by block-on-any-red. `safe-merge.sh` refuses on any non-advisory-named RED lacking its named `*-out-of-band` override label; bare `--auto` would merge straight past it — which is why arming `--auto` before the poller passes is the one remaining gap the required-contexts set (see § required checks) narrows.

**Armed / autonomous merges MUST go through `safe-merge.sh` — bare `--auto` both under- and over-fires (`dogfood-safe-merge`).** Beyond the two gaps above, the bare `gh pr merge --squash --auto` path is wrong in *both* timing directions, which is exactly why an armed/autonomous merge must always route through the wrapper:
- **Fires too early (merges past a CR finding).** Because CR is async and not a required context, `--auto` can complete the merge *before* CodeRabbit even posts its review — the merge wins the race and a real finding lands on `develop` unseen (the same class as the #1332 admin-merge-beats-review race `safe-admin-merge.sh` closes on the admin path). `safe-merge.sh` runs the full gate set (CR + user-comment + conversation) before arming, so CR has completed when the merge is allowed to proceed.
- **Wedges forever (never fires).** Conversely, when CR posts findings or `require_conversation_resolution` holds the PR at `BLOCKED`, bare `--auto` neither merges (the block stands) nor reports *why* — it silently waits forever on a state GitHub never resolves on its own. `safe-merge.sh` refuses with the named blocker instead of arming a no-op, and `scripts/dev/pr-blocked-why.sh <pr>` names the precise cause (see § PR-readiness step + the CONVERSATION class). The lesson generalises: never hand-arm a bare `--auto` / direct `PUT` for an armed or autonomous merge — `safe-merge.sh` is the only sanctioned entry-point, `safe-admin-merge.sh` the narrow stale-BLOCKED carve-out.

**Draft never pauses an authorized merge.** `safe-merge.sh` defaults `MERGE_GATES_FLIP_READY=true` when the caller left it unset: invoking the wrapper IS the merge authorization (standing `governance.auto_merge: on` grant or per-PR "merge when green"), so a PR that was opened draft — remote / web harnesses open drafts by default — is flipped ready before the poll instead of wedging the CodeRabbit gate (its `auto_review.drafts: false` skips drafts → the C4 class blocks on NONE past the grace window) and then failing the arm step (`gh pr merge` refuses drafts). The wrapper also runs `gh_pr_ready_idempotent` once more immediately before arming (mirroring the watcher's pre-merge flip) so a flip WARN or a CR-exempt pass can't leave a lingering draft at arm time. An explicit `MERGE_GATES_FLIP_READY=false` is preserved for poll-only semantics; unauthorized poll-only callers (status checks, dry-runs) still never flip because they call `merge-gates.sh` directly, not the wrapper.

`safe-merge.sh` is to non-admin merge what `safe-admin-merge.sh` is to admin merge: the green assertion is an **exit code**, never advisory text printed beside an unconditional merge command. The only callers with merge authority — orchestrator, `git-janitor`, `smatchet-merge-watcher` — use `safe-merge.sh` (or the watcher's equivalent in-process poll + `--auto`) on the normal path, and `safe-admin-merge.sh` for the narrow stale-BLOCKED carve-out. Tests: `tests/bats/safe_merge.bats`; dogfooded via `safe-merge.sh --selftest`.

**Don't arm auto-merge before the FINAL commit is pushed (`auto-merge-armed-before-final-push-orphans-commit`).** GitHub auto-merge merges the **branch tip that satisfies the gates** — if `--auto` (or `safe-merge.sh`) is armed and then a later commit lands locally but is **not yet pushed**, the gates can pass on the *already-pushed* tip and merge it, orphaning the un-pushed final commit (it never reaches `develop`). Arm the merge **only after the last commit of the PR is pushed** and the head SHA on GitHub matches local `HEAD`. The `[pre-first-push gate]` already batches CR-fix rounds into a single push; the symmetric rule at merge-arm time is: confirm `git rev-parse HEAD == <PR headRefOid>` before arming.

**PR-readiness step — enumerate unresolved reviewThreads classified vs HEAD before asserting "ready" (`verify-unresolved-review-threads-vs-head`).** Before reporting a PR "ready to merge" (or arming auto-merge), enumerate its unresolved, non-outdated `reviewThreads` and classify each against the current `headRefOid`: a thread anchored to a **prior** commit that the current head already addressed is stale (resolvable / non-blocking), while a thread on the **current** head is a live blocker. Do **not** assert readiness off a green CI rollup alone — an APPROVED `reviewDecision` with open human/bot threads on the head still blocks (gates #2/#3/#4). `scripts/dev/pr-blocked-why.sh <pr>` (PR-1 § green-pr-blocked-no-merge-signal) does exactly this classification for a MERGEABLE+BLOCKED PR — run it whenever a green-looking PR refuses to merge to get the precise blocker. It reports a **top-level `CONVERSATION` class** (`pr-blocked-why-conversation-surfacing`) when the PR has unresolved threads AND the base branch's `require_conversation_resolution` is on: this is the common *silent* BLOCKED cause — every CI check green, `reviewDecision` APPROVED, yet GitHub holds the merge purely on the open thread. The other classes it names are unresolved threads / skipped-required checks / review shortfall / absent-required context — instead of guessing.

**CR false-positive override — two steps, not one (`cr-false-positive-resolve-thread`).** When a CodeRabbit review thread is a **confirmed false positive** (you read the cited line and CR is wrong), waiving the CR *gate* alone is not enough — the open thread can still wedge the merge via `require_conversation_resolution`. The complete override is **both**:
1. **Waive the CR gate** — apply `cr-out-of-band` **paired with** a `cr-disposition:<reason>` attestation (label or PR-body marker; `cr-out-of-band` ALONE is not honoured — see § Per-PR overrides). The disposition records *why* CR was waived (e.g. `cr-disposition:false-positive`), so the override is never reflexive.
2. **Resolve the thread** — call GraphQL `resolveReviewThread` on the false-positive thread so `require_conversation_resolution` clears and the `CONVERSATION` blocker (above) lifts:
   ```bash
   gh api graphql -f query='mutation($id:ID!){resolveReviewThread(input:{threadId:$id}){thread{id}}}' -F id=<thread-id>
   ```
   (`smatchet-merge-watcher` does this automatically for stuck CR-authored threads via `MERGE_WATCH_RESOLVE_CR_THREADS` — see gate #2; the manual flow above is for the in-session orchestrator.)

Step 1 without step 2 leaves a CI-green, gate-waived PR still BLOCKED on the open conversation; step 2 without step 1 silences the thread but the CR *state* verdict can still block. Do both for a confirmed false positive.

**Merge throughput (develop)**: a GitHub merge queue is **unavailable** on this user-owned repo (org-only feature — absent from both classic branch protection and rulesets), so develop runs with **strict off** (require-branches-up-to-date = false): a PR merges the moment its required checks (`project.config.json` § branch_protection, applied by `setup-branch-protection.sh`) pass on its **own** head — no up-to-date/force-merge dance — with post-merge CI as the backstop. The 4 hosting workflows keep harmless `merge_group` triggers (future-proof if the repo ever moves under an org); the queue mechanics stay documented below for that eventuality. Merge via auto-merge (`gh pr merge --squash --auto`) or a direct `PUT .../merge` (both valid with no queue); the watcher's PASS handler uses `--auto`. The custom poller + `*-out-of-band` labels remain; CR stays PR-advisory (not a GitHub-required check).

**GitHub merge queue**: a repo may put its protected branch behind a GitHub merge queue, in which case the branch-protection required checks gate the merge by re-running on the queue's synthetic `merge_group` ref. Every workflow hosting a required check must then also trigger on `merge_group`, and every required job must either run there or self-gate to a green no-op that reports the same check context — a required check that never reports on `merge_group` **deadlocks the queue forever** (the same path-filtered-required-check class that previously deadlocked product-only PRs). When a queue is active a **direct** REST merge (`PUT pulls/{pr}/merge`) returns 405; the queue-safe path is to **enable auto-merge** (`gh pr merge --squash --auto`), which merges immediately if no queue is set and enqueues if one is — the merge-watcher's PASS handler uses `--auto` accordingly, keeping its `merge-gates.sh` gate-poll as the pre-enqueue check. The custom poller above + the `*-out-of-band` labels remain for the legacy / manual (non-queue) path; **CodeRabbit stays PR-advisory** — not a queue-required `merge_group` check.

**Env knobs**:
- `MERGE_GATES_POLL_INTERVAL` — seconds between polls (default 60).
- `MERGE_GATES_MAX_POLLS` — max poll count (default 60).
- `MERGE_GATES_TIMEOUT_SECONDS` — wall-clock budget (default 3600).
- `MERGE_GATES_QUERY_FILE` — override GraphQL document path (default `agents/scripts/core/merge-gates.graphql`).
- `MERGE_GATES_CR_INSTALLED` — override the auto-detected CodeRabbit-installed flag (`true` / `false`). Auto-detection probes `repos/<owner>/<repo>/contents/.coderabbit.yaml` (and `.yml`); set explicitly when the config lives outside the repo or when running against a fork that has not yet enabled CR.
- `MERGE_GATES_CR_GRACE_POLLS` — polls to wait for CR to start (a review or `CodeRabbit` SUCCESS status) before falling through `NONE` to pass (default 10). Only consulted when `MERGE_GATES_CR_INSTALLED` is true / auto-detected as installed.
  - **Watcher-side counterpart** (`agents/scripts/core/merge-watcher.py`): the daemon drives merge-gates with `MAX_POLLS=1`, so the in-process grace above never elapses; the watcher re-counts it across real cycles via `MERGE_WATCH_CR_NONE_GRACE_CYCLES` (default 10). For a **pure-docs diff** (per `is-pure-docs-diff.sh`'s allow-list — `docs/`, `backlog/`, `agents/scripts/`, any `*.md`) it instead uses `MERGE_WATCH_CR_NONE_GRACE_CYCLES_PURE_DOCS` (default **1**), because CR's `Review skipped` is its *terminal* verdict on a docs-only diff — the full 10-cycle wait is pure dead time (measured ~6 min, PR #976). This shrinks the watcher's WAIT only; it does **not** bypass CR — the required `CR finding gate` status check still gates the squash. Complements the gate's `crReviewSkipped` immediate-pass (line 16): the gate fast-passes once CR posts the terminal `Review skipped` *description*; the watcher window covers the interval before that description lands (or if it never does).
- `MERGE_GATES_BB_GRACE_POLLS` — polls to wait for Cursor Bugbot to re-review the current head when its only review is on a prior commit (`bb_state == STALE`) before grace-expiry pass (default 10). A `TERMINAL` (couldn't-run / usage-limit) or `ABSENT` (no Bugbot artefact) state is never waited on; this knob only bounds the `STALE` re-review window so a mid-re-review Bugbot can't be merged under, while a stuck Bugbot can't wedge the loop past the window.
- `MERGE_GATES_STALE_REREVIEW_POLLS` — consecutive blocking-STALE polls on the same HEAD before the poller auto-posts `@coderabbitai review` once per HEAD (default 5). `0` disables the STALE auto-nudge. (No longer gates the CR=NONE early-nudge — that moved to the separate `MERGE_GATES_NONE_NUDGE_POLLS` knob below, `reduce-coderabbit-review-spend` Slice 2.)
- `MERGE_GATES_NONE_NUDGE_POLLS` — consecutive blocking-NONE polls on the same HEAD before the poller auto-posts `@coderabbitai review` once per HEAD (default **0 = disabled**). Decoupled from the STALE knob so the redundant first-poll NONE nudge can stay off — `auto_review` already reviews every push — while the STALE backstop stays on. Set > 0 to re-enable after an N-poll grace that lets auto_review post first. Carries across `MAX_POLLS=1` watcher cycles via `MERGE_GATES_PRIOR_NONE_STREAK` / `MERGE_GATES_PRIOR_NONE_HEAD` (mirror of the STALE carry, emitted on the `GATE_CARRY` line). Shares the once-per-HEAD guard with the STALE trigger, so at most one `@coderabbitai review` is posted per head SHA.
- `MERGE_GATES_FRESHNESS` — gate-logic self-freshness guard (`off` default / `warn` / `block`; #1428). In `block` mode `poll_merge_gates` refuses `GATES_PASSED` when this `merge-gates.sh`'s on-disk blob differs from `origin/develop`'s (fail-closed; unverifiable also blocks) — so an unattended merger running a STALE checkout can't enforce out-of-date gate logic (the #1428 escape: a host tree parked behind develop merged a PR past a RED non-required `Intent section` its old allow-list lacked). `smatchet-merge-watcher` sets `block`; `warn` prints the divergence without blocking; test-only `MERGE_GATES_FRESH_RUN_BLOB` / `MERGE_GATES_FRESH_DEV_BLOB` bypass the git compare. **An invalid value returns 3 (never passes)** so a typo can't silently weaken enforcement.
  - **Watcher-side complement** (`agents/scripts/core/merge-watcher.py` `maybe_self_resync`, `MERGE_WATCH_AUTO_RESYNC` default `on`): the fail-closed guard preserves correctness but *wedges* a drifted daemon at zero throughput. To self-heal, at startup + every `MERGE_WATCH_RESYNC_EVERY_CYCLES` cycles (default 30) the daemon checks whether its checkout drifted behind `origin/develop` on any gate-logic file (`merge-gates.sh` / `.graphql` / `merge-watcher*.py`); on a **SAFE** fast-forward (clean tree, on `develop`, no divergence) it `git pull --ff-only`s develop so the on-disk `merge-gates.sh` goes fresh (the next poll re-reads it → the guard passes again) and re-execs **on POSIX only** when the daemon's own code changed (Windows would detach the process from its Scheduled Task, so it logs a restart-needed WARN instead). The **unsafe-tree** case — the #1428 feature-branch park, a dirty tree, or a diverged HEAD — is **never auto-mutated** (the banned shared-tree rug-pull): it warns + waits for a human, the fail-closed guard still blocking any stale merge. `MERGE_WATCH_AUTO_RESYNC=off` disables the self-resync, leaving only the fail-closed guard.
- `MERGE_GATES_TEST_ANSWER` — bats-only canned `ask_user_question` answer.

**Scope boundary**: the auto-`gh pr ready` + auto-merge path applies to the orchestrator, `git-janitor`, and `smatchet-merge-watcher`. No other caller has merge authority. The deleted spawned-child agents (`handoff-implementer`, `pr-iterator`) are gone per v1 of `docs/plans/shipped/github-tracker-backend.md`; the watcher runs as a host daemon, not a per-PR subprocess, so the spawned-child draft-only carve-out no longer applies.
