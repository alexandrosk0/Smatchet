This file groups the rules that govern **how agents move work through the pipeline** — plan-doc lifecycle, destructive-VCS-op discipline, and cadence/verification rules. The companion files are [`merge-gates.md`](merge-gates.md) (what blocks a squash-merge), [`ship-loops.md`](ship-loops.md) (the turn-level loop shape), and [`delegation.md`](delegation.md) (agent routing + scratchpad / progress / output contracts).

## Plan-doc family

**Doc structure**: the normative taxonomy + the portable/project boundary + per-dir enforcing guards live in [`docs/STRUCTURE.md`](../STRUCTURE.md) (reuse guide: [`docs/PORTABILITY.md`](../PORTABILITY.md)). The portable agentic layer (`agents/core/`, `agents/_shared/`, `docs/agent-rules/`, `docs/harness/`) must not hardcode project literals — read them from `project.config.json` (guard: `test-portable-purity`).

**Plan location**: every plan / design doc lives under `docs/plans/active/<slug>.md`; once shipped, `git mv` to `docs/plans/shipped/<slug>.md` (the `INDEX.md` row auto-appears). A **third tier** — `docs/plans/deferred/<slug>.md` — holds a plan **parked indefinitely**: judged not-worth-building-now but with a captured design, to be built **only on a named recurrence / condition** (not in-flight, not shipped). Use it instead of leaving a deferred plan in `active/` pretending to be in-flight, or deleting one other docs still reference. The plan keeps a `> **STATUS: DEFERRED (pending <condition>)**` banner naming the trigger. Gates know all three tiers (`test-plan-naming` + `test-plan-ref-integrity` scan `{active,shipped,deferred}`); `INDEX.md` indexes `shipped/` only. No plans in repo root, `~/.claude/plans/`, or working-tree-only scratch. Agent self-improvement entries live in `docs/self-improvement/categories/` — not as plans. Naming: kebab-case slug matching the feature (guard: `test-plan-naming`).

**Plan-doc safety**: as soon as a plan is written to `docs/plans/active/<slug>.md`, `git add` + commit it immediately with a `wip(plan): <slug>` prefix before any other work or branch operation. Working-tree-only files are silently lost on `git checkout`, `git reset --hard`, or GitHub Desktop branch switches. Recovery via `git fsck --lost-found` is expensive. Never leave a plan untracked across a session boundary.

**High-integrity zone declaration**: when a plan touches C++ under a strict-zone directory (`AGENTS.md` § Tiered enforcement — `Source/Core/src/{Tracker,Sync,Persistence,Config,Commands}` and their `Source/Core/include/{Tracker,Sync,Persistence,Config,Commands}` header mirrors, `Source/Plugins/Mcp`), note it so the author expects `test-lint-rules.sh --diff` to fail any NEW `no-printf-stderr` / `no-raw-new` / `define-imgui` / overdue-deviation violation (existing grandfathered). Silence a justified case with a `SMATCHET_DEVIATION(...)` comment, not an ad-hoc inline marker.

**Plan revision after implementation**: when work shipped from a plan lands (PR merged, scenario validated, or feature shipped), edit the originating `docs/plans/active/<slug>.md` in the same or next commit to record what actually happened. Mandatory sections to append:

- `## Implementation log` — bullet per shipped commit: `<sha> · <one-line summary>`.
- `## Deviations from plan` — what was changed, removed, or deferred relative to the original plan, with one-line rationale per item.
- `## Verification` — what was actually tested + result (passed / failed / not-run).

A plan that ships without revision is a stale plan. Future agents read these docs as truth; drift between plan and shipped reality is the main cost of multi-week feature work.

**Archive on revision**: the same commit that populates § Implementation log + § Deviations + § Verification (actual) MUST also (a) flip the plan's `> **Status**:` header to `shipped`, (b) `git mv docs/plans/active/<slug>.md docs/plans/shipped/<slug>.md`, and (c) regen the index (`bash agents/scripts/core/test-plan-index.sh --fix`). **No ref-sweep** — cross-references use the **tier-less** form `docs/plans/<slug>.md` (no `active/`/`shipped/`/`deferred/` segment), which `test-plan-ref-integrity` + `test-markdown-links` resolve against whichever tier holds the file (PR #890 — *write every new plan reference tier-less*), so the `git mv` can't break a reference. A legacy ref that still names `active/<slug>` keeps resolving until the plan moves; convert just that one ref to tier-less when you hit it (a `tests-out-of-band` label covers a `Source/Core/` comment-ref touch — the test-delta gate counts comment-only changes as production). The `Status: shipped` flip is the machine-readable signal the archival backstop keys on (below) — and because it's an edit co-located with the impl-log write (the action that reliably happens) rather than a separable filesystem op, it rides along where the bare `git mv` historically dropped off. A plan-doc lives in `docs/plans/active/` only while it's still driving in-flight implementation work; once the post-ship sections are populated the doc is reference material and belongs in `shipped/`. Without this rule, ~62% of post-ship plans drifted into stale-in-place state (empirical sweep 2026-05-28 found 33 of 48 plans in `docs/plans/active/` were eligible for archive but had been left behind).

**Archive-staleness drift is recurring — automated catch (`plan-archival-owed.sh`)**: the rule above is prose-only and was under-followed three times (sweeps 2026-05-28 → 33/48, 2026-05-31 → 16/25, 2026-06-05 → 7/18 shipped-but-unmoved). A mandate alone doesn't hold across many parallel sessions, so a SessionStart safety-net nags until the move happens — `agents/scripts/core/plan-archival-owed.sh` (sibling of `postmortem-owed.sh` / `followup-due-nudge.sh`), advisory/exit-0, never a hard gate.

**Discriminator — key on `Status: shipped`, NOT on impl-log population.** An earlier proposal flagged "any active plan whose § Implementation log carries real commit bullets, and whose cited PRs are all merged." That discriminator is **unreliable and was rejected**: a live multi-batch campaign (e.g. `agentic-backlog-campaign` mid-B5–B11) has a fully-populated Impl-log *and* all its *already-cited* PRs merged while still being live — it would false-positive — and a done plan can still carry a template stub (`decompose-top-20-monoliths`), so impl-log markers misclassify in **both** directions. The robust signal is the explicit `> **Status**: shipped` header an agent sets at closeout (above): exact, zero-false-positive (a live plan is never `Status: shipped`), and it catches the exact observed failure (closeout edits done, `git mv` forgotten). The nudge fires for any `docs/plans/active/*.md` marked `shipped`; the all-cited-PRs-merged probe is a secondary confirmation, not the trigger. Pre-existing active plans authored before the `Status:` field simply aren't flagged (graceful) — they pick up the field when they next ship.

**Audit-doc status sync — a remediation PR updates the source audit doc in the same PR**: a remediation PR that closes findings from a root `*_AUDIT.md` MUST update that doc's per-finding status (a `REMEDIATED` banner / per-finding ✅ table rows) in the **same** PR — the plan tracks the fixes, but the SOURCE audit doc is what a reader trusts, and it otherwise presents every finding as open long after the fixes shipped (the 2026-07-05 reconciliation session existed solely to back-annotate `CPP_CODE_AUDIT.md` + `SECURITY_AUDIT.md`). Advisory backstop: `agents/scripts/core/audit-doc-status-owed.sh` (sibling of `plan-archival-owed.sh`; `--list` / `--nudge` / `--selftest`) warns when a root `*_AUDIT.md` whose companion remediation plan sits in `docs/plans/shipped/` still carries no `REMEDIATED`/✅ marker.

**Deferred plan-file rows at ship boundary**: when the orchestrator labels a numbered row in `docs/plans/active/<slug>.md` § Files to modify as "optional" or skips it at the ship boundary, it MUST in the **same turn** either (a) ship the row, or (b) record both: an entry under `## Deviations from plan` in that plan-doc (`Item N deferred — <one-line rationale>`), and a new open per-entry file `docs/self-improvement/categories/process/<YYYY-MM-DD>-<slug>.md` (one entry per file — see [`AGENT_SELF_IMPROVEMENT.md`](../self-improvement/AGENT_SELF_IMPROVEMENT.md) § Format) when the deferral is follow-up work (not a permanent non-goal). Silent "optional" without deviation + backlog is a process failure — the next session treats the feature as complete.

**Plan stress-test — `grill-with-docs` skill**: before finalising `docs/plans/active/<slug>.md`, invoke the skill to grill the plan against `docs/CONTEXT.md` (glossary) and `docs/adr/` (ADRs). Outputs: refined plan + glossary updates + new ADRs only when hard-to-reverse + surprising + real-trade-off all fire. Smatchet file mapping in `agents/_shared/skills/grill-with-docs/SMATCHET-NOTES.md`.

**Plan template — start from `docs/plans/active/_plan-template.md`**: every new plan-doc is copied from the template, not authored blank. The template stubs every section the project rules require (Context, Approach, Files, **Pillar 1-3 callouts**, **Perf-review-system gates**, Risks, Verification, Implementation log / Deviations placeholders). Sections that genuinely don't apply must be filled with `N/A — <one-line reason>`, not deleted — drives the "did you consider this?" forcing function.

**Plan-doc perf-gate section — mandatory when diff touches `Source/Core/`**: every plan whose recommended-approach diff touches `Source/Core/` MUST include a § Perf-review-system gates section naming which gates from `docs/plans/shipped/pillar-1-2-perf-review-system.md` fire on the PR (PR-fast scenario subset + which scenario directly exercises the changed path; Pillar 2 static scanner; dispatcher drain; visible-cue bucket-E; marker inventory) AND which don't apply with a one-line reason. The section also names the recommended pre-push local check (`scripts/dev/perf-run.sh <scenario>` + `perf-compare.py`) so the author catches regression before CI burns runner time. Orchestrator self-checks this section is present before `ExitPlanMode`; missing section = plan not ready.

**Backlog-archive union merge**: `.gitattributes` carries a `merge=union` driver on `docs/self-improvement/categories/applied.md` only. Parallel slices in multi-slice plans each prepend new archive entries; without union the parallel prepends conflict and need ~5 min of manual resolution per slice (see `docs/plans/tooling-process-backlog-sweep.md` retrospective — 8 of 9 slices hit this). The driver concatenates both sides on conflict — correct for prepend, may interleave date order. To restore the "Latest first" convention after a merge that interleaved dates, run `bash agents/scripts/core/sort-applied-md.sh` (or `--check` to dry-run). The driver is **deliberately not** applied to `process.md` / `tooling.md` (parallel branches DELETE different entries — union would wrongly preserve both deleted blocks) or `AGENT_SELF_IMPROVEMENT.md` (parallel branches MODIFY the same count line — union would garble it). The legacy monolith files still need manual conflict resolution on adjacent-entry archives. **New entries no longer hit this**: the incremental one-entry-per-file slice has landed — new entries are written as their own file `docs/self-improvement/categories/<cat>/<YYYY-MM-DD>-<slug>.md` (distinct paths → adds can't conflict; archiving = removing/moving that one file → deletes can't either), needing no merge driver. See [`AGENT_SELF_IMPROVEMENT.md`](../self-improvement/AGENT_SELF_IMPROVEMENT.md) § Format. The full 135-entry migration stays deferred ([`self-improvement-one-entry-per-file`](../plans/deferred/self-improvement-one-entry-per-file.md)).

**Pre-implementation triage — first action of every "fix existing tooling" slice**: when a plan item says "fix X", "extend X", or otherwise targets pre-existing code, the slice agent's **first** action is to verify the fix hasn't already shipped. Two-step check:

1. **Code state** — `Grep` / `Read` the cited file. If the fix is already in tree, the backlog entry is stale.
2. **Git history** — `git log --oneline -- <file>` plus a grep over `docs/self-improvement/categories/applied.md` for the backlog entry's date or symbol. If a prior PR archived it, the entry is stale.

If either signal fires, archive the backlog entry into `applied.md` with a `Resolution: verified-in-tree (already shipped via ...)` note and skip the slice — do **not** reimplement. The plan's § Approach should pre-flight this triage for any item known to overlap recent work and surface the findings as per-item bullets, so the implementer doesn't redo the search. Empirically (see `docs/plans/tooling-process-backlog-sweep.md` § Approach), pre-implementation triage on a 37-item plan caught 5 items already-resolved on develop in ~5 min total and saved ~3 h of redundant implementation.

**"Not started" / "shipped" / "stale" status is asserted against the MERGED `develop` tree, never against PR presence**: before stamping any work item, plan row, or backlog entry as "not started", "already shipped", or "stale", `grep` / `git show origin/develop:<path>` the **merged develop tree** for the actual code — absence-of-PR ≠ absence-of-code (a sibling/spawned chip may have landed it directly, a squash-merge erases the branch, a feature can ship under an unrelated PR per § Concurrent-worktree isolation). The symmetric error is calling code "shipped" off a merged PR title without confirming the symbol is actually present on develop (CodeRabbit "✅ Addressed" matches keywords, not the diff — AGENTS.md § Merge gates). Both directions are a ground-truth read against `origin/develop` (post-`git fetch`), not against a PR list or a local tracking ref.

## Git/p4 discipline

**Committing to a worktree — pass a LITERAL `git -C <path>`, never a `$VAR`**: the head-drift guard (`docs/harness/claude-code/hooks/guard-head-drift.sh`) inspects the raw, **un-expanded** `tool_input.command` text, so `git -C "$WT" commit …` is denied — it sees the literal string `"$WT"`, can't stat `"$WT"/.git`, and blocks. Only a literal absolute worktree path passes (`git -C /c/Development/Smatchet/.claude/worktrees/<slug> commit …`). The same form is required for the drifted-op deny (a `rebase` / `checkout` / `merge` in a worktree under the integration tree): use the literal-path `git -C <abs-path> <op>`. Set a no-op editor first via `git -C <abs-path> config core.editor true` rather than an interposed `-c core.editor=…` flag.

**Commit-message form is tool-specific — the `@'…'@` here-string is PowerShell-only**: the environment's commit guidance (the `Co-Authored-By:` / `Claude-Session:` footer) is written as a PowerShell single-quoted here-string `git commit -m @'…'@`. When committing through the **Bash** tool (the standard ship-loop path, since worktree commits need `git -C <literal-abs-path>`), that template is **not** a here-string: git-bash parses `@'` as a literal `@` then a single-quoted block, so the subject becomes a bare `@` and the real message is silently mangled (only a `git log -1 --format=%s` readback catches it, costing an `--amend` round-trip). From Bash, pass the body via `-F` instead: `git -C <abs-path> commit -F - <<'EOF' … EOF` (heredoc), or `-F <tempfile>` for the most robust multi-line case. Reserve `-m @'…'@` for the PowerShell tool only.

**PreToolUse git-op guards key on an explicit `-C <path>` per command-position op — never an inferred cwd**: the head-drift / shared-tree guards parse each git op out of the literal command text and resolve its target from that op's own `-C <path>` argument; they do **not** track a `cd` from an earlier command, nor infer cwd from the shell's working directory. So every guarded git op (`commit` / `checkout` / `rebase` / `merge` / `reset`) must carry its own literal `git -C <abs-path> <op>` — a bare `git <op>` preceded by `cd <path>` is guard-invisible (it reads as targeting the current tree and is denied or, worse, mis-attributed). One op, one `-C`; chain them as separate `git -C <path> …` invocations rather than `cd <path> && git …`.

**Destructive git ops in shared worktrees**: before running any destructive git op (`reset --hard`, `checkout --`, `clean -f`, `branch -D`) against a worktree the orchestrator did not personally check out earlier in the same session, run a mandatory 5-step pre-flight via `git -C <path>` from the orchestrator's main worktree (do not `cd`). Parallel agents in other worktrees can — and do — switch the target worktree's HEAD to a different branch between sessions; a stale assumption about "the develop worktree" is what destroys uncommitted work.

1. `git -C <path> branch --show-current` — verify the actual current branch matches the user-named target. If it doesn't, **stop**; the worktree has been reassigned.
2. `git -C <path> status --short` — inventory tracked-modified + untracked files. Any non-empty result means the worktree is load-bearing for a parallel agent; treat as a refusal condition unless explicitly authorised.
3. `git -C <path> stash push -m "<reason>" -- <modified-files>` for any tracked-modified files, regardless of apparent relevance to the asked task. Untracked files survive `reset --hard` but `clean -f` is fatal — pass `--include-untracked` when `clean -f` is part of the plan.
4. Run the destructive op only after 1-3 succeed.
5. Decide whether to `stash pop` (recovers the user's work), leave the stash for the human (when unrelated to current PR), or report the stash hash so the human can pop manually if conflicts arise.

`reset --hard` permanently destroys uncommitted tracked-modified content; it is not in reflog. Branch pointers are reflog-recoverable; uncommitted changes are not. Cross-link: `agents/core/git-janitor.md` § Destructive-op pre-flight (authoritative checklist).

**Re-check HEAD before every commit/push — the watcher swaps branches underfoot**: the `smatchet-merge-watcher` daemon (`agents/scripts/core/merge-watcher.py daemon`; runs continuously as the `SmatchetMergeWatcher` scheduled task) operates on the **same main working copy** the orchestrator uses. When a registered sibling PR hits passing gates, the watcher squash-merges it and its git-janitor step runs `git checkout develop` + `git pull --ff-only` + deletes the merged local branch — in the main clone, **mid-session**. If the orchestrator was on that now-deleted branch, HEAD is silently moved to `develop`, so the next `git commit` lands on `develop` and `git push <branch>` fails with `src refspec ... does not match any`. Therefore: before **any** `git commit` / `git push` in a multi-step task, re-run `git rev-parse --abbrev-ref HEAD` — never trust the branch checked out earlier in the session. **Recovery** when a commit already landed on `develop` (nothing pushed yet): `git checkout -b <new-branch>` (preserves the commit at HEAD), then `git branch -f develop origin/develop` (restores the `develop` pointer while off it — no `reset --hard` needed), verify `git diff --stat develop..<new-branch>` shows only the intended change, then push the new branch + open a fresh PR. Never direct-push the stray commit to `develop`.

**`spawn_task` can run in-place + switch the main tree's branch**: a `spawn_task` chip may execute in the **main** working tree (not an isolated worktree) — checking out a new branch + editing files there — so the orchestrator's own working directory silently switches branches mid-flow (surfaces as "files reverted" reminders + a stale `git log origin/develop..HEAD`). Two rules: (1) **after any `spawn_task`, re-verify `git branch --show-current` + `git status` before the next git op** (same defensive read as the watcher case above — a chip may have moved HEAD). (2) **Avoid `spawn_task` during an active same-repo merge-flow**, or require the chip to run isolated. When a spawned fix and a local duplicate of the same change both exist, dedupe against the merged-PR set (`gh pr list --state merged --search ...`) before pushing — the chip may have already PR'd + merged it, making your local commit a redundant 3rd duplicate.

**Concurrent-worktree isolation — the shared main tree accrues other agents' edits**: ~7-9 agent worktrees run over one shared clone, and sibling agents live-edit the **main** working tree while you work — the session-start "clean" status snapshot goes stale within minutes. Two hard rules:

1. **Never `git add -A` / `git add .`** — stage explicit file paths only. A blanket add sweeps a concurrent agent's uncommitted WIP (and your own large generated artifacts) into the wrong commit. This has shipped one agent's feature bundled under another agent's PR (a sibling editing the *same* file ran `git add` over the shared file holding both changes, merged it, and the first agent's isolated PR became a conflicting duplicate that had to be closed).
2. **Isolate new feature work in a worktree off `origin/develop`** — `git worktree add -b <branch> <path> origin/develop`, reproduce the change there, commit/push/PR from it: zero interference with concurrent writers + a clean PR base. **Re-apply edits from your own old/new strings, never reconstruct them via `git diff`** — a sibling editing the same file entangles its edits into your diff (confirm a clean baseline first: `git diff --stat origin/develop -- <files>` must equal your intended change). Corollary: **before shipping a change made in the shared main tree, re-check `git log origin/develop` / merged PRs for your code** — a concurrent merge may have already carried it, so "check the PR" can legitimately end in "close it, already shipped elsewhere."

**Concurrent interactive sessions — one worktree per session, HEAD-drift guarded**: the same shared-HEAD collision that bites agent worktrees also bites multiple *interactive* Claude Code sessions launched in the **same** clone — a `git checkout` / `pull` / `reset` in one session (or the user's terminal, or a janitor) moves the shared HEAD under another, and that session's next commit lands on the wrong branch (the vsync-on-`plan/multi-grid-tabs` incident). Model + tooling:

1. **Main clone = integration tree** (pinned to `develop`; pull/merge/review only — never feature work, never direct-committed). Every concurrent session gets its **own** worktree under `C:\Dev\trees\<slug>` (override `$env:SMATCHET_TREES_ROOT`) with an independent HEAD. One-liner: `pwsh scripts/dev/worktree.ps1 new <slug>` (creates the worktree off `origin/develop`, wires its `.claude/`, prints the launch line); make it the default with the `nsc <slug>` profile alias (`scripts/dev/new-session.ps1`). Lifecycle: `worktree.ps1 list | rm <slug> [-DeleteBranch] | prune`.
2. **HEAD-drift guard** (`docs/harness/claude-code/hooks/guard-head-drift.sh`, PreToolUse Edit/Write/Bash/PowerShell): records each session's `{branch,sha}` baseline at SessionStart (`session-tree-banner.sh`) and **denies** an Edit/Write/commit when live HEAD ≠ baseline (sha-level → catches same-branch `pull`/`reset` too), plus denies any direct commit to `develop`/`main` in the integration tree. Exempt: a `git -C <path> …` op whose every matched target is a **linked worktree** (`.git` is a file) on a non-protected branch — such an op can't touch this tree, so an integration-rooted session may ship from a worktree it created (suite: `tests/bats/guard_head_drift.bats`). Registry-independent — fires even against a sibling that predates the hook. The Stop hook (`session-heartbeat.sh`) refreshes liveness only (never re-baselines — Stop is per-turn); `resync-head-baseline.sh` (PostToolUse) re-baselines after the session's own HEAD-moving ops.
3. **Recovery after a drift-deny** = `pwsh scripts/dev/worktree.ps1 resync` (accept the current branch) or a fresh worktree + cherry-pick — **never** `git switch` back in a shared tree (that rug-pulls the live sibling). Escapes: `SMATCHET_ACK_BRANCH_DRIFT=1` (drift guard), `SMATCHET_ALLOW_SHARED_SWITCH=1` (aggressor guard `guard-shared-tree.sh`). `git-janitor.sh` **self-excludes the calling session** (`CLAUDE_SESSION_ID`, override `SMATCHET_JANITOR_SELF_SESSION`) and then **hard-defers by default** when any *other* session is live in its tree (`SMATCHET_JANITOR_DEFER=0` forces cleanup; legacy `=1` still defers); the `merge-watcher` daemon's opt-in auto-act likewise defers its `gh pr checkout` spawn while sessions are live in the clone (its server-side squash-merge is unaffected — it never moves a local HEAD).
4. **Fresh-clone bootstrap hole** — the guard hooks live in the **gitignored** `.claude/`, wired only by `setup-harness.sh claude-code`, so on a brand-new clone the drift guard is **INACTIVE until setup-harness has run once** (it cannot self-bootstrap — no committed hook to fire). The standard launcher closes it automatically: `worktree.ps1 new` (hence `nsc`) provisions the integration tree's `.claude/` on first run, then the worktree's. Probe any tree with `bash agents/scripts/core/check-harness-provisioned.sh` (warn + fix on exit 1, OK on exit 0). Full table: [`docs/harness/SETUP.md`](../harness/SETUP.md) § Concurrent-session HEAD-drift guard.

**Pre-edit merged-PR-branch check — never edit on a branch whose PR already merged, or behind develop on the target file** (PR-16 `edit-on-merged-pr-branch-reverts-develop`): editing a file on a feature branch whose PR has **already squash-merged**, then pushing, re-opens the PR (or opens a new one) carrying that file at its **stale pre-merge content** — which on merge **reverts** every change develop received since. The shared-account reality above (item §90: a sibling / the watcher can merge your open PR out from under you) makes this routine: you keep editing what you believe is an open branch, but its PR landed minutes ago. Before the **first** Edit/Write of a session on a non-`develop`/`main` branch (or after any watcher HEAD-swap), confirm BOTH:
   - **The branch's PR is not already merged** — `gh pr list --head "$(git rev-parse --abbrev-ref HEAD)" --state merged --json number` returns `[]`. A non-empty result means the branch shipped; start fresh off `origin/develop` (`git fetch origin develop && git checkout -b <new-slug> origin/develop`) and re-apply, never edit-and-repush the merged branch.
   - **The target file is not behind develop** — `git rev-list --count HEAD..origin/develop -- <path>` (after `git fetch origin develop`) is `0`. A non-zero count means develop has commits to that file your branch lacks; rebase/merge `origin/develop` in first (per § Catch-up sync — default `git merge`) so the edit lands on top of, not under, the newer content. This is the file-scoped guard the HEAD-drift hook (sha-level, whole-tree) does not give you. No clean automated hook point exists today (the check needs a network `gh`/`git fetch` round-trip, too slow for a PreToolUse on every Edit) — run it manually at session start on any non-develop branch; a SessionStart advisory is a backlog follow-up if this recurs.

**Serial multi-slice plan in ONE session — reuse ONE worktree across slices, don't `worktree.ps1 new` per slice**: the "one worktree per session" rule above targets **concurrent** sessions (sibling HEAD rug-pull); it does **not** mean a fresh worktree per *slice* when a single session ships a sliced plan as N serial PRs (each branched off `develop` after the prior merges). A `worktree.ps1 new` per slice re-wires `.claude/` and forces a cold CMake configure that re-fetches every FetchContent dep (~minutes); reuse the same worktree between slices — `git fetch origin develop && git checkout -b feat/slice<N> origin/develop` (or `worktree.ps1 resync`) — to keep `build/` warm (incremental rebuilds, no dep re-fetch). Demonstrated 2026-06-09: the close-gate-gaps slices reused one worktree → zero reconfigure across slices.

**Campaign of PARALLEL sibling PRs — defer the plan-doc impl-log/Verification to the final archival PR; never edit it from a sibling** (PR-16 `campaign-sibling-prs-edit-shared-plan-doc-thrash`): when a plan is shipped as **concurrent** sibling PRs (multiple worktrees in flight at once, as opposed to the *serial* one-session case above), the shared `docs/plans/active/<slug>.md` is a contention magnet — every sibling that appends to § Implementation log / § Deviations / § Verification collides with every other on merge, and the second-to-merge thrashes on rebase. Rules: (1) sibling feature PRs **carry only their code/test diff** — they do **not** touch the plan doc; (2) the plan doc's impl-log + Verification + Deviations are written **once**, in the campaign's **final archival PR** (the one that moves `active/<slug>.md` → `shipped/`), aggregating every sibling's outcome in one place; (3) the `merge=union` attribute on `docs/plans/active/**/*.md` (`.gitattributes`) is the backstop for an unavoidable mid-campaign plan touch, not a license to edit from every sibling. The same shared-file thrash on `tests/CMakeLists.txt` (PR-16 `decomposition-prs-serial-conflict-shared-files` — each test PR appends its TU + curated link-closure to the hand-maintained source list) is handled by its own `merge=union` entry; see § "GLOB auto-registration is unsafe" below for why the cleaner fix (no shared-file edit at all) does not apply.

**GLOB auto-registration of `tests/Core/*.test.cpp` is UNSAFE — keep the hand-maintained list** (PR-16 investigation outcome): the tempting fix for the test-PR shared-file thrash is a `file(GLOB)` over `tests/Core/*.test.cpp` so a new test needs no `tests/CMakeLists.txt` edit. It does **not** work here. `SmatchetTests` links a **curated subset** of `Source/Core/src/*.cpp` (not all of Core), and **each** `*.test.cpp` entry in `add_executable(SmatchetTests …)` is paired with a hand-written link-closure block (its specific production `.cpp` deps + the comment explaining why). A blind glob would compile every test TU with **no** matching link closure → mass unresolved-symbol link failures; it would also break the cpr-free TSan rig, the SQLite-free `_smatchet_pure_sync_test_files` purity set, and the Whisper/AI/agent-debug conditional gating, all of which depend on a TU being explicitly placed in the right block. The existing `file(GLOB)` at the bottom of `tests/CMakeLists.txt` is a **guard only** (assert every on-disk test is text-referenced — the false-green tripwire), never a registration mechanism. The chosen mitigation is therefore `merge=union` on `tests/CMakeLists.txt` (above), which keeps the curated list while removing the manual-resolution cost on parallel appends.

**Leave an isolated worktree standing until its PR is MERGED** (standing user instruction, 2026-05-30): after pushing fixes from a worktree, do **not** `git worktree remove` it — report the path + "leaving until merged" and stop. It may be needed for follow-up CR rounds, re-pushes, or conflict resolution before the watcher merges. Remove only once `gh pr view <n> --json state` shows `MERGED` (or the user says clean up). Cross-link: [`agents/core/git-janitor.md`](../../agents/core/git-janitor.md).

**Verify real tree layout before any path-bearing edit — context can be stale from a watcher HEAD-swap**: the watcher swaps `HEAD` mid-session (seen ~4× in one session), so the `AGENTS.md` paths loaded into session context can reflect an *older* branch's layout. Before authoring any path-bearing plan/doc/edit, confirm each referenced path exists on the checked-out branch — `git ls-files --error-unmatch <path>` (or `git show origin/develop:<path>`), never trust the in-context paths. One session cost a full plan rewrite because context showed a since-renamed source root. Grep the draft for path tokens and confirm each before commit/PR.

**Re-verify ground truth after any tool-batch cancel-cascade or context replay**: when many tool calls are issued in one parallel block and an early one errors, the harness cancels **every** later call in that block — and across a context replay/summary boundary the visible results for those cancelled calls can come back **fabricated** (a phantom workflow edit + worktree + "PR #607" once all appeared to succeed though none existed on disk or GitHub). Mitigations: keep tool batches small (a single early failure voids the rest; prefer sequential calls for ship-critical commit/push/PR steps), and after **any** anomaly — cancel-cascade, replay, or output that looks too convenient — trust only re-verified state (`git rev-parse` / `git worktree list` / `gh pr view <n> --json state`), never the narrative of a prior batch.

**Loss/residue audits diff vs `origin/<base>` (post-fetch) — `ahead`-count and tip-diff are NOT loss signals**: a "what's lost / parked in git?" sweep MUST `git fetch` first, then diff every branch against `origin/<base>` — never a local tracking ref. Siblings and the watcher advance `origin` continuously, so the local base ref goes stale and a branch looks "ahead with unique code" when its work has already shipped. Compounding it: squash-merge leaves a merged branch's `ahead`-count > 0 and its tip-diff non-empty **permanently** (new squash hash + base moving on), so both are routinely misread as loss. The only merge-truth is `gh pr view <head-PR> --json state == MERGED` (or content byte-identical to `origin/<base>`). Distinct from the HEAD-swap and file-contents rules above: this is *which base ref to diff against*.

**An open green PR you left unmerged can be merged by a sibling on the shared account — "I didn't merge it" ≠ "it's still open"**: the GitHub login is shared by all concurrent sessions plus the `smatchet-merge-watcher` daemon, so a sibling session's end-of-session `git-janitor` (squash-merges open PRs in dependency order) or a sibling's "merge when green" can sweep up **any** open PR whose required checks have gone green — including one you just opened and deliberately left unmerged. The merge gates still enforce CI-green / CodeRabbit / no-unresolved first, so a *verified-clean* PR merging this way is benign — but it breaks the assumption that an open PR stays open for later edits. Three corollaries: (1) push everything a PR needs **before** it can go green, or keep it `--draft`, if you intend to add more; (2) when two PRs touch the same file region, expect the second-to-merge to need a rebase and the ordering is **not** under your control; (3) a PR you authored showing `MERGED` / `mergedBy: <shared-login>` that you didn't merge is the shared-account reality, not a gate failure — reconcile against `gh pr view <n> --json state,mergedBy`, don't treat it as loss. Observed 2026-06-16: PRs #1321 + #1326 both opened-but-unmerged, both `MERGED` within minutes of their docs checks going green.

**Catch-up sync for squash-destined PR branches — default to `git merge`, not `git rebase`**: when `origin/<base>` advances while a feature branch is open and the branch needs to sync (CI says `CONFLICTING`, or before opening the PR), run `git merge origin/<base> --no-edit` rather than `git rebase origin/<base>`. Squash-merge collapses the merge commit out of the base's linear history anyway, so the only thing rebase buys is a linear *local* history — moot post-squash — while its per-commit conflict replay is strictly more work than the merge form's single resolution (observed: a 10-commit branch faced ~10 sequential modify/delete replays under rebase vs one under merge). Use rebase only when the branch is destined for a non-squash merge.

**CR-fix commit sequencing — three rules to prevent "fix replied but never landed"**: addressing CodeRabbit (or any reviewer) feedback that touches one or more files MUST follow this sequence, in order. Violating any rule risks the silent-drop failure documented in `639e2a9` (CR triage reply cited file changes that origin never received).

1. **Commit before merge**: `git add <files> && git commit -m "fix(cr): <summary>"` BEFORE any `git merge origin/develop` / `git pull`. The merge becomes a separate commit and the CR-fix commit is independently inspectable via `git show <sha> --stat`. Combined-diff views on merge commits hide single-side-only changes — `git show <merge-sha> -- <file>` produces empty output for changes that exist on only one parent, so it is **not** a valid post-fix verification.
2. **Commit before branch switch**: never `git checkout <other-branch>` with uncommitted product changes — either commit on the current branch first, or use `git worktree add` for the sibling work. `git checkout` auto-stashes silently; the subsequent `stash pop` after sibling commits reapplies the changes as "current state" rather than "missing from history," which the orchestrator routinely misreads as "already shipped."
3. **Post-push verification before claiming**: when the orchestrator replies to CR (or to the user) that fixes have shipped, the reply MUST cross-check at least one cited file via `git show origin/<branch>:<file>` before posting. A 5-second sanity check would catch the silent-drop class. Mechanical assistance: `bash agents/scripts/core/verify-cr-reply.sh <branch> <file>...` diffs the cited files between `origin/<branch>` and `develop` and refuses if any cited file is identical to develop (meaning the fix didn't land).

**Destructive `p4` ops in p4-mode**: when `SMATCHET_AGENT_VCS=p4`, the same defensive principle applies to destructive Perforce verbs (`p4 revert -k`, `p4 obliterate`, `p4 unshelve -f`). Five-step pre-flight in [`docs/perforce/AGENT_FLOWS.md`](../perforce/AGENT_FLOWS.md) § Destructive p4 ops pre-flight: confirm `p4 -ztag info` (client + user), inventory `p4 opened -c default //smatchet/...`, `p4 shelve -c <CL>` any pending unrelated CLs, run the destructive op, then `p4 changes -c <client>` to confirm state. `p4 revert` on a freshly-added file removes it from the workspace too — coordinate before running across shared depot paths.

**Force-push carve-out for Claude Code SDK-spawned recovery and p4 task-stream promotion**: the global `git push --force` ban (and the harness's banned `--no-verify` / `--no-gpg-sign` flags) gets two narrow carve-outs — `git push --force-with-lease origin <branch>` is permitted **only** during API-500 recovery (see [`docs/agent-rules/delegation.md`](delegation.md) § API-500 mid-run recovery) when the orchestrator is amending an unpushed-since-API-500 commit on:

1. A Claude Code SDK-spawned worktree branch matching `claude/<id>/*`, OR
2. A Perforce-task-stream-promoted branch matching `agent/<task-stream-id>/*` (created by `agents/scripts/project/p4-task-stream-to-pr.sh`).

The `agent/<id>` carve-out was deleted post-`ClaudeCodeLocalRunner` (per v1 of `docs/plans/shipped/github-tracker-backend.md`) and is reinstated here for the p4-task-stream surface: those branches are recovery-style throwaways, created by the script after a successful shelf submit, and they should never carry non-self commits. The `smatchet-merge-watcher` host daemon (per `docs/plans/shipped/smatchet-merge-watcher.md`) runs in-process, not as a spawned subprocess, so it has no worktree branch that would need this carve-out.

**Exclusion list — top-level-prefix-only** (an exclusion triggers only at the first path segment): `develop`, `main`, `chore/*`, `feat/*`, `fix/*`, `docs/*`, `wip/*`. Branches under `claude/<id>/*` and `agent/<task-stream-id>/*` are permitted regardless of the nested slug prefix (a slug like `feat-perf-fix` under `agent/perf-detective-01/` is fine — the `feat-` prefix is below the protected first segment).

Additional conditions for the carve-out to apply: ahead-range contains zero non-self commits; `--force-with-lease` (never bare `--force`). ADR [0005](../adr/0005-force-push-carve-out-for-spawned-agent-recovery.md) (Withdrawn as historical) covers the `claude/<id>` rationale; ADR [0008](../adr/0008-p4-gated-ship-loop.md) records the `agent/<task-stream-id>` extension + exclusion-list rewrite.

## Cadence and verification

**Verification automation — zero manual steps**: `test-author` converts every manual verification step into a deterministic CLI / scenario / screenshot / sanitizer / ImGui-Test-Engine assertion. Three invocation points: (1) plan-time audit of `docs/plans/active/<slug>.md` § Verification, (2) post-first-round sweep, (3) every agent handoff that mentions a manual step. Unified runner: `bash scripts/dev/test-all.sh` (auto-enrols `scripts/dev/test-*.sh`). Manual residue without a `docs/self-improvement/AGENT_SELF_IMPROVEMENT.md` entry (category `tooling`) is a fail. "Truly interactive" is never the final answer — bucket E (ImGui Test Engine) is wired (see `docs/plans/shipped/imgui-test-engine-bucket-e-execution.md`; first test at `tests/ui/views_columns_reorder.test.cpp`; run via `cmake --build --preset ninja-ui-test-msvc`). Bucket details in `agents/core/test-author.md`.

**Schema-version bumps**: when a feature requires a config / cache schema-version bump, hold the bump until the feature is verified end-to-end. Do not commit interim version bumps as the feature evolves — squash or amend. The shipped version should be exactly one higher than the previous shipped version, not N higher because of intermediate iterations.

**Trivial-visual-only change envelope**: a change qualifies as **trivial-visual** when **every** condition holds — (a) write set is a strict subset of `{Source/Core/src/SmatchetTheme.cpp, Locales/*.json, ImGui style constants (ImVec4 / ImGuiStyle literals)}`; (b) diff shape is literals-only (no API surface, no header touch, no schema, no control flow, no new symbols); (c) zero touch under `Source/Core/include/` / `Source/Plugins/` / `cmake/` / `CMakePresets.json`. Under this envelope the orchestrator may ship after: (1) `cmake --build --preset ninja-iter-msvc --target SmatchetStandalone` builds, (2) `ninja-test-msvc` ctest passes **if** a pure-logic test touches the changed file, (3) **NO** `ninja-ui-test-msvc` bucket-E run, (4) **NO** isolated worktree — use the main worktree with `git stash` race-recovery if a concurrent agent appears. Bucket-E coverage gets deferred to a single post-batch run before merge, or to the test backlog. Saves ~10× wall-clock on visual-only PRs (palette retunes, locale string fixes). Any condition fails → fall back to the full build + test-all + bucket-E loop.

**Build / ctest cadence — slice-boundary only**: within a single agent turn (= one logical slice), invoke `cmake --build` and `scripts/dev/test-all.sh` **at most once each**, and only after the implementation is complete. Mid-slice rebuilds and mid-slice ctest runs are wasted work — Ninja is already incremental and the doctest rig is fast at the slice boundary but expensive when amortised across N edits.

**New-file delta-lint reflex — before push, when the slice ADDS a first-party file.** A bare `cmake --build` (or the `build-and-run.sh --build-only` build-verify shortcut) proves compilation but runs **none** of the comment-noise / function-size / strict-zone delta gates — and a brand-new file is exactly where a comment-blank-run, a `// ====` banner, or a `//  * `-bulleted header slips in undetected (it has no pre-existing-violator grandfathering to hide behind, so every line is fresh and gated). Whenever a slice creates a new `Source/**` / `tests/**` C++ file, run the delta gates locally before push: `bash scripts/dev/pre-ship.sh` (full gate, auto-`intent-to-add`s untracked files so they're visible to the diff), or the build-then-delta-lint shortcut `bash scripts/dev/verify.sh` / `build-and-run.sh --build-only --verify`. New files are invisible to `git diff <base>` until `git add --intent-to-add`, so a gate run before the first `git add` false-passes them (PR #953) — `pre-ship.sh` / `verify.sh` handle that for you.

**Code-review before every commit** (user-mandated 2026-06-07): every commit's diff gets a `code-review` agent pass BEFORE it lands — orchestrator-direct commits review the staged diff; agent-produced branches get the review on the PR diff before merge (the orchestrator dispatches it at PR-open). Delta commits answering a review get a scoped delta re-review. The review is advisory-blocking: Critical/High findings block the commit/merge until fixed or explicitly waived by the user. The practice caught 6 HIGH findings across PRs #959/#962 on its first day.

**Gate output is consumed by verdict, never by `tail`**: read a gate/test suite's result from its exit code (`bash scripts/dev/test-docs.sh && …`) or by grepping its verdict lines (`grep -E "FAIL|Failed: [1-9]"`) — never by eyeballing `| tail -N`. A truncated tail shows only the LAST sub-test's "Passed/Failed" line and hides earlier red sub-tests (this shipped a red doc-validation suite to PR #946; entry: `categories/process.md` 2026-06-07).

**Ad-hoc backlog recounts must be filename-aware — `grep -rh … | grep -v applied.md` is a no-op filter**: `-h` strips the filename from every line, so the `applied.md` exclusion matches nothing and every archived entry counts as live (this twice produced a phantom list of ~20 "open" P1s that were all already fixed + archived). Recount with `grep -rHn` and exclude by the `/applied.md:` path prefix, AND pair each header hit with its entry's `Status:` line (a header line alone says nothing about open/applied) — or just use `bash agents/scripts/core/test-backlog-counts.sh --list` (per-file, no `-h` bug) for category totals.

**Never gate a build/configure/test decision on a command piped into `grep` / `tail` / `head` — the pipe masks the producer's exit code**: in a pipeline `cmd | grep …`, `$?` is the exit status of the **last** stage (`grep`), so a failed `cmake --build` / `cmake --preset` / `ctest` whose output happens to match (or whose `grep` finds nothing) reports the wrong rc and a real red passes as green. When you must filter a build/configure/test command's output AND key a decision on whether it succeeded, either capture the producer's rc explicitly (run it alone, read `$?`, then filter a saved log) or set `set -o pipefail` so any failing stage fails the pipeline. The verdict rule above governs how to *read* a suite result; this one governs not corrupting the rc on the way to that read.

**Before chasing a red REQUIRED check, rule out staleness-vs-develop**: a required check can red because the branch is **behind develop**, not because the diff broke anything — develop moved (a sibling / the watcher merged) after the failing run started, and the run executed against an out-of-date base. Before debugging the failure, compare the failing run's start time against develop merges since the branch's merge-base; if develop has advanced past what the run tested, `git merge origin/develop --no-edit` (per § Catch-up sync) and re-run **first** — a stale red routinely clears on a fresh run with no code change. Only treat the failure as real once it reproduces on a run whose base includes current develop.

**Re-confirm a CI-symptom backlog entry reproduces before coding a fix — entries go stale**: any backlog item whose trigger is a CI symptom (a named check red, a flaky lane, a sanitizer report from CI) MUST be re-validated against the **most recent run that actually executed that step** before any fix is written — pull the failing step's log (`gh run view <id> --log` / the run's check annotations) and confirm the symptom still reproduces on current develop. CI symptoms decay: the underlying flake may have been fixed by an unrelated merge, the lane may have been retired, or the check may already be green. Coding a fix against a symptom that no longer reproduces wastes a slice and can re-introduce churn. If it no longer reproduces, archive the entry `verified-resolved (no longer reproduces as of run <id>)` instead.

**P4-gated loops carve-out**: when running the small-change variant of [`docs/agent-rules/ship-loops.md`](ship-loops.md) § P4-gated ship-loop, the loop sequence has a legitimate `[smoke build] → [shelf] → [full tests]` phase split. The shelf-review boundary is a real phase transition (user-in-the-loop), so the pre-shelf smoke build (`ninja-iter-msvc` target `SmatchetStandalone`) and the post-shelf test-rig build (`ninja-test-msvc`) count as **distinct gates within the slice** — at-most-once per gate, not at-most-once total. The "wasteful mid-implementation rebuilds" rule the cadence targets still applies; the user-review boundary is not "mid-implementation".

**Perf slice-boundary auto-run — scenario-aware**: when a slice's write set touches files in the curated diff→scenario map at [`agents/core/perf-gatekeeper.md`](../../agents/core/perf-gatekeeper.md) § "Curated diff → scenario map", the orchestrator runs the affected scenario(s) at slice boundary (right after the build + ctest pass) and surfaces the top-N rows inline. No need for the user to ask "how is the performance" — Pillar 1 evidence shows up automatically next to the regular slice output. Mechanically:

```bash
bash scripts/dev/perf-run.sh <scenario>  # writes build/perf-runs/<scenario>-<ts>.json
# When docs/perf/baselines/<scenario>.dev.json exists, also:
python scripts/dev/perf-compare.py docs/perf/baselines/<scenario>.dev.json \
    build/perf-runs/<scenario>-<ts>.json --markdown-only
```

When no `dev`-host baseline exists yet (the common case during phase rollouts before bootstrap), the perf-run output is reported on its own as evidence and the orchestrator notes `MISSING_BASELINE` rather than silently passing — same contract as `agents/core/perf-gatekeeper.md` § Hard rules. The CI gate at `.github/workflows/perf-pr-fast.yml` handles the per-PR enforcement (auto-bootstraps the `ci-windows-latest` baseline on first run, fails subsequent PRs on regression beyond `docs/perf/regression-policy.json`). Local slice-boundary runs are for fast feedback; the CI gate is the merge-block. Skip the local run when the slice ALSO qualifies for the pure-docs skip below — there's no code to measure either way.

**Pure-docs slice skip**: a slice whose write set is strictly within the pure-docs allow-list (`docs/**`, `backlog/**`, `agents/scripts/**`, and **any `*.md` at any depth** — including the per-subsystem leaf docs under `Source/Core/src/<ctx>/{AGENTS,CONTEXT,README}.md` and root `CONTEXT-MAP.md`) skips **both** `cmake --build` and `scripts/dev/test-all.sh` entirely — Markdown is never compiled, so there is no executable code to verify. (The same `*.md`-is-docs rule gates the Windows build / coverage / perf CI lanes: `build-and-test.yml`'s `changes` job classifies `*.md` as docs, and `coverage.yml` / `perf-pr-fast.yml` carry a `'!**/*.md'` path-exclusion so a leaf-doc-only change never spins up a build.) Discriminator (mirrors the end-of-session FF-clean gate at `agents/core/git-janitor.md` § FF-clean docs-batch exception § Pure-docs sub-exception):
```bash
bash agents/scripts/core/is-pure-docs-diff.sh develop && echo "pure-docs (skip build + test-all)" || echo "needs full gate"
```
Exit 0 → skip both gates. Exit 1 → falls back to the standard slice-boundary cadence above.

**Pure-docs is NOT zero-gate — run the doc-validation mirror.** Skipping `cmake --build` + `test-all.sh` does **not** mean a docs slice ships unverified. The paths that qualify for the skip (`docs/**`, `AGENTS.md`, plan files) are exactly what the **Doc validation** CI workflow ([`.github/workflows/doc-validation.yml`](../../.github/workflows/doc-validation.yml)) gates — anchor resolution, agent-contract parity, shipped-plan-`INDEX.md` sync, plan-ref integrity, kebab naming, portable purity, agent discovery. That workflow is **not** part of `test-all.sh`, so a pure-docs slice that skips `test-all.sh` has **no** local coverage of the gate it is most likely to trip. Before pushing any pure-docs / docs-touching slice, run the local mirror:
```bash
bash scripts/dev/test-docs.sh
```
It runs the 7 doc-validation steps 1:1 with the workflow (<2s, no compile; many sub-checks self-fix, e.g. `bash agents/scripts/core/test-plan-index.sh --fix`). `test-docs.sh` is also auto-enrolled by `test-all.sh` (matches `scripts/dev/test-*.sh`), so mixed code+docs slices get the same coverage through the normal gate. Motivating miss: a docs-only PR went red on `test-plan-index` + `test-plan-ref-integrity` because an upstream plan-move left a stale `INDEX.md` row and dangling `active/` citations — both caught instantly by `test-docs.sh`, neither by `cmake --build` or `test-all.sh`.

**Repairing dangling markdown links — trust the checker as the enumerator, not a grep.** When fixing broken relative links, let [`agents/scripts/core/test-markdown-links.sh`](../../agents/scripts/core/test-markdown-links.sh) drive the work — its `LINK_RE` matches every `[label]`-then-`(href)` link form; a hand-rolled grep anchored on `./` / `../` misses **bare-relative** hrefs (`](archive/foo.md)` with no leading `./`) and undercounts the breakage (PR #1279: a first grep pass found ~40, the checker then caught 3 stragglers). Two checker facts prevent false edits: it **skips fenced code blocks** (template placeholders like `](./<plan>.md)` inside ` ``` ` / `~~~` are safe) and **tier-less plan paths** `docs/plans/<slug>.md` auto-resolve across `active`/`shipped`/`deferred`. It scans each changed `.md` **in full** (whole-file, not per-line-delta), so touching one frozen-archive line pulls all that file's pre-existing breaks into scope — **split frozen-doc link repair into its own PR**. Loop edit → run → fix-from-violation-list until `Failed: 0`.

The same allow-list governs both surfaces (in-session orchestrator + end-of-session `git-janitor`) so a slice that qualifies in-session also qualifies for the FF push without re-evaluation. Deny-list paths (`agents/**`, `scripts/**`, `tests/**`, `.gitignore`, `.github/**`, `CMakePresets.json`, `CMakeLists.txt`, any C++/Lua/Python/shell source) keep the full gate — even a single deny-list file in the diff disqualifies the slice. CI ([`.github/workflows/build-and-test.yml`](../../.github/workflows/build-and-test.yml) `paths-ignore`) and CodeRabbit ([`.coderabbit.yaml`](../../.coderabbit.yaml) `auto_review.enabled: true`) handle the same diff orthogonally — CI skips on doc-only paths via its own `paths-ignore`; CodeRabbit reviews every PR including doc-only ones.

**Stale-read recovery on `Edit`**: `Edit` may error with `File has been modified since read, either by the user or by a linter` when (a) a concurrent orchestrator in a sibling worktree edited the same file, (b) a `PostToolUse` hook (e.g. `lint-cpp.sh`'s `clang-format -i`) rewrote the file between your `Read` and `Edit`, or (c) the user touched the file in their editor.

Canonical recovery — always works, no manual conflict resolution:

1. Re-`Read` the file at the same path (and same `offset` / `limit` if you used them).
2. Diff your intended change against the new content — verify the `old_string` you were going to pass still exists verbatim. If a hook reformatted it (trailing whitespace stripped, line wrapped), update `old_string` to the new exact form.
3. Re-`Edit` with the refreshed `old_string`.

Hot files (high race rate; expect to re-Read at least once per edit):

- `docs/plans/active/_plan-locks.generated.md` (every orchestrator that takes / releases a plan-lock touches it)
- `AGENTS.md` (multi-agent doc edits)
- `docs/self-improvement/categories/*.md` (legacy monolith — still hot for archives / manual edits of existing entries; **new entries avoid this** by landing as their own per-entry file `categories/<cat>/<date>-<slug>.md`, so concurrent adds touch disjoint paths)

Do NOT use `replace_all: true` as a "force-write" — it amplifies race-collision risk by widening the rewrite surface. Stick to the targeted Re-Read + Re-Edit pattern.

The harness maintains a `.claude/.tree-dirty` sentinel file written by `.claude/hooks/lint-cpp.sh` on every first-party `.cpp` / `.h` edit and cleared automatically by the `PreToolUse:Bash` hook (`clear-tree-dirty.sh`) the moment any `cmake --build …` invocation is about to run. Agents reading the sentinel know edits have happened since the last build — if your implementation isn't done yet, defer the build.

The deferred lint pipeline (`.claude/hooks/lint-cpp.sh` PostToolUse → `.claude/hooks/lint-cpp-drain.sh` Stop) follows the same principle for `cppcheck` / `clang-tidy` / dual-target syntax: heavy passes drain once at end-of-turn against the dedup'd set of edited files, not after each Edit/Write. `clang-format -i` still runs inline. Escape hatches: `SMATCHET_LINT_INLINE=1` reverts to per-edit, `bash agents/scripts/core/lint-flush.sh` drains explicitly mid-turn. The trivial-visual-only envelope above is a special case of this rule.

## Context compaction

**Target ~80% of the context window** — compact / summarise the conversation when it reaches ≈80% of the active harness's context window, preserving headroom for the in-flight turn rather than waiting for the hard limit. This is a **harness-agnostic operating convention**, not a portable config key: compaction is a runtime feature of the harness, not agent-controllable, so each harness enforces the target through its own mechanism (or, where it exposes no knob, the operator applies it by hand).

| Harness | Mechanism for the ~80% target |
|---|---|
| Claude Code | Built-in **auto-compact**, toggled in the interactive `/config` menu (Auto-compact on) — it fires automatically as the context approaches the limit. The trigger point is **internal and not a settable numeric knob**, so the precise ~80% target is *not* configurable via settings; for a chosen point, run **`/compact`** (optionally `/compact <focus>`) by hand. NB: there is **no** `autoCompactEnabled` / `autoCompactWindow` settings key — auto-compact is a `/config` boolean, not a numeric `settings.json` value (do not add those keys; they are silent no-ops). |
| Codex / OpenAI Agents | Built-in auto-summarisation; threshold not user-tunable — convention is advisory. |
| Cursor | Built-in auto-summarise; not tunable — convention is advisory. |
| Aider | Manual (`/tokens`, `/clear`) — operator applies the 80% target by hand. |
| Generic CLI / script | Operator or wrapper trims / summarises history at ≈80% of the model's window. |

Where the harness offers no threshold setting, treat this as a documented operating convention, not an enforced gate. Per-harness tool/equivalent table: [`docs/harness/capability-adapter.md`](../harness/capability-adapter.md).

## Triggered follow-ups

Some backlog entries are **deferred follow-ups gated on a future condition** ("re-measure after ~10 PRs", "after ~20 PRs flip the gate", "once plan X ships"). Rather than relying on manual triage to remember the condition, an entry in `docs/self-improvement/categories/*.md` can carry an optional, grep-parseable `Triggered-follow-up:` line; [`followup-due-nudge.sh`](../../agents/scripts/core/followup-due-nudge.sh) (a SessionStart nudge + a `git-janitor` closeout step) fires it automatically when the condition is met. Grammar + the four `when=` kinds (`pr-count` / `date` / `plan-shipped` / `file-age`): [`AGENT_SELF_IMPROVEMENT.md`](../self-improvement/AGENT_SELF_IMPROVEMENT.md) § Format.

**Lifecycle:**

1. **Author** the entry with `… fired=never` (the unfired sentinel). Triggers live ONLY on backlog entries, never in plan-docs — a trigger authored in `docs/plans/active/<slug>.md` dies when the plan archives to `shipped/` (the exact loss that motivated this).
2. **Fires** — when the `when=` condition becomes true, the nudge surfaces the entry's `action` + `baseline`, priority-sorted (P0→P3). The nudge is **read-only** (never edits a tracked file), so a due-but-unaddressed entry re-nudges every session until acted on — same "keeps nagging until resolved" semantics as `postmortem-owed`.
3. **Act + stamp** — when the orchestrator does the follow-up it stamps `fired=<date>` on the entry **via the normal PR flow** (not the script), suppressing further nudges. Then close the entry or spawn a successor.

Degrades safely: `gh`-unavailable / ambiguous → SKIP (never a false fire, never a hard fail); a malformed `when=` emits a WARN. Spec: [`docs/plans/shipped/triggered-followup-tracking.md`](../plans/shipped/triggered-followup-tracking.md).

## Where new rules go

Authored fresh per [`docs/plans/shipped/agents-md-reduction.md`](../plans/shipped/agents-md-reduction.md) D7 — the meta-rule that drives where future rules land so the AGENTS.md ↔ `docs/agent-rules/` split doesn't drift.

1. **Build / language / quality 1-liner that every agent must see** (Build, Language, Layout, Logging, Lint, etc. shape) → `AGENTS.md` § Project rules inline. These are 1-line invariants; cross-link follow would cost more than inline reading.
2. **A rule that fits within an existing extracted topic** (`merge-gates.md`, `quality-pillars.md`, `ship-loops.md`, `process-rules.md`) → add to that file. Update the corresponding `AGENTS.md` stub only if the new rule changes the load-bearing essence (the WHAT + must-know invariants the stub names).
3. **A new topic that doesn't fit any existing file AND is > 30 lines** → create new `docs/agent-rules/<topic>.md` (kebab-case) + add a 5-12 line load-bearing stub to AGENTS.md per the Stub format rule (D6 in the reduction plan).
4. **A new topic that doesn't fit AND is ≤ 30 lines** → put it in `process-rules.md` (the catch-all) rather than fragmenting into another file. Fragmentation has a fixed per-file overhead (stub maintenance, cross-link rot, agent context switch); keep it bounded.
