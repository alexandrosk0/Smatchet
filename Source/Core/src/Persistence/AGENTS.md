# Persistence subsystem — agent rules

Scoped rules for `Source/Core/src/Persistence/` (SQLite-backed local cache, audit trail, field-edit audit source). Global rules stay in the root [`AGENTS.md`](../../../../AGENTS.md).

This is a **strict lint zone** (`agent-layer/docs/agent-rules/cpp-rules.md` § Tiered enforcement).

## Invariants

- **SQLite schema changes are additive only.** Add columns/tables; never drop, rename, or change the type of an existing column in place. The local cache is a long-lived per-user file — a destructive migration corrupts or discards a user's offline state. Flag any `DROP` / `ALTER ... RENAME` / type change. A genuine schema evolution needs a versioned migration step, not an in-place edit.
- **All SQLite work is off the UI thread.** `SQLite::Database` calls run on a worker thread, never inline in a render frame; the worker posts only the result back via `MainThreadDispatcher::PostToMainThread`, and chunks large writes (`SmatchetChatPersistWorker` is the reference pattern; this is the Pillar-2 UI-thread rule — see `Source/Core/src/Ui/AGENTS.md`).
- **The chat-history hydrate and Lua `get_ticket` never read SQLite on the UI thread.** `HydrateFromConfigOnce` loads the AI chat history on a worker. On the UI thread `get_ticket` answers from the focused view's in-memory snapshot (`GetActiveTicketsSnapshot`) and returns `nil, "Ticket not loaded in the focused view"` on a miss; worker and MCP Lua states still read the cache. Click-driven `QueueCreateOffline` (a single INSERT) is a named, measured exception, not moved yet.
- **One connection, one lock.** `LocalCacheManager` has one `SQLite::Database` (`db_`, private) and one non-recursive `connMutex_`. Every public method holds a `ConnGuard` for its whole operation, and the connection is reachable only through `conn(guard)`, so code that touches it unlocked does not compile. Every multi-statement write runs through `RunTxn_` (guard per attempt, bounded BUSY retry); its body can run again, so it returns its outputs and does no non-SQLite side effect. A helper that runs inside a method takes the guard as its first parameter; a public method never calls another public method (a same-thread re-entry throws `std::logic_error`; use the underscored witness form, e.g. `hasCacheMetaFlag_`). A new method opens with `const ConnGuard guard(*this, "Op"); SQLite::Database& db = conn(guard);`. Check: `rg -n 'SQLite::Database&' Source/Core/src/Persistence | rg -v 'ConnGuard&|= conn\('` prints only the `RunTxn_` return-type line in `LocalCacheManagerInternal.h`.
- **The cache opens on a worker, and a failed open degrades; it never throws out of boot.** `Initialize` raises the recreate gate (state `Opening`) and `LaunchStartupCacheOpen_` opens the file, runs the one-time migrations and legacy sweeps and publishes the cache from `FinishStartupCacheOpen_` on the UI thread, which does no SQLite. Until then `Cache` is null, sync holds its requests, and an enqueue is refused with "still opening"; a caller with no frame loop (the one-shot CLI, a test) uses `WaitForLocalCacheOpen`. A constructor failure (an unwritable or missing directory, a locked file, too old an SQLite; a corrupt file is rebuilt inside the constructor and never reaches it) publishes a `:memory:` cache with `LocalCacheState::SessionOnly`: reads and sync keep working, every durable enqueue is refused with its reason (`CacheEnqueueBlock`, `IOfflineQueueDeps::EnqueueBlock`) instead of being lost at exit, Recreate is refused, and `StartReopenLocalCache` tries the file again. Anything new that enqueues asks `EnqueueBlock()` before it takes the cache.
- **The cache file has one planned location, and an older file is copied there, never moved.** `PlanLocalCacheDbPath` (`LocalCacheDbPathPure.h`, called from `AppController::PlanLocalCacheLocation_`) resolves a relative or empty configured path against the user-data directory, not the process working directory, and lists the older places (the working directory, the runtime asset directory, the shared user-data directory) as import candidates; an absolute path, `:memory:` and `SMATCHET_USER_DATA` have none. On the open worker, `ImportLegacyLocalCacheIfNeeded` (`LocalCacheLocationMigration.{h,cpp}`) runs only when the target does not exist: it opens each candidate `OPEN_READONLY`, picks the one with live queue rows (then tickets, then the newest), copies it with SQLite's online backup into a temporary file beside the target, `quick_check`s it and publishes it with a rename that cannot replace a file. The import never writes, moves or deletes a legacy file (it is probed and copied read-only, `trusted_schema` off, interruptible), so an older build or a switch back to the old storage mode keeps its own copy. Every first creator of the target (an import and a `CreatedEmpty` start alike) holds `<target>.init-lock`; a copy that cannot be made now (a lock, a publish failure) opens the older file for this session (`LocalCacheStatus::UsingLegacyPath`) with `OpenOptions::RebuildCorruptFile = false`, so a corrupt borrowed file is never moved aside or rebuilt (the open fails and the session is session-only); it is the session's live cache, written like any cache (additive schema only). While that flag is up Recreate is refused and the retention sweep and vacuum must not run. A file unreadable for a non-corruption reason (a lock, permissions, I/O) is never called corrupt, and `Deferred` (another process is importing, or nothing is readable and no lock could be taken) opens nothing durable, so this session never writes into a file another process is copying: the target is only ever created under the init-lock. A candidate is eligible only if it is a regular file (never a FIFO, device or symlink), at most 2 GiB and, on POSIX, owned by the current user; a copy holding a trigger, a view or a virtual table is rejected like a damaged file, and every cache connection runs with `trusted_schema=OFF`. Read-only and worker-only: never call the import from the UI thread.
- **A corrupt file is quarantined, rebuilt, and its queues salvaged best effort.** `RebuildFreshAfterCorruption` moves the damaged file and its sidecars aside (`<db>.corrupt-<ts>`), opens an empty cache and calls `SalvageFromQuarantine_` (`LocalCacheManager_Salvage.cpp`), which attaches a working copy and copies `kSalvageTables` (the `pending_*` queues, their `*_dead` twins and `cache_meta`) column by column, with a row-by-row fallback; a table that cannot be read or whose shape does not match is listed in `LocalCacheRecoveryReport::IncompleteTables`, never dropped silently. A salvaged `sending` action becomes `ambiguous`, as on any open. `kSalvageTables` must list every new queue table, or its rows are lost on a rebuild. The report is stored as the `cache_meta` value `last_corruption_recovery_v1` (a mutable value, not a set-once flag, so it is only read through `ReadLastRecoveryReport`) and shown once as a notice on the launch that rebuilt, and in Preferences afterwards. The salvage runs inside the constructor under its guard, never through `RunTxn_`.
- **Audit trail is append-only + redacted.** `BackendAuditTrail` entries are begin/result pairs; secrets/tokens go through the redaction helpers before they land. Don't log raw payloads.
- **Offline actions persist in `pending_actions`.** Comments, worklogs and watches saved while offline are rows of one generic queue keyed by `kind` (`PendingActionTypes.h`), with a `pending_actions_dead` twin; add a new `kind` rather than a new table. The UI reads the service's published snapshot, never the table per frame. A `sending` row also records who claimed it and when (`claimed_by`, `claimed_at`; additive columns): only a transition to `sending` writes a claim and every other write clears it, and the open turns a `sending` row into `ambiguous` only when its claim is at least `kMaxSendingClaimLeaseSec` old, so a second Smatchet starting up never flips a send the first is making.
- **`backend_key` names a tracker site and account** (`Config/CacheBackendKeyPure.h`, #2268), not a tracker kind. Rows written under the legacy kind keys (`"Jira"`, `"Jira:<host>"`, `"Plane"`, …) were moved once by `RunOneTimeCacheIdentityRekey` (`cache_meta` flag `cache_identity_rekey_v1`, `LocalCacheManager_CacheIdentity.cpp`). A new table keyed by backend must be added to its table lists.
- **Offline read-side lookups persist in `lookup_cache`.** Store them as (backend_key, kind, cache_key) → JSON rows through `ILookupCache` (backend-namespaced like the ticket tables); add a new `kind` rather than a new ad-hoc JSON file. Reads and writes run on workers; the owning service keeps an in-memory copy for the UI thread. Kinds today: `workflow_transitions` (`IssueTransitionsCacheService`), `project_components`, `users`, `editmeta_project_type` and `projects` (`LookupPayloadsPure.h`; `projects` is written and read by `ProjectListLookup`). `editmeta_project_type` rows are keyed by (project, issue type) and written only from a representative result (`EditMetaScopePure.h`); the legacy `editmeta_type` kind is only deleted, once per backend, never read or written. A service loads its saved rows once per backend through `smatchet::offline::LoadSavedRowsOnce` (`StoreLoadLatch.h`), never overriding a value fetched live meanwhile.

## Before you edit

- The cache owns `CachedTicket` (the in-memory + on-disk issue row) and `PendingCreate` / `PendingFieldEditRecord` (offline-queue payloads). Tracker reads/writes these; Sync replays them. A schema touch here ripples to both — check `Source/Core/src/Tracker/` and `Source/Core/src/Sync/`.
- **A cached ticket has two storage axes.** `CachedTicket::fieldValues` maps a field id to its display string; the parallel `fieldRichValues` maps the same id to rich content (ADF JSON or HTML). On disk they are `ticket_field_values_v2` and `ticket_field_rich_values_v2`. A new cached field type uses one of them; don't invent a third storage axis.
- **A new queue table mirrors the existing ones.** Prefer a new `kind` in `pending_actions` (Invariants). A genuinely new queue copies the `pending_creates` / `pending_field_edits` shape: `id`, the payload, `backend_key`, `attempts`, `last_error`, `created_at`, plus a `<table>_dead` twin carrying `dead_id`, `original_id`, `archived_at` and `terminal_reason`. Later columns go in through `AddColumnIfMissing`.
- **A change the additive rule forbids needs an approved plan.** Dropping, renaming or retyping a column, or changing a primary key, needs an approved § Interface contracts entry in the active plan that names the versioned step (the `tickets_v2` family is the precedent: a new table set, the legacy tables left on disk unused). Without one, stop and ask the user.
