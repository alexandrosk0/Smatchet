# Sync subsystem — agent rules

Scoped rules for `Source/Core/src/Sync/` (ticket sync, offline-queue replay, conflict/merge resolution). Global rules stay in the root [`AGENTS.md`](../../../../AGENTS.md).

This is a **strict lint zone** (root `AGENTS.md` § Tiered enforcement zones).

## Invariants

- **Every backend write goes through the offline queue.** Creates and field edits enqueue via `OfflineQueueService` (`PendingCreate` / `PendingFieldEditRecord`), and comments, worklogs and watches via `PendingActionQueueService` (`PendingActionRecord`), so a change made offline replays on reconnect. A write path that calls the backend directly — skipping the queue — drops the user's edit when they're offline. Flag it.
- **Queue first when offline.** When the connectivity probe says the tracker is unreachable (`IsOfflineState`), a write persists to the queue immediately (`RouteWrite` → `QueueImmediately`, e.g. `FieldEditPipelineService::CommitOrQueue`) instead of first spending the HTTP retry window; online, a retryable failure still falls back to the queue. Queueing never fetches editmeta, and the SQLite enqueue runs on the worker, never the UI thread.
- **A replayed action is sent at most once.** `PendingActionQueueService` persists `sending` before each request; a row found `sending` on open, or whose send failed after the request went out, is `ambiguous` and is checked against the tracker before it is resent (`PendingActionPolicyPure.h`). An action that cannot be checked (a worklog) goes to `needs_review` for the user — never a blind resend.
- **Replay reuses the live pipelines.** Draining a `PendingCreate` reconstructs the `IssueDraft` (`IssueDraftHelpers::FromJson`) and runs it through the same `IssueCreatePipeline::Run` as a live create; a `PendingFieldEditRecord` replays through the same `UpdateField`. A queued sprint edit (`{"sprint_add": id}`) replays through the same `AddIssueToSprint` call as the live edit, and an estimate through the `timetracking` field; both payload shapes live in `TrackerFieldPayloadPure`, which conflict resolution also rebuilds them with. Don't fork a separate replay code path — divergence is how offline and online behaviour drift apart.
- **Never resend a write that may have landed.** A create / comment / worklog is resent blind only when the tracker provably did not apply it (`TrackerError::ProvablyNotApplied`: never sent — a DNS / proxy / connect failure or a cancel before the send — or refused without acting: 429, other 4xx). After a timeout, a 5xx or a success response it could not use, it may have landed: a create is not queued, and on replay it goes to the failed list (`IsAmbiguousCreateFailure`, reason `kAmbiguousCreateReason`), which the panel's ordinary retry skips — only an explicit "not on the tracker" action sends it again. A comment is matched against the tracker before any resend; a worklog waits for the user's review.
- **Writes emit an audit pair.** Replayed and live writes both append a `BackendAuditTrail` begin/result attributed via `FieldEditAuditSource`. Conflict detection (3-way merge for rich text) records its decision too.
- **Parent and child top-ups are worker-side, multi-hop, non-fatal steps.** After the streamed fetch completes cleanly, `TicketSyncService::FetchMissingParentsIntoQueue` chases the ancestor chain hop by hop: each hop fetches the parent keys referenced but not yet held via `ITrackerIssueReader::FetchIssuesForKeys` (no per-backend branching) and queues them as one batch, for at most `kMaxParentFetchHops` (16) hops. It is skipped when the active view has `HideParents` set or `TrackerConfig::LoadParentIssues` is off (Preferences → Editing → Grid behaviour, default on). `FetchChildrenIntoQueue` then walks down from the streamed rows through `FetchChildrenOfKeys`, at most `kMaxChildFetchHops` (16) hops, never asking about a key twice in one sync; it is gated on `LoadParentIssues` only (not `HideParents`). A failed hop becomes `TrackerIssueFetchSummary::Warning` — never a `FetchError` — so the primary results still apply, and a walk that failed or hit its hop cap clears `FullSyncCompleted`, so rows an earlier complete walk cached are kept rather than stale-purged (Pillar 6). Levels past a cap are not loaded by any sync.
- **The cache is namespaced by tracker site and account (#2268).** `smatchet::cache_keys::TrackerCacheBackendKey` (`Config/CacheBackendKeyPure.h`) names the site the data came from: `Jira@<host>#<account hash>`, `Plane@<host>/<workspace>`, `GitHub@<host>/<owner>/<repo>`, `Linear@<host>/<team>` (the bare kind only while unconfigured). It never carries a secret or an email address. Every table keyed by `backend_key` uses it, so two sites (or two accounts) never share tickets, saved lookups or queued writes. A queued row whose key matches no live context is held: replay never sends it to another site, and the Offline Queue panel shows it as held. `TicketSyncService::SwapBackendIfTrackerChanged` treats a same-kind key change (another Jira host or account, Plane workspace, GitHub repo, Linear team) as a backend switch: new client, in-memory tickets cleared.

## Before you edit

- The queue payloads (`PendingCreate`, `PendingFieldEditRecord`) live in Persistence (`CachedTicketTypes.h`); the create/update pipelines live in Tracker. Sync is the seam that ties them — a change here usually touches both neighbours.
